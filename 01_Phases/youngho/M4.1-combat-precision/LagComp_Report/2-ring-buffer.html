Chapter 2

위치 기록 — Ring Buffer

이 페이지에서 배울 것
시간을 되감으려면, 먼저 서버가 "과거에 각 플레이어가 어디 있었는지"를 기억하고 있어야 합니다. 이 페이지에서는 그 기억 장치인 ring buffer(고정 크기 원형 배열)가 무엇이고, 왜 굳이 "고정 크기"여야 하며, 실제 코드에서 어떻게 위치를 기록(RecordPosition)하고 조회(GetPositionAtTick)하는지를 배웁니다.

왜 "고정 크기 원형 배열"인가

과거 위치를 저장하는 방법은 여러 가지입니다. 가장 단순하게는 매 틱마다 위치를 리스트에 계속 추가(append)할 수도 있습니다. 하지만 게임 서버는 50ms마다, 모든 플레이어에 대해 영원히 돌아갑니다. 리스트에 계속 추가하면 메모리가 무한히 늘고, 오래된 항목을 지우는 작업이 또 비용을 만듭니다.

ring buffer는 이 문제를 우아하게 풉니다. 크기가 4로 고정된 배열을 만들고, 쓰기 위치(head, 머리 인덱스)를 0 → 1 → 2 → 3 → 0 → 1 … 처럼 빙글빙글 돌립니다. 5번째로 기록할 때는 다시 0번 슬롯으로 돌아와 가장 오래된 데이터를 덮어씁니다. 우리는 최근 200ms(=4틱)만 필요하므로, 그보다 오래된 위치는 버려도 됩니다.

✅ 고정 배열의 장점

메모리 크기가 처음부터 끝까지 일정합니다. 새로 할당하거나 해제하는 일이 없으니 GC(Garbage Collection, 쓰레기 수집) 부담이 0입니다. 이는 게임 엔진의 표준 패턴으로, Unity의 NGO(Netcode for GameObjects)나 Mirror 같은 네트워킹 라이브러리도 위치 보간(interpolation)에 똑같은 원형 버퍼 방식을 씁니다.

4슬롯이 회전하는 모습

아래 그림은 틱이 진행되면서 head 인덱스가 회전하고, 5번째 틱에서 0번 슬롯이 덮어써지는 과정입니다.

4슬롯이 회전하며 항상 최근 4틱(=200ms)만 유지한다. tick 5가 들어오면 가장 오래된 tick 1을 덮어쓴다.

위치만이 아니라 "몇 번 틱인지"도 함께 저장

여기서 중요한 설계 포인트가 하나 있습니다. 슬롯에 위치(Vector2)만 저장하면, 나중에 "tick 2의 위치를 줘"라고 요청받았을 때 어느 슬롯이 tick 2인지 알 수 없습니다. 슬롯은 재사용되며 덮어써지기 때문입니다. 그래서 우리는 위치 배열과 틱 번호 배열을 짝(parallel arrays)으로 둡니다.

  • Vector2[4] _posHistory — 그 슬롯에 저장된 위치
  • long[4] _posHistoryTick — 그 슬롯이 "몇 번 틱"의 것인지
  • int _posHistoryHead — 다음에 쓸 슬롯 인덱스 (0~3 회전)

조회할 때는 틱 번호 배열을 훑어 일치하는 틱을 찾고, 그 슬롯의 위치를 돌려줍니다. 못 찾으면(=덮어써져 사라졌으면) 현재 위치를 돌려주는 보수적 처리(fallback)를 합니다.

실제 코드 ① — 필드 선언

02_Server/GameServer/Maps/PlayerEntity.cs
// **깊이 = 4 슬롯** = 4 tick = 200ms @20TPS.
//   5 tick 전 attackerClientTick은 rewind 범위 검증에서 silent drop.
const int HistorySize = 4;
readonly Vector2[] _posHistory     = new Vector2[HistorySize];
readonly long[]    _posHistoryTick = new long[HistorySize];
int _posHistoryHead; // 다음 쓰기 index (0~3 회전)

실제 코드 ② — 기록 (RecordPosition)

head 슬롯에 (틱, 위치)를 박고, head를 한 칸 전진시킵니다. % HistorySize 나머지 연산이 인덱스를 0~3 안에서 자동으로 순환시켜 줍니다.

02_Server/GameServer/Maps/PlayerEntity.cs — RecordPosition
public void RecordPosition(long serverTick, Vector2 pos)
{
    _posHistory[_posHistoryHead]     = pos;
    _posHistoryTick[_posHistoryHead] = serverTick;
    _posHistoryHead = (_posHistoryHead + 1) % HistorySize;
}

실제 코드 ③ — 조회 (GetPositionAtTick)

틱 번호 배열을 처음부터 끝까지 훑어 일치하는 틱을 찾습니다. 4개뿐이라 단순 선형 탐색으로 충분합니다. 못 찾으면 현재 위치를 돌려주는데, 이것은 "확신이 없으면 보수적으로 처리한다"는 안전 정책입니다.

02_Server/GameServer/Maps/PlayerEntity.cs — GetPositionAtTick
public Vector2 GetPositionAtTick(long serverTick)
{
    for (int i = 0; i < HistorySize; i++)
    {
        if (_posHistoryTick[i] == serverTick)
            return _posHistory[i];
    }
    // 못 찾음 — 현재 위치 fallback (헌법 #3 보수적 fail-safe).
    return Position;
}

언제 기록하는가 — 타이밍이 중요

"어느 시점의 위치"를 기록하느냐가 정확도를 좌우합니다. 우리는 매 틱의 물리 시뮬레이션(Physics.Step: 이동·중력·점프 적용)이 끝난 직후에 기록합니다. 즉 "그 틱에 실제로 도달한, 물리 적용 후의 최종 위치"를 박습니다.

⚠️ 함정 — 물리 적용 전에 기록하면?

만약 Physics.Step 전에 위치를 기록하면, 그 틱의 이동이 반영되지 않은 옛 위치가 저장됩니다. 나중에 되감을 때 1틱만큼 뒤처진 위치를 돌려주게 되어 판정이 미세하게 어긋납니다. 그래서 코드 주석에도 "Step 후에 기록해야 정확하다"고 명시되어 있습니다.

02_Server/GameServer/Maps/GameMap.cs — Tick() 안의 물리 루프
PhysicsState after = Physics.Step(before, input);
p.Position = after.Position;
p.Velocity = after.Velocity;
p.OnGround = after.OnGround;
p.PendingInputX = 0;
p.PendingJumpPressed = false;
// M4.1 Phase 06 (1단계): Physics.Step 완료 후 위치 기록.
p.RecordPosition(tickNumber, p.Position);

이제 서버는 모든 플레이어의 최근 200ms 위치를 손에 쥐고 있습니다. 다음 페이지에서는 이 기록을 이용해 실제로 "시간을 되감는" 과정을 봅니다.
