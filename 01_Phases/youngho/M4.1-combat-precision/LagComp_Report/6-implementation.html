공격 패킷 한 번의 여정

플레이어가 공격 버튼을 누르면 아래 흐름이 일어납니다. 클라이언트는 의도만 보내고, 모든 판정은 서버 틱 루프 안에서 일어납니다.

클라는 target과 시점만 보낸다. 서버는 network thread에서 패킷을 받아 EnqueueJob으로 tick thread에 위임하고, 모든 판정은 ProcessAttack 안에서 단일 스레드로 처리한다.

C_Attack 패킷 정의 (PDL)

패킷은 직접 손으로 쓰지 않고 PDL.xml(Packet Definition Language)에 정의한 뒤 코드 생성기로 C# 클래스를 자동 생성합니다. 이번에 attackerClientTick 한 줄을 맨 끝에 추가(append-only)했습니다. 주목할 점은 이 패킷에 attacker(공격자) 필드가 없다는 것입니다 — 서버가 세션에서 공격자 id를 강제하므로, 패킷에 attacker를 넣으면 남의 id를 도용할 수 있어 일부러 뺐습니다(헌법 #3).

99_Tools/PacketGenerator/PDL.xml — C_Attack
<!-- 클라 = "공격 시도" / 서버 = hit/miss/damage 권위 판정 -->
<!-- attacker 필드 *없음* — 서버가 세션 id에서 강제 (헌법 #3) -->
<packet name="C_Attack">
    <int name="targetEntityId"/>
    <int name="attackerClientTick"/>   <!-- M4.1 Phase 06 추가 -->
</packet>

ProtocolVersion 4 → 5 bump

필드를 끝에 추가하는 것은 기술적으로 backward compatible(하위 호환)입니다 — 옛 클라가 이 필드를 모르고 0으로 채워 보내도 패킷 자체는 깨지지 않습니다. 그런데도 버전을 올린 이유는, 옛 빌드 클라가 attackerClientTick=0을 보내면 서버 되감기 검증에서 매번 silent drop되어 "공격이 안 먹는" 이상한 경험을 하기 때문입니다. 차라리 핸드셰이크 단계에서 버전 불일치로 빠르게 끊어주는(cutoff) 것이 더 친절합니다.

98_Shared/Protocol/ProtocolVersion.cs
// v5: M4.1 Phase 06 — C_Attack.attackerClientTick 추가 (lag compensation rewind).
//     backward compatible append-only지만 옛 클라가 tick 안 보내면 0 →
//     서버 rewind 범위 검증에서 silent drop 가능 → 빠른 cutoff 위해 bump.
public const ushort Current = 5;
⚠️ PDL 변경 3종 의무

PDL을 수정하면 ① 코드 생성기 재실행 → ② Shared.dll 재빌드(Unity로 자동 복사) → ③ PDL.xml·GenPackets.cs·Shared.dll 세 산출물을 함께 커밋해야 합니다. 하나라도 빠지면 다른 팀원이 pull한 직후 빌드가 깨집니다. 이는 과거 실제 사고에서 박제된 규칙입니다.

새 race(경합) 차원 — 동시성 audit

이번 Phase는 새로운 race condition(경합 조건, 여러 스레드가 같은 데이터를 동시에 건드려 생기는 버그) 차원을 들여왔습니다. ring buffer를 쓰는 시점(틱 스레드)과, 패킷이 도착하는 시점(네트워크 스레드)이 다르기 때문입니다. "한 차원의 race를 막았다고 다른 차원도 안전한 건 아니다"라는 원칙에 따라 별도로 audit(점검)했습니다.

단일 소유(single ownership) 패턴. ring buffer 접근을 한 스레드에 가두면 lock 없이도 안전하다 — GameMap의 actor 모델과 정합.

audit 결과 세 가지를 확인했습니다. (a) 네트워크 스레드는 ring buffer를 직접 만지지 않고 오직 EnqueueJob으로만 일을 넘깁니다. (b) RecordPosition과 GetPositionAtTick은 모두 틱 스레드 단독으로만 호출되므로 lock이 필요 없습니다. (c) 테스트용 봇의 스레드 간 값 가시성은 volatile int로 보장했습니다.

_currentTick 갱신 순서도 중요합니다. 틱이 시작될 때 맨 앞에서 _currentTick = tickNumber를 박은 뒤에 큐의 job(=ProcessAttack)을 처리합니다. 그래야 job 안에서 올바른 현재 틱으로 되감기 범위를 검증할 수 있습니다.

클라이언트 상수 정리 (B1 sweep)

이번 기회에 클라이언트에 흩어져 있던 매직 넘버 9.0f를 TargetingRangeSquared로 이름 붙이고 주석을 달았습니다. 중요한 점은, 이 값이 서버의 권위 판정 상수와는 의도적으로 분리된 별개 개념이라는 것입니다. 이것은 클라이언트가 "어느 적을 공격 대상으로 지명할지" 정하는 UX 힌트일 뿐이고, 실제 hit/miss는 서버의 AABB가 최종 결정합니다.

03_Client/Assets/Scripts/Input/LocalPlayerController.cs
// TargetingRangeSquared = 클라 측 *타게팅 힌트* (3.0f 사거리의 제곱).
// 서버 권위 판정(AABB hitbox)과 *의도적으로 분리*된 별개 개념.
// 헌법 #4 정합 — 밸런스 수식 복붙 X, 클라 UX 힌트.
const float TargetingRangeSquared = 9.0f;

만약 서버 상수를 그대로 복사해 왔다면 헌법 #4(복사-붙여넣기 금지)를 위반했을 것입니다. "역할이 다르면 별개 상수"라는 구분이 핵심입니다.
