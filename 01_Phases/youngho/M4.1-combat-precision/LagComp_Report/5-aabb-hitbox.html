Chapter 5

정밀 충돌 판정 — AABB Hitbox

이 페이지에서 배울 것
되감긴 위치를 손에 쥐었으니, 이제 "맞았는지"를 판정할 차례입니다. 기존의 거리 기반 원형 판정을 AABB(Axis-Aligned Bounding Box, 축 정렬 경계 상자) 박스 교차 판정으로 교체했습니다. 이 페이지에서는 두 박스가 겹치는지 판단하는 알고리즘, 왜 원형에서 박스로 바꿨는지, 그리고 AABB vs capsule(캡슐형) trade-off를 배웁니다.

기존 방식 — 원형 거리 판정

이전 응급 구현에서는 attacker와 적 사이의 거리의 제곱이 사거리의 제곱보다 작으면 명중으로 처리했습니다 (dist² < AttackRangeSquared, 여기서 AttackRangeSquared = 9.0). 제곱근(sqrt)을 피하려고 양변을 제곱한 형태입니다. 단순하지만, 이는 attacker를 중심으로 한 "원" 안에 적이 있으면 무조건 맞는 방식이라, 사이드스크롤 게임의 캐릭터 실루엣(세로로 긴 직사각형)과 잘 안 맞습니다.

새 방식 — AABB 박스 교차

AABB는 "축에 정렬된(기울어지지 않은) 직사각형 박스"입니다. 우리는 박스를 중심(Center) + 반-길이(HalfExtent, 각 축으로 절반 크기)로 표현합니다. 예를 들어 3×3 박스는 중심에서 가로·세로로 각각 1.5씩 뻗으므로 HalfExtent = (1.5, 1.5)입니다.

  • attacker 공격 박스 = 되감긴 위치를 중심으로 한 3×3 (halfExtent 1.5)
  • 적 피격 박스 = 적 위치를 중심으로 한 1×1 (halfExtent 0.5)

이 두 박스가 겹치면 명중입니다.

겹침 vs 안 겹침

왼쪽: 두 박스가 겹쳐 명중. 오른쪽: 한 축에서 분리 갭이 생겨 빗나감. AABB 교차 판정은 "어느 축에도 분리 갭이 없으면 겹침"으로 판단한다.

겹침을 판단하는 알고리즘

두 박스가 겹치지 않으려면, 적어도 한 축(X 또는 Y)에서 둘 사이에 틈이 있어야 합니다. 이것을 수식으로 옮기면 간단합니다. 각 축에서 두 중심 사이의 거리가 두 반-길이의 합보다 작거나 같으면 그 축에서는 겹친 것이고, X와 Y 둘 다 겹치면 박스가 겹친 것입니다.

이는 SAT(Separating Axis Theorem, 분리 축 정리)라는 충돌 판정 이론을 축 정렬 박스에 맞춰 특수화한 형태입니다. 일반 SAT는 회전한 도형까지 다루지만, 축 정렬 박스는 검사할 축이 X·Y 둘뿐이라 비교 몇 번으로 끝납니다.

02_Server/GameServer/Combat/Hitbox.cs — AABB.Intersects
public bool Intersects(AABB other)
{
    float dx = Math.Abs(other.Center.X - Center.X);
    float dy = Math.Abs(other.Center.Y - Center.Y);
    float sumHalfX = HalfExtent.X + other.HalfExtent.X;
    float sumHalfY = HalfExtent.Y + other.HalfExtent.Y;
    return dx <= sumHalfX && dy <= sumHalfY;
}

한 점이 박스 안에 있는지 검사하는 Contains도 같은 발상입니다. 점과 중심의 거리가 각 축의 반-길이 이하면 박스 안입니다.

02_Server/GameServer/Combat/Hitbox.cs — AABB.Contains
public bool Contains(Vector2 point)
{
    float dx = Math.Abs(point.X - Center.X);
    float dy = Math.Abs(point.Y - Center.Y);
    return dx <= HalfExtent.X && dy <= HalfExtent.Y;
}
💡 경계값은 "포함(≤)"으로

비교에 <=(이하)를 쓴 점에 주목하세요. 박스가 정확히 경계에서 닿는 "간신히 닿음" 상황을, 우리는 명중으로 처리합니다. 만약 <(미만, strict)를 썼다면 딱 경계에 닿은 공격이 빗나감으로 처리되어, 플레이어가 "분명 닿았는데 안 맞았다"는 억울한 miss를 겪습니다. 이 경계값 동작은 테스트(AABB_EdgeContact)로 못 박았습니다.

박스 크기는 어디서 나오나

박스 크기는 매직 넘버를 흩뿌리지 않고 한 곳(CombatConstants)에 모았습니다. 기존 사거리 상수 AttackRange = 3.0에서 절반을 취해 AttackHalfExtent = 1.5를 도출합니다. 즉 3×3 공격 박스가 됩니다.

02_Server/GameServer/Combat/CombatConstants.cs
public const float AttackRange = 3.0f;

// M4.1 Phase 06: AABB attack hitbox 크기.
// AttackRange=3.0f → halfExtent=1.5f → 전체 3×3 unit 박스.
public const float AttackHalfExtent = AttackRange / 2f;

AABB vs capsule — 왜 AABB를 택했나

충돌 판정 도형에는 더 정밀한 대안인 capsule(캡슐형: 선분 + 반지름)도 있습니다. 둘 사이에는 명확한 trade-off가 있습니다.

AABB (이번 선택)capsule (M4.3 backlog)
모양축 정렬 직사각형 박스선분 + 반지름 (둥근 캡슐)
계산 비용~5 비교 (싸다)~20 비교 (비싸다)
구현 복잡도단순복잡
점프·회전 정합박스가 실루엣과 약간 어긋날 수 있음정밀
적합 시점지상 공격 위주의 현재 데모보스 AI + 활발한 점프 판정이 생기면
⚖️ 결정 — 지금은 AABB, capsule은 미룸

현재 데모는 지상에서의 공격이 대부분이고, 학습 호흡상 단순한 것부터 익히는 게 맞습니다. capsule은 점프·회전이 게임의 핵심이 되는 시점에 가치가 커지므로 M4.3 backlog로 명시적으로 미뤘습니다. capsule을 지금 도입하면 작업 등급이 "복잡 → 대규모"로 자동 상향될 만큼 범위가 커지므로, scope creep을 피하는 결정이기도 합니다. "더 좋은 것"이 항상 "지금 해야 할 것"은 아니라는, 엔지니어링 판단의 좋은 예입니다.

readonly struct로 만든 이유

AABB는 class가 아니라 readonly struct로 정의했습니다. struct(값 타입)는 힙(heap) 할당을 일으키지 않아 GC 부담이 없습니다. 매 공격마다 박스를 새로 만드는데, class였다면 그때마다 힙에 객체가 쌓여 GC 압박이 커집니다. readonly는 한 번 만든 박스를 실수로 변경하지 못하게 막아 줍니다. 이 또한 Unity의 Bounds처럼 게임 엔진의 표준 패턴입니다.

이제 모든 부품이 갖춰졌습니다. 다음 페이지에서 이 조각들이 패킷 한 번의 흐름 속에서 어떻게 이어지는지 전체 그림을 봅니다.
