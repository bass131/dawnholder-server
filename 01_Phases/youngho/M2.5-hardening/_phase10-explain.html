Phase 10 — "두 이벤트 사이"의 race를 없애기

M2.5 Hardening · netcode · ~1.5시간 · commit 9418ad9
한 줄 요약: 누가 접속하자마자 즉시 끊으면, 서버 상태가 *이상해질 수 있었어요*. 실제로 다른 사람 화면에 "유령 캐릭터"로 보일 수 있는 버그를 사전에 봉합했습니다.

🤔 어떤 문제였나? — "두 이벤트 사이"

🏢 비유 — 회사 입사 + 즉시 퇴사 race
새 직원이 입사했어요. 절차는 두 단계:
① 본인이 인사팀에 ID 카드 신청 (즉시)
② 인사팀이 다음 회의 때 그 신청 처리 → 시스템 등록 (15분 후)

그런데 이 직원이 신청 *직후* 마음 바꿔서 사직서 던지고 나가버렸어요.
옛 규칙: "사직서? 본인 시스템 등록 안 됐으면 패스, 처리 안 함."
결과: 인사팀이 회의 때 신청 처리 → 시스템에 "이미 떠난 직원"이 등록됨. 다른 사람 눈엔 보이는데 실제론 없는 사람.

서버에서 똑같은 일이 일어날 수 있었어요. 두 스레드가 다른 속도로 일하는 사이에 race window가 열려있던 거죠.

🛠️ 어떻게 고쳤나? — 핵심 3가지

① _closing 플래그 추가

BEFORE
각 세션이 "지금 닫는 중인가?"를 알 방법이 없었음. OnDisconnected가 와도 queued job들은 그 상태를 모르고 계속 실행.
AFTER
int _closing = 0; 필드. Interlocked로 cross-thread 안전하게 1로 박음. 다른 스레드는 Volatile.Read로 확인.

② OnDisconnected를 "항상 큐에 넣기"로

BEFORE
if (_entityId < 0) return; — 아직 등록 안 됐으면 그냥 끝.
→ race window 안에 들어가면 cleanup 누락.
AFTER
Interlocked.Exchange(_closing, 1) == 1이면 두 번째 호출이므로 종료.
그 외엔 항상 cleanup job 큐에 넣음. 멱등(idempotent)이므로 안전.

③ "owner 기준" cleanup helper

BEFORE
RemovePlayer(int entityId) — entityId 알아야 cleanup 가능.
→ race window 안에선 entityId가 아직 -1. cleanup 못 함.
AFTER
RemovePlayerBySession(owner) — 세션 참조 기준.
→ entityId 모를 때도 owner-ref로 찾아서 제거. 0건이어도 안전(멱등).

💡 핵심 개념 두 가지

🏃 분산 시스템의 "두 이벤트 사이"

A 이벤트와 B 이벤트가 서로 다른 스레드에서 진행되면, 그 사이 시간에 *세 번째 이벤트*가 끼어들 수 있어요. 이게 race condition의 본질.

이 패턴은 게임 서버만 아니라 Discord 봇, gRPC 스트림, REST API의 webhook 등 모든 long-lived 세션의 공통 함정. M3에서 사람이 늘면 더 자주 발생할 것.

🔁 멱등성 (Idempotent) cleanup

"같은 함수를 두 번 불러도 결과가 같다"가 멱등성. 본 Phase의 RemovePlayerBySession은 owner가 없으면 0건 반환 — 두 번 호출해도 OK.

분산 시스템 cleanup의 표준 패턴: "항상 큐에 넣되 함수 자체는 멱등" = 락 없이 race를 봉합하는 방법.

🧪 무엇을 검증했나? — 결정론적 race regression

8개 자동 테스트 — 그중 핵심은 결정론적(deterministic) race 재현. CPU race를 실제로 트리거하지 않고 ConcurrentQueue 순서만 직접 제어해서 같은 race를 100% 재현.

✓ A 정순 race — OnConnected → OnDisconnected → tick 1회 → players=0 + "AddPlayer skipped" 로그
✓ A2 역순 race — OnDisconnected → OnConnected → tick 1회 → players=0 (Codex β 권장 추가)
✓ B 정상 flow 회귀 — 일반 connect/tick/disconnect는 영향 X
✓ C 이중 호출 멱등성 — OnDisconnected 2번 호출 → 로그 1회만
✓ D rapid 100회 smoke — 누적 누수 X
✓ E disconnect-only edge — connect 없이 disconnect만 와도 crash X
✓ F owner 정확성 — 두 세션 중 한 명만 disconnect 시 다른 사람 영향 X
✓ G entityId reset — cleanup 후 낡은 id 잔존 안 함 (Codex β 권장 추가)

🤝 Codex β 검토 — 안전망 평가

Codex β가 코드 검토 후 "전체 구조 OK". 단, 2건 추가 권장 → 100% 반영:

  • cleanup 후 _entityId reset 누락 — 기능상 ghost는 막혔지만 낡은 id가 로그/방어 로직에 남음. self._entityId = -1; 추가.
  • OnDisconnected → OnConnected 역순 시나리오 미테스트 — race 안전망의 대칭성 입증. ScenarioA2로 박음.

추가 발견 — int _closing + Interlocked.Exchange + Volatile.Read 조합이 cross-thread 플래그 용도로는 충분하다는 확인. ReferenceEquals(p.Owner, owner)도 owner가 null인 entity 안 건드림 (NRE 위험 X).

한 줄 마무리: M3에서 두 명이 같은 맵에 들어가면 누군가는 분명히 connect 직후 끊을 거예요. 그때 우리 서버에 ghost player가 안 남아요. 비동기 race를 결정론적으로 재현 가능한 테스트 패턴도 함께 박았으니, 비슷한 race가 다른 영역에서 발견돼도 같은 패턴으로 잡으면 됩니다.
