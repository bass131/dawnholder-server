왜 본 문서가 있나: Hamachi 시연 검증 도중 발본한 서버 race condition 사고 + 본인 의심 "패킷이 Queue에 제대로 박히는 거 맞나?" 분석을 박제. 캡스톤 평가 자산 + 면접 결정타 소재.

1. 사고 발견 경위

M3.8 Phase 05 마감 의례 직전, Hamachi 가상 LAN 시연 검증 단계에서 본 머신 + 서브 노트북 2 인스턴스 통신 점검 도중 서버 콘솔에 다음 박힘:

흥미로운 관찰: Unhandled exception이 박혔는데 서버가 즉시 죽지 않음. [Tick] #140~#180 계속 흐름. 이게 더 위험한 패턴이에요 — IOCP worker thread가 1개씩 점진 소모. Listener.Init에서 _register=10 박힌 worker가 모두 소모되면 신규 accept 거부 → 서버 효과적 사망. 시연 중 조용히 망가짐.

2. Race Condition (경쟁 상태)이 뭔가요?

두 개 이상의 thread(흐름)가 같은 자원을 동시에 박을 때, 누가 먼저 박는지에 따라 결과가 달라지는 상황이에요. 본 사고의 자원 = args.AcceptSocket이라는 TCP socket 객체.

  • Thread A — 서버 OnAcceptCompleted 콜백 (accept 통과 후 socket 박는 흐름)
  • Thread B — .NET 내부 socket lifecycle 관리 thread (클라이언트가 close 박으면 서버 측 socket을 dispose 박는 흐름)

두 thread가 박는 타이밍에 따라 사고가 박힘.

3. 본 사고의 시간순 시나리오

시간누가뭘 박음socket 상태
T+0서버accept 통과 → args.AcceptSocket 박힘alive
T+1서버session = m_SessionFactory.Invoke()alive
T+2서버session.Start(args.AcceptSocket) — IO 등록alive
T+3클라이언트close() 박음 (ConnectionProbe 패턴)→ FIN 패킷 전송
T+4.NET 내부서버 측 args.AcceptSocket dispose 박힘 ★disposed!
T+5서버args.AcceptSocket.RemoteEndPoint 박으려 함💥 ObjectDisposedException

T+3 ~ T+4의 짧은 창이 race window. 평소엔 클라이언트가 connect → handshake → 한참 후 close 박았기 때문에 T+5 시점엔 socket이 alive였어요. 그런데 5-B에서 박은 ConnectionProbe.TryConnect는 connect 통과 즉시 close 박는 패턴 → race window가 매번 노출 → 사고 표면화.

4. 왜 옛에 안 박혔나? (M2.5 봉합 영역과 본 사고의 차이)

M2.5 Phase 10에서 봉합한 race는 GameSession 내부 — session이 박힌 후의 lifecycle race (connect job vs disconnect handler). 본 사고는 Listener accept callback의 race — session 박기 전의 race라 옛 봉합 영역 밖.

"차원이 다른 race"는 박혀있을 수 있고, 한 차원 봉합이 다른 차원 안전을 보장 X. 시스템 외곽까지 audit 박는 게 정합 — 본 사고가 그 교훈 실증.

5. 봉합 패턴 (try-catch + early skip + fail-closed)

race window 박는 거 자체는 TCP 본성이라 피할 수 없어요. 하지만 socket이 disposed면 예측 가능한 예외(ObjectDisposedException)가 박혀요. 그러니까:

  • 예외 잡고 정상 처리 = race window 박혀도 서버는 안 죽음
  • "fail-closed" 패턴 (헌법 #3 Trust Boundary 정합) = 사고 박히면 본 connection 포기 + 다음 accept 박는다 = 서버 process 보호

봉합 전 (사고 코드)

void OnAcceptCompleted(object? sender, SocketAsyncEventArgs args)
{
    if (args.SocketError == SocketError.Success)
    {
        Session session = m_SessionFactory!.Invoke();
        session.Start(args.AcceptSocket!);
        session.OnConnected(args.AcceptSocket!.RemoteEndPoint!); // ← 💥 race window
    }
    else { Console.WriteLine(args.SocketError.ToString()); }
    RegisterAccept(args);
}

봉합 후 (race window 안전)

void OnAcceptCompleted(object? sender, SocketAsyncEventArgs args)
{
    if (args.SocketError == SocketError.Success)
    {
        Socket acceptedSocket = args.AcceptSocket!;
        EndPoint? remote = null;
        try { remote = acceptedSocket.RemoteEndPoint; }
        catch (ObjectDisposedException)
        {
            // race window — 클라가 accept 직후 close. session 박지 않고 skip.
        }

        if (remote != null)
        {
            Session session = m_SessionFactory!.Invoke();
            session.Start(acceptedSocket);
            session.OnConnected(remote);
        }
        else
        {
            try { acceptedSocket.Close(); } catch { /* swallow */ }
        }
    }
    else { Console.WriteLine(args.SocketError.ToString()); }

    RegisterAccept(args); // race 분기에서도 다음 accept 의무
}

6. 비유로 이해하기

문지기(Listener)가 입장객(accept된 socket)을 안내처(session)로 데려가는 중인데, 입장객이 안내처에 도착하기 전에 갑자기 사라짐 (close). 문지기가 "이 입장객 이름 뭐였지?" (RemoteEndPoint) 박으려고 돌아봤는데 이미 사라진 상태 → 문지기가 충격 받고 쓰러짐 (process 죽음).

봉합 = 문지기가 "어, 사라졌네? 그럼 다음 입장객 받자" 박는 거 (try-catch + 다음 accept).

7. 본인 의심 답변 — 패킷이 Queue에 제대로 박히는가?

본인 의심: "애초에 패킷이 들어와서 처리되는 서순 보장되게 Queue에 제대로 들어가는거 맞나?"

결론 먼저: Queue 자체는 제대로 박혀 있어요. 진짜 race는 Queue 진입 시점이 아니라 socket lifecycle 외곽에 박혀있고, 그게 바로 본 Listener 사고. 본인 의심이 핵심을 가리켰지만 위치가 한 단계 밖이에요.

패킷 처리 3-layer 흐름

┌─ Layer 1: socket worker (IOCP) thread ────────────────────────┐ │ TCP byte 수신 → 프레이밍 통과 → OnRecvPacket(buffer) 호출 │ │ ★ TCP 본성: 같은 connection의 byte는 *순서 보장* ★ │ └────────────────────────────────────────────────────────────────┘ ↓ (같은 thread, sync 호출) ┌─ Layer 2: HandlerRegistry dispatch ───────────────────────────┐ │ PacketID 추출 → IPacketHandler.Handle() → session 캡슐화 │ │ 메서드 (SubmitMoveIntent / SubmitAttack 등) 호출 │ │ ★ decode + 검증만, mutation 없음 ★ │ └────────────────────────────────────────────────────────────────┘ ↓ (EnqueueJob — thread-safe queue) ┌─ Layer 3: GameMap tick thread (단일!) ─────────────────────────┐ │ 50ms마다 (20 TPS) Queue 풀어서 FIFO 처리 │ │ ★ 한 맵 = 한 thread → lock-free + 순서 보장 ★ │ └────────────────────────────────────────────────────────────────┘

케이스별 보장 정합 (3가지)

케이스보장메커니즘
같은 클라의 연속 패킷 A1 → A2 → A3 ✅ 보장 TCP 순서 + 같은 IOCP thread sync 처리 + Queue FIFO. A3가 A1보다 먼저 박힐 일 X
다른 클라 간 패킷 A vs B ⚠️ 부분 보장 물리 도착 순서 ≠ Queue 진입 순서 가능 (각 클라마다 다른 IOCP thread). 다만 20 TPS tick window 안에 들어오면 같은 tick에서 처리 → 게임 본질 영향 X (이동 = PendingInputX 박는 거라 순서 의존 X). 진짜 순서 중요한 거 = 전투 (먼저 친 사람 우선) → M4+ lag compensation으로 별도 봉합 예정
session 내부 state (_handshakeCompleted/_entityId) ⚠️ 부분 보장 bool은 atomic이라 read tear X. 다만 visibility는 Volatile.Read/Interlocked 박은 곳만 보장. _closing은 박음, _handshakeCompleted는 안 박음. M2.5에서 일부 봉합, 잔여 race 가능성은 별 시점 audit

진짜 잠재 race 영역 3개

  1. 본 Listener accept callback race — 본 commit으로 봉합 ✅
  2. 다른 클라 간 도착 순서 — 게임 본질 영향 X, M4+ lag compensation 예정
  3. session state visibility — bool 박힌 거는 안전, 별 시점 audit 박을 가닥

8. 면접 자산화 정신

"M2.5에서 session 내부 race는 봉합했는데, 캡스톤 1 시연 검증 중 Listener accept callback의 다른 차원의 race를 발본했고, try-catch + early skip + fail-closed 패턴(헌법 #3 Trust Boundary 정합)으로 봉합했다."

이게 경험 있는 백엔드 신예의 정통 답변. 한국 게임 회사 백엔드 면접 결정타 소재 = 발견 + 봉합 사이클 그 자체의 가치 박제.

9. false-promise cadence 박제 (ADR-024 정합)

본 사고 = M3.8 누적 22번째 false-promise 변종 (옛 21건 + 본 사고 1건). ADR-024 박힌 cadence 정합 — 마일스톤 마감 -DONE.md "false-promise 점검 결과" 섹션에 박을 가닥.

본 변종의 특징: 옛 변종(폰트 false-promise, PretendardStd 영문만 박힌 거 등)은 약속 vs 실재 불일치였는데, 본 사고는 한 차원 봉합이 다른 차원 안전 보장 X라는 더 깊은 패턴. ★★★ 학습 자산.
