🧭 결정 흐름 · SendBuffer 사건

감사 #4: "dead code 삭제" JobQueue/PriorityQueue/SendBuffer
PriorityQueue는 0참조+0테스트+잠재버그 → 삭제. SendBuffer도 같은 묶음으로 AI가 "삭제" 추천.
영호 제동 "0참조라고 삭제 아니지?"
"패킷 어떻게 보내는데?" — 미참조 코드를 갈래 분류 없이 지우려던 것을 멈춤.
실측 = 송신 경로 추적
Session.cs가 패킷당 new byte[] → _sendQueue → SendAsync(BufferList) 직접. SendBuffer(청크 재사용 GC최적화)는 끼우지 않은 참조 구현 = JobQueue 동급.
결론: 삭제 X, 정직 라벨 3f8aed2
02_Server/CLAUDE.md + 양쪽 SendBuffer.cs 헤더 + PacketFormat.cs 주석 4곳 정정. 교훈 memory 박제 + M8후 perf 백로그.

#8 실측 정정 — work-pin 가정("BossStates 중복")은 코드와 달랐다: BossStates.ApplyBossAttack은 ApplyMeleeDamage에 위임만 해 사망/부활 site는 단일. death-guard는 즉시부활로 도달불가. plan-auditor가 코드로 검증 → 범위 밖 잔류.

#8 클라↔서버 시너지 — 서버가 S_PlayerHp(0)→(MaxHp) 순으로 보내므로, 클라 사망 페이드를 권위 HP 채널(currentHp≤0)에서 도출하면 DoT/함정/투사체 등 모든 사망 소스에 robust.
