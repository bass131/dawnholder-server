본인이 느낀 "공격 중 이동 가능 = 동작이 안 딱 떨어짐"은 코드로 확인됐습니다. 그런데 이건 사실 두 개의 다른 문제가 겹친 거예요 — ① 규칙이 빠진 것(공격 커밋/이동 잠금 = 서버 권위)과 ② 구조가 안 깔끔한 것(State 클래스화 = 코드 품질). 본인이 말한 "Exit Time"의 진짜 정체는 ①이고, "State 추상화"는 ②입니다. 둘을 분리해야 설계가 풀려요.

✅ 이미 잘 돼 있는 것

  • AnimState(시각) ↔ EnemyState(AI) 분리 — 클라는 AI 상태를 아예 모르고 애니만 받음. 이 경계는 리팩토링 후에도 유지.
  • Tick 루프 순서 명문화 — GameMap.Tick()에 System 호출 순서가 박혀 있음.
  • 보스가 독립 System — 일반 AI와 격리돼 있어 난이도 손대도 번짐 없음.

⚠️ 손볼 여지

  • 플레이어엔 "행동 상태" 개념 자체가 없음 — 공격은 그냥 AttackLatchTicks=8 카운터(애니 전용).
  • 타이밍 메커니즘 2개 혼재 — rate-limit(ms) vs latch(tick).
  • 적 AI는 아직 2상태뿐 — 풀 클래스 계층이 당장은 과할 수 있음.

2 핵심 발견 — "공격 중 이동"은 왜 일어나나

🔍 확인 사실   서버 SubmitMoveIntent()에 공격 상태 체크가 0줄입니다. AttackLatchTicks(8틱=400ms)는 Attack 애니메이션만 구동하고, 이동을 전혀 막지 않아요. → 지금 "공격"은 겉모습(애니)만 있고 게임플레이 커밋(이동 잠금)은 없는 상태.

두 입력(이동·공격)이 서버에서 완전히 따로 처리돼요. 공격이 이동에게 "나 지금 공격 중이야, 멈춰" 하고 말을 거는 길이 아예 없습니다. 그래서 동시에 일어나요.

3 개념 분리 — 규칙 vs 구조

본인이 한 덩어리로 말한 걸 둘로 쪼개야 합니다. 이게 이번 논의의 핵심이에요.

① 규칙 서버 권위

"공격은 끝까지 커밋 → N틱 동안 이동 잠금"

= 본인이 말한 "Exit Time"의 진짜 정체. 게임플레이 규칙이라 서버가 진실의 원천이어야 함 (헌법 #1). 클라 Animator의 Exit Time은 이걸 따라가는 거울일 뿐.

이게 "동작이 딱 떨어지는 느낌"을 실제로 만듦.

② 구조 코드 품질

"State를 추상 베이스 + 클래스로, 전환 시 행동 분기"

= State 패턴 / 계층형 FSM. enum+switch가 비대해질 때 가는 정석. 코드 정리·확장성 문제지 동작 자체는 안 바꿈.

이것만 해선 여전히 공격 중 움직임.

왜 중요하냐면 — ②(구조)만 멋지게 리팩토링해도 ①(규칙)이 없으면 공격 중 이동은 그대로예요. 반대로 ①만 넣어도 동작은 딱 떨어집니다. "느낌"을 고치는 건 ①, "코드"를 고치는 건 ②. 둘 다 가치 있지만 별개의 일.

4 서버 권위 경계 — FSM은 사실 "두 개"

플레이어 한정으로 가장 조심할 부분. "Exit Time"을 Unity Animator 전환 조건으로만 두면 핵 취약점이에요 — 조작된 클라가 공격 중에 그냥 움직여버립니다.

권위 아님

규칙(이동 잠금)은 왼쪽 빨강(서버)에 살고, 오른쪽 초록(클라)은 그걸 보고 애니만 맞춰요. 몬스터·보스는 아예 오른쪽에 예측조차 없이 100% 서버가 시키는 대로.

5 제안 — 플레이어부터 "수직 슬라이스"

셋(플레이어·몬스터·보스)을 한 번에 갈아엎는 대신, 플레이어 한 줄기를 끝까지 먼저 만들어 패턴을 증명하고 확장합니다. 위험 ↓, 학습 호흡 유지.

서버에 클래스 기반 ActionState FSM + commit window 도입 → "공격 중 이동 잠금" 규칙 구현. 클라 Animator는 미러.

서버 클라
