# 실제 DB 1단계 — 시험 DB 생성과 기본 스키마 설치를 시도한 의도와 과정

이 문서는 [실제 SQL 설치·엔진 판정 goal](goal.md)의 첫 실제 DB 실행인 「DB 1단계」(2026-10-05)를 사람이 읽기 쉽게 다시 정리한 과정 기록이다. 무엇을 증명하려 했는지, 왜 그런 순서와 안전장치를 썼는지, 실제로 무슨 일이 있었는지를 담는다. 2026-10-05 시도 기준으로 고정한 기록이며, 이후의 진단과 결과는 goal의 [재개 지점](goal.md#재개-지점)에서 확인한다. goal의 상태 서술이 이 문서와 다르면 goal이 원본이다.

- 요청: 사용자 「그러면 지금까지 한 일련의 과정들이 무슨 의도고 왜 했어야했는데 운영툴 기록에도 작성해줘」(2026-10-05, 메인 `msg_2ecb51e414d5` 전달). 운영툴 기록은 2026-10-06 사용자 결정에 따라 원문을 프로젝트 문서에 두고 링크만 건다.
- 작성: Management 리드(지정 모델 `claude-opus-5-5`, 실제 backend unknown)가 goal과 로컬 원시를 직접 대조해 썼다. 사실·용어 검토와 병합 뒤 소유는 Core다.

## 한 줄 요약

1단계는 준비 확인과 장치·서비스 확인까지 마쳤다. 그러나 SQL Server 서비스 시작이 실패해 멈췄다. 시험 DB 생성과 기본 스키마 001 설치는 실행하지 않았다. 원인은 이 기록 시점에 진단 중이다.

## 왜 이 단계가 필요했나

직전 [SQL 영속성 구조와 오프라인 검증 goal](../2026-10-02-persistence-repository/goal.md)(PR169)은 기본 스키마 `99_Tools/database/migrations/001_initial.sql`과 시험 환경 도구(`99_Tools/database/test-environment/New-TestDatabase.ps1` 등)를 만들었다. 하지만 검증은 실제 SQL 엔진 없이 오프라인 시험과 대역 실행으로만 했다. 오프라인 시험 통과만으로는 실제 SQL Server에서 DB가 만들어지고 스키마가 설치된다고 말할 수 없다.

그래서 이 goal은 실제 SQL Express에서 두 가지를 차례로 증명하려 했다.

1. **1단계:** 승인된 시험 DB 하나를 실제로 만들고 기본 스키마 001을 설치한다. 각 직후 상태를 읽기 전용으로 기록한다.
2. **2단계:** 그 DB에서 설치를 마무리하고 실제 엔진 판정(U-01)을 한다.

두 단계를 나눈 이유는 메인 판단 `msg_5d2ef0b0289f`에 있다. 2단계의 정확한 명령과 hash는 1단계가 실제 기록 파일(manifest)을 만든 뒤에야 확정할 수 있다. 그래서 사용자 실행 승인도 단계마다 따로 받기로 했다. 1단계 승인이 실패 뒤 정리(DROP)나 2단계까지 허락하는 것은 아니다.

## 어떻게 하려 했나 — 순서와 안전장치의 이유

사용자는 「3) 실제 DB 1단계 - 시험 DB 생성·기본 스키마 설치를 지금 실행할지 → A 지금부터 20:00 KST까지 실행 승인 · 4) 실제 DB 1단계 - 끝난 뒤 SQL 서비스를 끌지 → A 1단계 끝나면 바로 끄기」로 승인했다(메인 `msg_31fb076e492d`, 2026-10-05T09:20:15Z 전달). 계획은 14단계였다. 순서는 가상 디스크 마운트 → 관리자 창 → 준비 → 장치·서비스 확인 → 서비스 시작 → 생성 계획 → DB 생성 → 생성 후 관측 → 기본 스키마 설치 → 설치 후 관측 → 서비스 종료 → 창 기록 종료이고, 두 관측 앞에 관측 종류를 고르는 한 줄 입력이 하나씩 있다.

| 안전장치 | 이유 |
|---|---|
| 가상 디스크 `C:\myVHDX.vhdx`를 D:로 직접 마운트 | SQL Express가 D:의 `D:\MSSQL2025\MSSQL17.SQLEXPRESS\` 아래 설치돼 있고, 이 디스크는 평소 분리돼 있다. 에이전트가 시도한 승격 마운트는 권한 확인에서 거부돼 사용자가 직접 마운트한다. D:가 아닌 문자가 붙으면 바꾸지 않고 멈춘다. |
| 사용자 본인이 같은 승격 Windows PowerShell 5.1 창 하나에서 실행 | 서비스 시작과 DB 생성은 관리자 권한이 필요하다. UAC·SQL 실행을 에이전트에게 맡기지 않는다. 한 창만 쓰면 각 블록이 같은 프로세스(PID)에서 나왔는지 확인할 수 있다. |
| 고정 명령으로 관리자 창 열기(`-NoProfile` 등) | 사용자 프로필과 다른 셸의 모듈 경로가 섞이는 것을 막는다. |
| 준비 블록 | 창 기록(transcript)을 시작하고, PID·계정 SID·관리자 여부를 고정하고, 제품 파일 39개의 hash와 승인된 실행 계획의 SHA·승인 ID를 대조한다. 검토받은 코드·계획과 실제로 실행하는 것이 같다는 증거를 남기기 위해서다. 이후 블록마다 같은 대조(guard)를 반복한다. |
| 한 블록씩 제출하고 출력을 확인한 뒤 다음 블록 | 부분 실패를 성공으로 넘기지 않기 위해서다. 오류가 나면 다음 DB 블록을 넘기지 않는다. 자동 재시도·창 재시작·수동 DROP·설정 변경으로 우회하지 않고 기록과 부분 상태를 보존한다. |
| 생성 직후·설치 직후의 읽기 전용 관측 | DB 상태(역할, 다른 연결, 엔진 정보, 스키마 결과 등)를 원시로 남겨 다음 블록 진행을 판단한다. |
| 끝나면 서비스 끄기, 창 기록 종료는 맨 마지막 | 사용자 결정 4)를 따른다. 서비스 종료 블록의 guard가 창 기록이 열려 있기를 요구하므로 순서는 서비스 종료 → 창 기록 종료다. |
| 20:00 KST 시간 창 | 승인 범위를 시간으로도 한정한다. 시간이 지나면 새 블록을 시작하지 않는다. |

## 실제로 일어난 일 (2026-10-05, KST)

- **18:44 장치 전제 정정.** 메인이 D:를 SanDisk USB로 잘못 해석해 「USB 연결」을 안내했다. 사용자가 「USB 연결은 무슨 말이야? 애초에 DB는 저번에 C드라이브에 가상 드라이브로 마운트 했던거로 기억하는데」라고 바로잡았다(메인 `msg_f061272f74cb`). 가상 디스크라는 실행 전제가 저장소와 메모리 어디에도 적혀 있지 않았던 것이 원인이다. 안내를 v2로 고쳤다.
- **18:50 마운트 완료.** 사용자가 마운트를 마쳤고 메인이 D:와 `sqlservr.exe` 경로, 서비스 Stopped/Manual을 읽기 확인했다고 보고했다(`msg_8739f507da55`).
- **19:02~19:15 창 순서가 꼬임.** 사용자가 직접 연 관리자 창, 고정 명령으로 연 창, 메인 자신의 조회 프로세스가 섞여 어느 창에 준비 블록을 넣을지 불분명해졌다. 사용자는 「순서가 꼬여서 다시 해야할 거 같은데, 처음부터 차근차근 다시 알려줘」라고 했다. 처음 창에서 준비 블록을 제출하지 않았다는 사용자 답(「안 눌렀어」)을 받은 뒤에 다시 시작했다. 실패한 준비를 다시 제출하는 일을 피하기 위해서다.
- **19:15 붙여넣기 대신 파일 실행.** 새 관리자 창이 콘솔 선택 모드에 걸려 붙여넣기가 되지 않았다. 사용자가 「그냥 너가 의도하는 스크립트를 파일형태로 만들어서 내가 관리자 권한으로 파워셀로 실행하는건 안되나?」라고 제안했다. 승인된 준비 블록과 내용이 같은 파일(136행, 승인 hash만 채움)을 만들어, 같은 승격 창에서 그 파일을 dot-source로 실행하는 방식으로 바꿨다. 같은 창 안에서 실행해 PID 대조를 유지하려는 선택이다.
- **모듈 경로 문제.** 메인 보고에 따르면 다른 셸(PowerShell 7)의 모듈 경로(PSModulePath)가 상속돼 PowerShell 5.1에서 `Get-FileHash`가 실패했다(`msg_039a453e53e8`). 환경을 정리해 연 일반 창에서 관리자 창(PID 27280)을 다시 열어 해결했다.
- **19:21:09 준비 성공.** 창 기록 원시에 따르면 PID 27280, PowerShell 5.1.26100.9444 Desktop, 관리자 true, 제품 파일 39개 불일치 0, 승인 실행 계획 SHA와 승인 ID 일치다.
- **19:23 장치·서비스 확인.** D:는 파일 시스템으로 보였다(사용 3.27GB, 여유 16.71GB). 서비스 `MSSQL$SQLEXPRESS`는 Stopped/Manual이고 실행 경로는 `D:\MSSQL2025\MSSQL17.SQLEXPRESS\MSSQL\Binn\sqlservr.exe`였다.
- **19:30:15~17 서비스 시작 실패.** 서비스 시작 블록의 guard는 같은 PID·39/0·승인 대조를 통과했다. 그러나 2초 뒤 `Start-Service`가 `StartServiceFailed`로 끝났다.
- **19:35:12 멈추고 기록 종료.** 재시도하지 않았다. Core가 서비스가 Stopped/Manual임을 읽기 확인했다. 서비스가 켜지지 않았으므로 서비스 종료 블록은 건너뛰고 창 기록 종료 블록만 제출했다. 같은 PID의 종료 기록과 transcript 끝을 확인했다. DB 생성·생성 후 관측·스키마 설치·설치 후 관측은 실행하지 않았다.
