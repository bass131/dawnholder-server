2. 왜 이 순서인가

병렬
01 + 02 동시 시작 가능
01(Unity 캐릭터 로컬 이동)과 02(서버 tick 루프)는 서로 의존 X. 학부생 페이스라 순차로 가도 되지만, 막히면 다른 쪽 먼저 진행 가능한 안전판.
필수 선행
03 핸드셰이크가 04 앞에
04(이동 패킷)이 의미 있으려면 "서버에 내 entity 존재 + 좌표 합의" 상태가 먼저 필요. 03 빼면 "누구의 좌표를 옮기는 거지?"부터 모호.
의도된 한계 노출
04는 prediction 없이 (lag 체감)
키 누르면 ~250ms 후 움직임 → "이거 느려요"를 본인 눈으로 보게. 그 고통이 05의 동기 부여. 학습 모드의 핵심 패턴.
면접 무기
05 (snap) → 06 (replay) 분리
"처음엔 snap으로 했는데 점프 보이길래 replay로 진화시켰어요" 서사를 위해 일부러 두 Phase로. 합치면 그냥 "구현했어요"가 됨.
변수 통제
07 점프를 마지막에서 두 번째로
점프는 중력 + ground 충돌 + state machine이 한 번에 옴. 좌우 이동이 완전히 안정된 다음 얹어야 디버깅 변수가 적음.
증명 영역
08을 별 Phase로 분리
봇 회귀, p99 측정, 영상 캡처는 코드 작성이 아니라 증명. 영역(qa-sim) 달라서 같은 Phase에 끼우면 컨텍스트 스위칭 비용 큼. M1 Phase 07 후속 패턴 재사용.

4. 만약 다르게 했다면 — trade-off

방식 장점 단점 왜 안 골랐나
대안 A — 5개로 응축
(01+02, 05+06, 04+07 묶기)		 호흡 짧음. 진도 빨라 보임. 변수 너무 많이 동시 → 디버깅 미궁. prediction 진화 서사 사라짐. 체감 시간은 비슷하거나 더 김(디버깅). 면접 무기 약함.
대안 B — 15개로 잘게
(패킷마다, 검증마다 따로)		 매번 만족감. 막힐 가능성 거의 0. 데모 누적 느림. 5단계 보고 + DONE 박제 의식 비용 폭증. 캡스톤 1 fallback 위험. 학습 호흡 너무 잘게 잘림.
대안 C — 기능 묶음
(좌우+점프+prediction 한 번에)		 일반 게임 회사 개발 흐름. "prediction 왜 필요?"를 경험으로 알 기회 사라짐. 학습 모드엔 부적합. 본인 처음 만드는 영역이라 학습 손실 큼.
✅ 우리 — 8개 캡스톤 fallback 안전 + 면접 서사 누적 둘 다 잡음. Phase 수 중간 → 호흡이 길게 느껴질 수도. —
