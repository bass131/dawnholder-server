2문제

SQL 서비스가 master 데이터베이스 파일 두 개를 열지 못해 시작에 실패했다. 이 실패가 DB 단계와 그 뒤 Core 영속화 작업을 막고 있다.

무슨 일이 있었나

2026-10-05 19:30:15 KST에 사용자가 관리자 창에서 SQL 서비스 시작을 요청했다. 19:30:17에 Start-Service는 StartServiceFailed로 끝났다. 사용자는 재시도하지 않았다. 서비스는 Stopped/Manual 상태로 남았다.

SQL 서비스의 자체 로그 파일인 ERRORLOG에는 아래 줄이 남았다. 두 파일 모두 OS 오류 5, 곧 「액세스가 거부되었습니다」다. 그 직후 SQL 서비스는 종료 코드 114로 스스로 종료했다.

막힌 일

  • Core 파트 goal 「실제 SQL 설치·엔진 판정」의 「DB 생성 실행」 단계가 멈췄다. DB 생성과 설치는 실행하지 않았다.
  • 뒤 단계는 모두 이 단계 뒤에 있다. 설치·판정 계획 실사, 실제 DB 설치·판정, 엔진 판정 PR·CI·병합, 시험 DB 정리, 결과 기록·종료다.
  • PR190 - 설치·검사 도구와 DB 1단계 기록은 2026-10-06에 체크포인트로 병합됐다. 엔진 판정은 다음 PR로 나뉘었다. 그 PR의 완료조건은 실제 SQL 엔진에 설치하고 판정한 원시 기록이므로, SQL 서비스가 시작돼야 진행할 수 있다.

3이미 확인한 것

읽기 조사 다섯 번에서 파일 권한·디스크 연결·필터 목록은 문제가 없어 보였다. 그러나 실패한 순간의 실제 접근 요청과 거부 주체는 어느 조사도 보지 못했다.

아래 조사는 모두 읽기만 했다. 서비스 재시작, 권한 변경, 재마운트는 하지 않았다. 시각은 2026-10-05 KST다.

왜 이것으로 부족했나

  1. ACL은 「누구에게 허용하는가」라는 정적 설정만 보여 준다. 실패 순간에 SQL 서비스가 어떤 계정으로, 어떤 권한을 요청했는지는 보여 주지 않는다.
  2. 파일 시스템 감사가 꺼져 있었다. 그래서 거부 사건이 Security 이벤트 로그에 남지 않았다.
  3. 필터 목록은 이름과 순서만 보여 준다. 어느 필터가 요청을 막았는지는 보여 주지 않는다.
  4. 결론: 정적 읽기로는 더 좁힐 수 없다. 실패하는 순간의 파일 열기를 기록해야 한다.

4왜 Procmon인가

Procmon은 보안 설정을 바꾸지 않고 실패하는 순간의 파일 열기를 기록한다. 승인안에 따르면 Microsoft의 오류 17204 지침도 이 방법을 제시한다.

Procmon(Process Monitor)은 Microsoft Sysinternals 도구다. 프로세스가 만드는 파일·레지스트리·프로세스 이벤트를 시각, 경로, 결과와 함께 기록한다. 이 기능을 위해 커널 필터 드라이버를 잠시 올린다.

다른 방법과 비교

감사 설정 추가 + 재시작

Fable 초안의 방법이다. 파일에 감사 항목(SACL)을 넣고 감사 정책을 켠 뒤 SQL 서비스를 다시 시작한다.

문제: 보안 설정을 바꾼다. 리드 실사(FJ-3)는 감사 항목을 원래대로 되돌린다는 보장이 없다고 지적했다.

채택 안 함

Procmon 관측 + 시작 1회

보안 설정은 그대로 둔다. Procmon을 켜고 SQL 서비스를 한 번만 시작한다.

대가: 도구 다운로드, 일시 드라이버 로드, Procmon 설정 흔적이 생긴다. 승인안은 이것을 승인 대상으로 적었다.

채택

근거: D/astra-fable-settlement.md 33·86행. 86행은 「SACL 변경 방식은 원본 보존과 정확 원복·정책 재검증이 완성되기 전 선택하지 않는다」고 적었다.

주의: Procmon이 거부를 보지 못할 수도 있다

필터 드라이버는 고도 순서로 쌓인다. 숫자가 큰 필터가 위에서 요청을 먼저 받는다. 위 필터가 요청을 먼저 끝내면 아래의 Procmon에는 요청이 오지 않을 수 있다. 위 필터가 열기를 나중에 취소하면 Procmon에는 SUCCESS로 보일 수도 있다.

따라서 「사건 없음」이나 「SUCCESS」 하나만으로 결론을 내지 않는다. 같은 시각의 ERRORLOG 오류와 함께 본다.

  • SQL 서비스의 파일 열기 요청 ↓고도
  • FsDepends407000
  • UCPD385250.5
  • Procmon 예상 위치385200(미확인)
  • WdFilter328010
  • bfs150000
  • Wof40700
  • FileInfo40500
  • 파일 시스템 → D: → C:\myVHDX.vhdx

D:의 필터 6개 이름은 2026-10-05 20:52 관리자 읽기와 2026-10-06 15:50 01a 출력에서 같다. 고도는 15:50 01a 출력을 옮긴 도우미 기록의 값이다. 385200은 Microsoft 할당 목록의 Procmon11.sys 값이다. 이번 Procmon 4.11의 실제 드라이버 이름과 고도는 미확인이다. 이번 실행의 02b 두 번 모두 새 필터를 확인하지 못했다.

한 번의 시작이 보여 줄 것

  • 두 DATA 파일 열기(CreateFile)의 결과 코드와 경로
  • 시각, 프로세스 ID, 스레드 ID
  • 요청한 계정(User 열)
  • 요청 세부: Desired Access, ShareMode, Disposition, Options, Impersonating(값이 있을 때)
  • 가능하면 호출 스택(Stack). 스택에 드라이버가 보인다는 사실 하나로 그 드라이버를 원인으로 지목하지 않는다.

기록은 원시 PML과 읽기용 CSV로 함께 저장한다.

왜 딱 한 번인가

이 실행은 증거 수집이다. 시행착오로 시작을 반복하는 일이 아니다.

  1. 성공 기준은 「SQL 서비스 시작 성공」이 아니다. 기준은 「관측 가능한 1회 시도와 종료 정산」이다.
  2. 시작에는 부작용이 있다. 시작에 성공하면 기존 DB 복구, tempdb 재생성, ERRORLOG 회전이 생긴다. 가장 오래된 보관 로그가 사라질 수 있다.
  3. 재현에 성공해도 처음 실패의 원인을 확정하지 않는다. 일시 상태 가능성만 기록한다.
  4. 관측이 부족해도 다시 시작하지 않는다. 새 시도는 새 승인으로만 정한다.
  5. goal 규칙은 재시작·권한 변경·재마운트를 「구체 수정안과 사용자 승인」 뒤로 둔다. 남은 승인 시간을 재실행 권한으로 쓰지 않는다.

5관측 범위와 안전장치

경고
  • 시작 파일 03-start-once는 한 번만 실행한다.
  • 오류가 나오면 멈춘다. 같은 파일을 다시 실행하지 않는다.
  • UAC 외 보안 경고나 SmartScreen이 나오면 멈춘다. 경고를 우회하지 않는다.

관측 범위는 승인안 v5로 고정했다. 사용자가 자기 관리자 창에서 실행하고, 에이전트는 실행하지 않는다.

항목규칙비고
실행 주체사용자 본인이 연 관리자 PowerShell 5.1 창 1개(-NoProfile)리드와 도우미는 스크립트·SQL·Procmon을 실행하지 않는다.
관측 대상Process Name is sqlservr.exe → Include한계: 다른 프로세스와 System의 VHD I/O는 기록하지 않는다.
이벤트 종류File System, Process/Thread만 켠다. Registry·Network·Profiling은 끈다. Drop Filtered Events를 켠다.Path·Result 조건은 넣지 않는다. 성공과 실패를 함께 남겨 비교한다.
시작·중지 횟수시작 요청 1회. Running이 되면 중지 요청 1회.Stopped로 끝나면 중지 요청을 보내지 않는다.
재시도없음. 새 시도 폴더(attempt-02)도 없음.관측이 부족해도 같다.
시간 창T부터 30분. T+20분 뒤에는 시작 요청을 보내지 않는다.이번 값: T 15:48, 시작 마감 16:08, 종료 16:18 KST. 마지막 10분은 종료와 보존에 쓴다.
대기 한도상태 판독은 최대 120초. Running 확인 뒤 30초 안에 중지하는 것을 목표로 한다.자동 강제 장치는 없다. 사람이 시각을 보고 지킨다.
수집 한도캡처 5분, PML 500MB, C: 여유 1GB 미만 중 하나면 수집을 멈춘다.사람 관찰 기준이다.
전달 파일 13개승인안 코드블록과 줄 불일치 0, PS 5.1 파싱 오류 0. 실행 직전 전체 SHA256을 기계 비교하고 같을 때만 dot-source한다.다르면 HASH MISMATCH를 출력하고 실행하지 않는다.
Procmon 확인Microsoft 공식 링크의 ZIP만 쓴다. ZIP·EXE의 SHA256, FileVersion 4.11, 서명 Valid와 Microsoft 서명자를 확인한다.4.11이 아니거나 서명이 불명확하면 실행하지 않는다.
EULA사용자가 직접 읽고 판단한다. 자동 수락 플래그를 쓰지 않는다.이번 실행에서는 EULA 창이 뜨지 않았다. 6절을 본다.
선행 대조(01a)계정·SID·관리자 여부, 서비스 Stopped/Manual, 시작 계정, 실행 경로, VHDX Attached, D: 위치, C: 여유 2GB 이상하나라도 다르면 시작하지 않고 멈춘다.
종료·정산Procmon을 File → Exit로 정상 종료한다. 05로 잔여 상태를 읽고 06으로 transcript를 닫는다.남은 드라이버·설정은 보고만 한다. 강제로 지우지 않는다.

하지 않는 것

  • SQL 접속과 쿼리, DB 생성 단계
  • 서비스 계정과 시작 유형 변경
  • ACL·SACL·감사 정책 변경
  • Defender 예외 추가나 중지
  • VHD 재마운트
  • 레지스트리 수기 변경, 예약 작업 등록
  • 재부팅, 프로세스 강제 종료
  • EULA 자동 수락 플래그, Unblock-File, 권한 우회
  • Boot logging, 온라인 심볼 다운로드, 전역 보안 설정 변경

리드의 위험 진술 · 미확정

아래 두 가지는 Core 리드가 16:05 KST 중간 보고에서 밝힌 위험이다. 확인된 사실이 아니다.

  • 같은 패치가 자동으로 다시 시도될 수 있다. 그러면 승인 없이 SQL 서비스가 시작될 수 있다.
  • 인스턴스는 「새 바이너리 + 패치 실패」 상태일 가능성이 높다. 다음 일반 시작이 master 스크립트 업그레이드도 실행할 수 있다. 그러면 v5의 「관측 시작 1회」 전제가 바뀐다.

이번 실행은 원인 자료를 만들지 못했다. 아래 1번은 진행 중이고, 2–6번은 모두 계획이며 결과가 아니다.

  1. 진행 중 정리 경로를 끝낸다. 04d, Procmon File → Exit, 05 잔여 상태 읽기, 06 transcript 닫기, 관리자 창 닫기 순서다. 시간 창은 16:18 KST에 닫힌다.
  2. 계획 리드가 원시를 정산한다. 제출 파일별 SHA, SQL 시작 요청 0회와 최종 서비스 상태, 2회차 02b의 fltmc 표가 빠진 이유, 실제 Procmon 필터 이름, 잔여 드라이버·설정을 기록한다. 오늘 13시대 SQL 패치 실행의 원시도 정산 대상이다.
  3. 계획 리드가 다음 행동을 제안한다. 새 시간 창이 필요한지, 위 두 위험을 어떻게 다룰지가 이 제안에 들어간다. 사용자가 그 제안을 보고 결정한다.
  4. 계획 새 관측 실행을 할 경우, 승인안 v5의 해석 규칙은 다음과 같다. 실패한 CreateFile과 요청 계정·권한이 보이면 그 관측값으로 수정 후보를 좁힌다. 파일 권한이 원인임을 확인하기 전에는 ACL 추가나 서비스 계정 변경을 제안하지 않는다. SQL 서비스가 시작에 성공해도 DB 생성으로 넘어가지 않는다.
  5. 계획 수정은 새 승인안으로 한다. 권한 수정·재마운트 방식 변경 같은 외부 변경은 구체 명령, 실행자, 되돌리기, 시간 창, 사용자 승인을 갖춘 뒤에만 한다.
  6. 계획 SQL 서비스가 정상 시작되면 goal의 「DB 생성 실행」을 이어서 하고, 엔진 판정 PR로 간다. 그 PR은 branch feat/persistence-engine-judgment-20261006에서 연다. 각 실행 단계는 사용자 실행 승인을 따로 받는다.
