02 / OWNERSHIP

순간적인 맵 조회에서, 월드의 종료 처리로

기존 단일 월드 틱과 맵 작업 큐는 유지했습니다. 달라진 핵심은 종료 요청이 이동 중 상태 때문에 사라지지 않게 한 점입니다.

이전 · 95058e5

  1. IOCP에서 연결 종료GameSession이 closing을 설정
  2. 그 순간의 GetMap() 조회이동 중이면 null → 정리 경로 반환
  3. 목적지 작업의 closing 검사에 의존검사 뒤 종료가 끼어드는 창은 별도 정리 요청을 잃을 수 있음

시작은 listener를 먼저 열고 world를 구성했습니다. 종료는 world.Stop에 집중돼 accept·연결·월드 정리 완료의 한 소유자가 없었습니다.

이후 · 956a391

  1. IOCP에서 closing 설정 + 종료 요청 제출세션은 생성 당시 월드에 결합
  2. 월드 틱에서 종료 큐 처리맵 순회 전·후, 모든 맵의 owner reference로 등록 확인
  3. 엔티티 제거 → 파티 정리 → 상태 초기화Party → Quest 순서 유지, 완료 barrier를 제어 흐름에 전달

호스트가 준비·수신·연결 해제·월드 정리·틱 종료 순서를 조정합니다. 틱에서 I/O나 자기 종료 완료를 기다리지 않습니다.

등록 불변식 · 세션당 전체 맵의 등록 수는 항상 0 또는 1. closing 순간 즉시 0을 약속하는 것이 아니라, 종료 요청을 처리한 틱 경계 뒤에는 0이고 지연된 작업이 되살리지 않게 합니다.
경계확정한 실행 순서실패를 다루는 방식
Startup월드 구성 완료·공개 → 틱 시작 → listener 시작시작 실패 시 만든 자원을 역순 정리
Shutdownaccept 차단·callback 정리 → 연결 해제 → cleanup barrier → 실제 틱 종료timeout이면 참조 유지. 완료 전에 새 월드 시작을 허용하지 않음
Accept fault회복 가능한 오류는 취소 가능한 재시도. terminal fault는 Completion으로 관찰모든 루프가 끝난 fault는 안전정리 후 보고. 살아 있는 callback의 timeout과 구분
지연 입력이동·공격·스킬·포탈·파티 요청 실행 시 생존/소유 재확인이미 시작한 동기 판정과 종료 후 대기 작업을 구분
03 / DECISIONS

작은 책임 경계부터 바꿨습니다

이 설계를 선택한 이유

  • closing 검사만 추가하기: 마지막 검사 이후의 창과 정리 책임 분산이 남습니다.
  • 전이 전체를 lock으로 묶기: IOCP와 틱을 서로 기다리게 만들 수 있습니다.
  • 모든 세션을 새 FSM으로 재작성하기: handler·테스트까지 한꺼번에 넓어집니다.
  • 선택한 범위: 얇은 ServerHost, 월드 종료 큐, 기존 작업 실행 시 가드. 소스 8파일과 독립 테스트 6파일로 책임 경계를 정리했습니다.

바꾸지 않은 게임 계약

  • 패킷 ID·필드·버전
  • 최초 Town 진입
  • handshake → 직업 선택
  • 이동 중 입력 drop
  • 이동 시 ID·HP·Stats 유지
  • 현행 cooldown 초기화
  • Enter/Transition → HP → roster
  • 파티·퀘스트 정책과 실행 순서

Shared·Unity·DB는 이번 서버 구현 범위에 포함하지 않았습니다. 맵 이동 cooldown이나 저장 정책은 구조 정리 중 조용히 바꾸지 않습니다.

공용 attempt를 선택한 이유

Unity 전용 socket adapter를 별도로 두면 취소와 자원 경합 처리가 두 구현으로 갈라집니다. ClientNet의 attempt를 재사용하고 Unity의 상태 선택만 일반 C# owner에 두었습니다. 그 비용으로 공용 DLL 교체와 기존 headless caller까지 검증해야 합니다.

OS 연결 성공과 socket 인수를 분리해, 성공 callback이 main queue에서 대기하는 동안 취소되어도 새 세션이 socket을 가져가지 못하게 했습니다. 기존 Connector.Connect는 호환 wrapper로 남았습니다.

보존한 계약과 다음 경계

  • handshake → 직업 선택

  • handshake 전 intent drop
  • 기존 ping 간격
  • ClassLoadout·PlayerPrefs
  • 프로토콜·Shared 정의

자동 재접속이나 새 timeout 정책은 추가하지 않았습니다. 이미 시작된 scene load, 씬 준비/전환 epoch, BGM·StageClear 수명은 M1c에서 다룹니다.

  1. 정적 pending spawn과 Awake첫 진입과 맵 전환에서 초기값 적용 경로 분리
  2. sceneLoaded 구독자가 roster drainplayer·registry·최초 HP 준비와 별도
  3. handshake 뒤 입력·지연 송신같은 연결의 이전 맵과 새 맵 구분 부족

현재 · 서로 다른 수명을 각 owner가 관리

  1. MapEntryCoordinator · 세션의 entry epoch목적 scene identity · spawn · HP · Ready
  2. SceneLoadQueue + SceneTransition앱의 active 물리 load 1개 + 최신 pending 1개

A 물리 load 중 B→C: A의 실제 작업 완료를 기다리고 B를 버린 뒤 C만 시작합니다. 이미 시작한 Unity load의 rollback을 보장하지 않으며, 취소된 요청의 domain 적용을 차단합니다.

이 설계를 선택한 이유

연결 generation, map entry epoch, 물리 load request ID는 수명이 다릅니다. 각 owner와 좁은 callback으로 구분해 bool 하나나 sceneLoaded 구독 순서에 준비를 맡기지 않았습니다. 범용 DI·이벤트 framework는 추가하지 않았습니다.

Unity scene identity는 GetRawData()의 ulong 전체를 보존합니다. 하위 비트는 같고 상위 비트가 다른 identity로 회귀를 검증했습니다.
