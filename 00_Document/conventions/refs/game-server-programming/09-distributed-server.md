# [GSP-09] 분산 서버 구조 (Distributed Server Architecture)
> 단일 서버의 한계를 극복하기 위한 수평·기능적 분산 설계 — 확장성·가용성·응집도 3축으로 판단

## 언제 참조하나 (트리거)
- 동시접속자 증가로 단일 GameMap/GameSession 서버가 병목이 될 때.
- 맵 서버 레지스트리 + 핸드오프(맵 간 이동) 구조를 설계하거나 확장할 때.
- 고가용성(서버 장애 시 플레이어 재연결) 전략을 논의할 때.
- DB 샤딩·파티셔닝, 로드밸런서 앞단 구조를 도입하려 할 때.

---

## 핵심 내용

### 9.1 수직 확장 vs 수평 확장
- **스케일 업(수직 확장)**: 단일 머신의 CPU·RAM·스토리지를 업그레이드. 비용 체증, 물리적 상한 존재.
- **스케일 아웃(수평 확장)**: 동일 역할의 머신을 여러 대로 늘려 처리량 분산. MMORPG 서버의 기본 확장 전략.

### 9.2 분산 없는 단일 서버의 장애 패턴
동시접속자 급증 시 순서대로 나타나는 증상:
1. 응답 지연 — 패킷 처리 큐 포화
2. 접속 지연 — TCP 핸드셰이크 큐 포화
3. 연결 끊김 — keepalive 타임아웃, TCP 재전송 타임아웃
4. 접속 실패 — listen backlog 초과

### 9.3 고전적 분산: 채널 서버 방식
- (서버 + DB) 세트를 채널 단위로 나열하는 가장 단순한 수평 분산.
- 플레이어는 채널을 선택해 접속. 채널 간 상호작용 없음.
- 구현 단순, 운영 단순. 단, 채널 간 파티/경매장 등 교차 기능 불가.

### 9.4 논리적 단일 서버 분산
- 플레이어에게는 "단일 세계"처럼 보이지만 내부적으로 여러 서버가 협력.
- 분산 설계 절차: ① 병목 지점 프로파일링 → ② 해당 지점만 선택적으로 분산.
- 단일 서버 기준 처리량 상한 예: 네트워크 장비 1 GB/s, 방화벽 500 MB/s, SSD 100 MB/s 등 레이어별로 상한이 다름.

### 9.5 데이터 분산 vs 기능적 분산
| 구분 | 데이터 분산 (수평) | 기능적 분산 (수직) |
|---|---|---|
| 원리 | 같은 역할의 서버 여러 대가 데이터를 나눠 가짐 | 기능(경매장·채팅·NPC 등)별로 서버를 분리 |
| 예 | 월드를 지역별 맵 서버로 분할 | 경매장 서버, 채팅 서버, NPC AI 서버 |
| 확장성 | 데이터 증가에 선형 대응 | 특정 기능 부하에 독립 대응 |
| 단점 | 크로스-서버 데이터 접근 발생 | 서버 간 의존 관계 복잡도 증가 |

### 9.6 로직 처리의 세 가지 분산 방식
"서로 다른 머신 간에 분산 처리를 할 일이 없게 하는 것이 가장 좋다"는 전제 아래, 필요 시 아래 중 택일.

#### 9.6.1 동기 분산 처리
- 서버 A가 서버 B에 연산을 요청하고, **결과가 올 때까지 블로킹**.
- 데이터 무결성을 위해 관련 데이터를 잠금(lock).
- 싱글스레드 틱 서버에서는 틱 자체가 순서를 보장하므로 추가 lock 불필요할 수 있음.
- 단점: 대기 중 틱이 막힘(헌법 §5 위반 위험), 암달의 법칙으로 분산 효율 상한 존재.

#### 9.6.2 비동기 분산 처리 (액터 모델 / MPI)
- 서버 A가 서버 B에 명령을 송신하고 **결과를 기다리지 않음**. 서버 B가 완료 후 역통보.
- MPI(Message Passing Interface), 액터 모델(actor model)과 동일한 개념.
- 흐름 예: A→B "몬스터에 데미지 줬음" → B→A "아이템 드랍했음".
- 장점: 틱 루프 비블로킹. 단점: 일시적 불일치 상태, 에러 처리 복잡.

#### 9.6.3 데이터 복제 기반 로컬 처리
- 각 서버가 타 서버 담당 데이터의 **복제본**을 로컬에 보유.
- 데이터 변경 시 변경분을 상대 서버에 통지 → 복제본 갱신.
- 장점: 원격 요청 없이 로컬 데이터로 연산 가능 → 레이턴시 최소.
- 단점: 복제 지연 기간 동안 두 서버의 뷰가 불일치(eventual consistency).

### 9.7 데이터 응집도 (Coherency / Locality)
- **응집도**: 특정 영역 안에 얼마나 많은 관련 데이터가 뭉쳐 있는지.
- 설계 원칙: **응집도가 높은 데이터끼리는 같은 서버에, 응집도가 낮은 데이터 사이에만 분산 경계를 둠.**
- 지리적 구분(MMORPG 맵/존), 플레이어 레벨 구분(매치메이킹) 등이 자연스러운 응집 경계.
- 응집 경계를 잘 나누면 크로스-서버 통신 자체가 드물어져 세 분산 방식의 단점이 희석됨.

### 9.8 기능적 분산 처리
- 데이터 단위 수평 분산이 불가능한 기능(원자성 필수, 전 데이터 집계 필요)은 **전담 서버로 분리**.
- 대표 예: 경매장(전체 입찰 데이터를 단일 서버에서 원자적으로 처리), 랭킹 서버, 채팅 서버.
- 기능 서버 장애 시 해당 기능만 중단, 나머지 게임플레이는 지속.

### 9.9 분산 처리를 엄선해야 하는 이유
- 분산 처리는 **네트워크 장비 부하** 증가 → 과도하면 인프라가 병목.
- **디버깅 난이도** 급증: 원격 디버거, 통합 로그, APM 도구가 있어도 단일 프로세스보다 훨씬 어려움.
- **성능 역전 가능성**: 잘못 분산하면 OS 컨텍스트 스위칭·소켓 오버헤드로 단일 서버보다 느려질 수 있음.
- **클라우드 불안정성**: 인스턴스 간 통신은 보통 빠르지만 드물게 고레이턴시·단절 발생 → 분산이 많을수록 장애 전파 범위 확대.
- 결론: **필수적인 이유가 없으면 분산 X. 측정(프로파일링) 후 병목만 분산.**

### 9.10 분산 처리 전략 요약
1. 성능 분석으로 병목 지점 파악
2. 데이터 응집도 검토 → 응집도 낮은 경계만 분산 후보
3. 분산 방식 선택: 동기(무결성 우선) / 비동기(처리량 우선) / 데이터 복제(레이턴시 우선)
4. 불필요한 분산은 피함

### 9.11 분산의 부가 장점: 장애 격리
- 수평 분산 5대 중 1대 장애 → **전체의 20%만 영향**, 나머지 80% 정상.
- 기능 분산: NPC 서버 다운 → NPC만 사라지고 전투·채팅 지속, 서버 복구 후 NPC 재생성.
- 장애 격리(fault isolation)가 분산의 확장성 못지않은 실용적 이점.

### 9.12 고가용성 (High Availability, HA)
- 정의: 하드웨어 고장·소프트웨어 업데이트 상황에서도 **사용자가 서비스를 계속 이용 가능**한 것.
- 비유: 히드라 — 머리 하나가 잘려도 나머지 머리가 작동하고 새 머리가 재생.
- 구현 패턴 (일반 지식 보완):
  - **핫 스탠바이**: 대기 서버가 실시간으로 상태 동기화, 장애 시 즉시 전환(failover).
  - **콜드 스탠바이**: 대기 서버는 평시 꺼진 상태, 장애 감지 후 기동(전환 시간 있음).
  - **로드밸런서 + 헬스체크**: 클라이언트 앞단 LB가 서버 heartbeat를 주기적으로 체크, 죽은 서버를 풀에서 제거.
  - **상태 비저장 서버**: 가능하면 서버를 stateless로 설계해 교체 용이성 확보.

### 9.13 데이터베이스의 분산
- 서버 분산만으로는 불충분 — DB도 분산해야 진정한 HA 달성.
- **수평 파티셔닝(샤딩)**: 레코드를 여러 DB 서버에 나눠 저장 (예: 플레이어 ID % N).
- **수직 파티셔닝**: 테이블 또는 컬럼을 다른 DB 서버에 분리 (예: 로그 테이블 전용 서버).
- 세부 구현은 10장에서 다룸.

## 우리 프로젝트 적용

### 현재 상태: 채널 방식 + 맵 Actor 분리 (부분 구현)
- **이미 사용 중** — `GameMap`이 맵별 단일 스레드 Actor로 동작하는 것은 §9.5 기능적 분산의 맹아.
  - 각 맵이 독립 틱을 가지고 서로 간섭 없음 → 맵 간 응집도 낮음, 자연스러운 분산 경계.
  - `02_Server/GameServer/` 내 `TickScheduler` + `GameMap` 구조.
- **이미 사용 중** — 맵 서버 레지스트리를 통한 핸드오프 (`portal migration`)는 §9.4 논리적 단일 서버 분산의 클라 투명성을 구현.
  - `GameSession.cs` 포털 처리, `GameMap`의 플레이어 퇴장/입장 시퀀스.

### 채택 후보
- **비동기 분산 처리 (§9.6.2)**: 현재 맵 간 통신이 필요할 때(파티, 귓속말 등) — 메시지 패싱으로 구현 예정.
  - Dawnholder의 `ConcurrentQueue<Action>` 기반 Actor 모델(`GameMap`/`PartyRegistry`/`QuestRegistry`의 EnqueueJob+Tick)이 이 패턴과 정확히 일치. 맵 간 통신 = 큐에 메시지 투입.
- **고가용성 (§9.12)**: 현재 단일 서버 프로세스. M5 이후 로드밸런서 + 멀티 인스턴스 전환 시 참조.
- **DB 샤딩 (§9.13)**: M5 DB 영속화 설계 시 플레이어 ID 기반 수평 파티셔닝 후보. 당장은 LocalDB 단일 인스턴스.

### 현재 무관
- **동기 분산 처리 (§9.6.1)**: 현재 맵 간 동기 호출 없음. 도입 시 헌법 §5(틱 블로킹 금지) 위반 위험 — 주의.
- **데이터 복제 기반 처리 (§9.6.3)**: eventual consistency 허용 기능(NPC 상태 캐시 등) 생기면 고려.

## 함정 / 과용 경계
- **조기 분산 금지**: §9.9의 핵심 — 프로파일링 없이 "확장성"을 위해 분산하면 오히려 성능 저하. 현재 Dawnholder는 단일 프로세스로 충분.
- **동기 분산 + 틱 루프 조합 위험**: 동기 대기가 틱 안에 들어오면 헌법 §5 직접 위반. 반드시 비동기 또는 사전 데이터 복제로 대체.
- **응집도 무시한 분산**: 전투 연산처럼 응집도가 극도로 높은 데이터를 억지로 쪼개면 크로스-서버 트래픽이 단일 처리보다 느려짐.
- **채널 방식의 함정**: 채널 서버는 구현이 쉽지만 "단일 세계" 경험(파티·경매장·랭킹)이 불가능. Dawnholder는 논리적 단일 서버를 목표로 하므로 단순 채널 분리는 지양.
- **HA를 코드 복잡도로 구현하려는 충동**: 먼저 서버를 stateless에 가깝게 설계하고(세션 상태 외부화), 인프라(LB + 헬스체크)가 HA를 처리하게 하는 편이 코드 단순.
