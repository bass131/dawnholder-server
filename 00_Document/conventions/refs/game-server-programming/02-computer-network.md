# [CH02] 컴퓨터 네트워크 (Computer Networks)
> 게임 서버 개발자가 알아야 할 네트워크 기초 — OSI 모델·식별자·품질 지표·UDP vs TCP·메시지 형식·NAT

## 언제 참조하나 (트리거)
- TCP Raw 소켓 코드(ServerCore, RecvBuffer/SendBuffer)의 스트림 경계 처리 문제를 분석할 때
- UDP vs TCP 선택 근거, 혹은 패킷 유실이 게임플레이에 미치는 영향을 논의할 때
- PDL 바이너리 메시지 포맷 설계 시 텍스트 vs 바이너리 trade-off를 검토할 때
- NAT 환경에서 클라이언트 연결 문제(공인 IP 부족, 포트 매핑 이슈)를 진단할 때

## 핵심 내용

### 2.1 네트워크 기기와 OSI 모델

- 네트워크는 **단말기(터미널)**와 **네트워크 장비(스위치/라우터)** 두 부분으로 구성된다.
- 단말기는 **클라이언트**(사람이 직접 쓰는 PC·스마트폰)와 **서버**(클라이언트 요청을 처리하는 무인 컴퓨터)로 나뉜다.
- **OSI 7계층**: 물리(1) → 데이터링크(2) → 네트워크(3) → 전송(4) → 세션(5) → 표현(6) → 응용(7).
  - **계층 2(데이터링크)**: LAN 내부 통신. 데이터를 **프레임(frame)** 단위로 교환. 프레임 = 헤더(송수신 주소) + 페이로드(실제 데이터). 우편 봉투 비유.
  - **계층 3(네트워크)**: WAN 간 라우팅. 우편 번호처럼 계층적 주소(IP)로 전 세계 목적지까지 패킷을 전달. 계층 2만으로는 동네 수준, 계층 3이 있어야 국가·대륙 간 이동 가능.
  - **계층 4(전송)**: 데이터가 수신 측에 신뢰성 있게 도달하도록 보장. TCP가 여기에 해당.
  - **계층 5~7**: 게임 개발자가 직접 프로토콜을 정의하는 영역 (HTTP, SSL, MPEG, 자체 PDL 등).

### 2.2 인터넷

- OSI 3계층(IP) 규약을 따르는 스위치·라우터들이 전 세계에서 연결되어 형성된 거대한 망이 인터넷이다.
- 이더넷 케이블·광섬유·무선 등 물리 매체 종류에 상관없이 IP를 공통 언어로 삼아 통신이 가능하다.

### 2.3 네트워크 데이터: 스트림 vs 메시지

개발자가 실제로 다루는 데이터 단위는 프레임·패킷이 아니라 **스트림**과 **메시지** 두 가지다.

| 구분 | 스트림(Stream) | 메시지(Message) |
|------|--------------|----------------|
| 경계 | 없음 — 연결이 닫힐 때까지 연속된 바이트 흐름 | 있음 — 메시지 자체가 시작·끝을 내포 |
| 보장 | 순서 보장, 단 읽는 단위가 쓴 단위와 다를 수 있음 | 보낸 단위(aaa, bbb, ccc)와 받는 단위가 동일 |
| 대응 프로토콜 | TCP | UDP |
| 주의 | 수신 측이 직접 경계를 재조립해야 함 | 없음 |

- **스트림**: 파일 읽기처럼 100바이트를 요청해도 30바이트만 올 수 있다. TCP 수신 시 RecvBuffer가 완전한 패킷을 조립할 때까지 기다려야 하는 이유가 바로 이것.
- **메시지**: 게임에서는 특정 순간 발생하는 이벤트(총 발사, 이동 입력 등)를 전송하는 경우가 많으므로 메시지 방식이 더 자연스럽다.

### 2.4 네트워크 식별자

- **IP 주소**: 단말기당 여러 개 가능 (유선 + 무선 = 최소 2개). `ipconfig`로 확인.
- **포트 번호**: 같은 단말기에서 복수의 프로세스가 통신할 때 프로세스를 구별하는 번호.
- **엔드포인트(endpoint)**: `(IP 주소 또는 호스트명, 포트)` 쌍. 프로세스 간 통신의 최소 식별 단위.
- IPv6 링크 로컬 주소 + IPv4 주소 + 서브넷 마스크 + 기본 게이트웨이가 함께 표시된다.

### 2.5 네트워크 품질과 특성

#### 품질을 저해하는 원인
- 스위치·라우터도 컴퓨터이므로 처리 한계가 있다.
- 트래픽이 처리 용량을 초과하면 두 가지 현상이 발생: **(1) 패킷 드롭(packet loss)** — 버퍼를 넘으면 데이터를 버림. **(2) 버퍼링** — 처리를 못 한 데이터가 메모리에 쌓임 → 레이턴시 급증.

#### 전송 속도(throughput)와 레이턴시(latency)
- **전송 속도**: 초당 전송 가능한 최대 데이터량. 단위 bps 또는 B/s. 광섬유 최대 54 Gbps 이상, 현대 일반망 1~10 Gbps, 1990년대 모뎀 2 Kbps.
- **레이턴시**: 최소 데이터를 양쪽 단말기 간에 전송하는 데 걸리는 시간(ms). 전송 선로 길이·라우터 수·라우터 처리 속도에 영향받는다.
- 두 지표는 **독립적**이다 — 대역폭이 넓어도 레이턴시가 높을 수 있고, 반대도 마찬가지.

#### 네트워크 품질 기준 3가지
1. **스루풋(throughput)**: 단위 시간당 총 전송 데이터량 — 높을수록 좋다.
2. **패킷 유실률(packet loss rate)**: 전송 중 버려지는 패킷 비율 — 낮을수록 좋다. 선로 품질·경로 상 라우터 수·라우터 성능이 영향.
3. **레이턴시(latency)**: 목적지 도달까지 걸리는 시간 — 낮을수록 좋다. 선로 길이·라우터 수·처리 속도가 영향.

#### 무선 네트워크 품질
- WiFi 신호 약하면 단순 패킷 유실뿐 아니라 레이턴시가 수백 ms까지 치솟는 **불균형 현상**이 나타난다.
- 신호 약화 → 재전송 시도 반복 → 지연 폭발. 게임에서 무선 연결 유저의 spike를 따로 고려해야 하는 이유.

### 2.6 데이터 보내기와 받기

#### UDP (User Datagram Protocol)
- 사용자가 정의한 **데이터그램(datagram)** 단위로 전송하는 프로토콜.
- 송신 측: 로컬 포트 할당 필요. 수신 측: 수신 대기 포트 할당 필요. 송신 측은 수신 측의 IP + 포트를 알아야 한다.
- 연결 수립 없이 바로 전송 가능 — 브로드캐스트도 지원.
- **신뢰성 보장 없음** — 순서, 전달 여부 모두 미보장.

#### TCP (Transmission Control Protocol)
- **신뢰성 보장**: 송신 측 데이터가 수신 측에 동일하게 도착함을 프로토콜이 보장.
- **연결 기반**: 데이터 교환 전 반드시 연결(3-way handshake)을 수립해야 한다.
- **1:1 전용**: 브로드캐스트 불가.
- **스트림 포맷**: 데이터를 묶거나 쪼개어 전송할 수 있어 수신 측이 경계를 재조립해야 한다.
- OSI 계층 4에 위치. 대부분 인터넷 애플리케이션이 TCP를 채택하는 이유가 이 신뢰성 보장.

### 2.7 패킷 유실 시 UDP와 TCP의 차이

| 구분 | UDP | TCP |
|------|-----|-----|
| 유실 단위 | 데이터그램 전체 | 개별 IP 패킷 |
| 크기 영향 | 데이터그램이 클수록 여러 IP 패킷으로 단편화 → 유실 확률 증가. 10,000바이트 = ~8개 패킷, 1개라도 유실 시 전체 데이터그램 손실 | 단편화 없이 TCP 세그먼트 단위 재전송 |
| 대응 메커니즘 | 없음 (애플리케이션이 직접 처리) | **ACK(acknowledgment)** + 재전송. 수신 ACK가 오지 않으면 해당 세그먼트를 재전송하고, 수신 측은 빠진 조각이 올 때까지 상위 레이어에 데이터를 올리지 않음 |
| 게임 특성 | 위치·방향처럼 유실되어도 다음 패킷으로 대체 가능한 고빈도 데이터에 적합 | 인벤토리 거래·채팅·인증처럼 반드시 도달해야 하는 데이터에 적합 |

- TCP 재전송은 **HOL(Head-of-Line) 블로킹**을 유발한다 — 하나가 막히면 그 뒤 데이터 전체가 지연된다. 실시간 게임에서 TCP가 단독으로 불충분할 수 있는 근본 이유.

### 2.8 주로 사용하는 메시지 형식

#### 텍스트 형식
- 사람이 읽을 수 있는 문자열 기반. 예시: `BuyItem\n Sword\n 1\n \x00`
- 수신 측이 특정 구분 문자(개행, `\0` 등)를 탐색하거나 파서를 써야 한다.
- 현대에는 자체 형식 대신 HTTP + JSON처럼 표준화된 텍스트 형식을 쓰는 추세.
- **장점**: 디버깅 쉬움. **단점**: 파싱 비용, 페이로드 크기 증가.

#### 바이너리 형식
- 바이트 배열로 인코딩. 예시: `0x01 | 0x0023 | 0x0001` — 각 필드의 오프셋·크기가 사전 정의됨.
- **장점**: 파싱 속도 빠름, 페이로드 크기 최소. **단점**: 직접 읽기 어려워 디버깅 툴 필요.
- 메타데이터(필드 타입·길이 정보)를 포함하면 하위 호환성에 유리하지만 트래픽이 늘어난다.
- 게임 서버에서 성능이 중요할 때 바이너리 형식이 표준.

### 2.9 네트워크 주소 변환 (NAT)

- **NAT(Network Address Translation)**: 패킷이 라우터를 통과할 때 송신자 또는 수신자 주소를 다른 주소로 바꾸는 과정.
- **NAT 라우터**: NAT를 수행하는 장비 — 가정/사무실의 인터넷 공유기가 대표적.
- **주 목적**: 공인 IP 주소 하나를 여러 단말기가 공유. 예: 외부 공인 IP `55.66.77.88`을 내부 PC 여러 대가 함께 사용.
- **동작 원리**: NAT 라우터가 내부 `(사설 IP, 포트)` ↔ 외부 `(공인 IP, 포트)` 매핑 테이블을 유지. 외부에서 들어오는 패킷을 내부 단말기로 전달.
- **게임 서버 함의**: 클라이언트는 NAT 뒤에 있으므로 서버가 클라이언트에게 먼저 연결을 시작할 수 없다(P2P 펀칭 문제). 권위 서버 아키텍처(클라이언트가 서버에 연결)는 이 문제를 우회한다.

## 함정 / 과용 경계

- **TCP = 완전 신뢰** 오해: TCP가 재전송·순서 보장을 하지만 HOL 블로킹으로 실시간 게임에서 체감 레이턴시가 폭발할 수 있다. "TCP 쓰면 OK"로 끝내지 말 것.
- **UDP = 빠름** 단순화: UDP 데이터그램이 커질수록 IP 단편화로 오히려 유실 확률이 급증한다. UDP 사용 시 MTU(~1400바이트) 이하로 단편화 방지가 필수.
- **스트림을 메시지처럼 읽기**: TCP 수신 시 `Read()` 한 번이 패킷 하나라고 가정하면 절반 패킷 버그가 생긴다. RecvBuffer가 항상 length 헤더로 경계를 확인해야 한다.
- **레이턴시 ≠ 전송 속도 혼용**: "인터넷이 느리다"가 대역폭 부족인지 레이턴시인지 구별하지 않으면 잘못된 곳을 최적화한다.
- **NAT 환경에서 서버→클라이언트 연결 시도**: 권위 서버 구조가 아니라 P2P를 도입할 때 NAT 펀칭이 필요해진다 — 게임 서버 수준에서는 복잡도 폭발.
