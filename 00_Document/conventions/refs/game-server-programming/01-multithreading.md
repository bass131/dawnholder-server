# [GSP-01] 멀티스레딩 기초 (Multithreading Fundamentals)

## 핵심 내용

### 1.1–1.2 프로세스와 스레드
- **프로세스**: 실행 중인 프로그램. 독립 메모리 공간(힙+스택+코드 영역)을 가지며, 서로 다른 프로세스는 상대방 메모리를 읽고 쓸 수 없다.
- **스레드**: 프로세스 안에서 명령어를 순차 실행하는 단위. 한 프로세스 안에 여러 개가 존재하며, **힙은 공유하지만 스택은 스레드마다 독립**이다. 지역 변수는 스레드별로 분리된다는 뜻이다.

### 1.3 멀티스레딩이 필요한 3가지 상황
1. **오래 걸리는 일 + 짧은 일을 동시에**: 예: 게임 로딩 중 진행 바 표시 — 메인 스레드가 블락되면 UI가 멈춘다.
2. **I/O 대기 중 다른 일 처리**: 디스크·DB 접근은 메모리 대비 수만 배 느리다. 대기 중 CPU가 놀지 않도록 멀티스레드 또는 비동기 프로그래밍이 필요하다.
3. **CPU 코어를 모두 활용**: 싱글스레드는 8코어 기계에서 전체 성능의 1/8만 쓴다. 2000년대 중반 이후 CPU 클록은 ~4 GHz에서 정체됐고, 대신 코어 수가 늘었다. 멀티코어 활용 없이는 성능 한계가 있다.

### 1.4–1.5 스레드 정체 & 경쟁 상태
- **스레드 정체(Thread Contention)**: 여러 스레드가 같은 자원을 두고 대기하는 현상. 물리적으로 CPU 하나를 여러 스레드가 나눠 쓸 때 컨텍스트 스위치 비용이 발생한다.
- **경쟁 상태(Data Race)**: 두 스레드가 보호 없이 같은 데이터를 읽고 쓸 때 결과를 예측할 수 없다. `x += y` 처럼 단순해 보이는 연산도 CPU 명령어 수준에서는 '읽기→계산→쓰기' 3단계라서 중간에 컨텍스트 스위치가 끼어들면 값이 깨진다.

### 1.6 임계 영역과 뮤텍스
- **임계 영역(Critical Section)**: 한 번에 하나의 스레드만 진입해야 하는 코드 구간.
- **뮤텍스(Mutex, Mutual Exclusion)**: 임계 영역 보호 도구. `lock → 작업 → unlock` 패턴. 이미 잠긴 뮤텍스에 lock을 요청하면 스레드는 블락(잠자기) 상태가 된다.
- 읽기도 반드시 잠금해야 한다 — "읽기만이라 괜찮겠지"는 대표적 실수(1.16.1).

### 1.7–1.8 교착 상태와 잠금 순서 규칙
- **교착 상태(Deadlock)**: 스레드 A가 B의 잠금을 기다리고, B는 A의 잠금을 기다리는 순환 대기. 관련 스레드들이 영원히 멈춘다.
- **잠금 순서 규칙**: 여러 뮤텍스를 쓸 때 항상 **정해진 순서**로만 잠근다. 예: `lock(A) → lock(B) → unlock(B) → unlock(A)`. 어디서든 역순(B → A)이 없으면 교착 상태는 발생하지 않는다. 실무에서는 뮤텍스 개수를 최소화해야 이 규칙을 지키기 쉽다.

### 1.9 병렬성과 시리얼 병목
- **병렬성(Parallelism)**: 여러 CPU가 각 스레드의 연산을 동시에 실행해 처리량을 높이는 것.
- **시리얼 병목(Serial Bottleneck)**: 임계 영역이 너무 넓으면, 멀티스레드로 설계했어도 실질적으로 스레드가 한 줄로 줄 서서 순차 처리된다. 잠금 범위를 줄여야 진짜 병렬성이 나온다.

### 1.10–1.11 싱글스레드 vs 멀티스레드 게임 서버
- **싱글스레드 멀티프로세스**: CPU 개수만큼 서버 프로세스를 실행한다. 스레드 동기화 복잡도를 피할 수 있다. 단, MMO처럼 프로세스당 맵 데이터 로딩 부담이 크거나 방끼리 공유 메모리가 필요한 경우엔 적합하지 않다.
- **멀티스레드 서버가 필요한 5가지 상황**: ① 맵 데이터가 너무 커서 프로세스 복제가 부담 ② 단일 프로세스에서 멀티코어 연산력 필요 ③ 코루틴·비동기 없이 I/O 대기 발생 ④ 기기당 1인스턴스 제약 ⑤ 서로 다른 방이 공유 메모리에 접근해야 할 때.
- **방(Room=Map) 단위 잠금**: 멀티스레드 게임 서버에서 자연스러운 잠금 범위. 맵 하나가 하나의 스레드(Actor)에서 돌고, 맵 내부는 lock이 없다.

### 1.12 스레드 풀링
- 클라이언트마다 전용 스레드를 붙이면 5,000명 접속 시 스레드 스택만 수 GB. 컨텍스트 스위치도 초당 수십만 번으로 폭발한다.
- **스레드 풀(Thread Pool)**: 코어 수에 비례한 고정 스레드 집합이 작업 큐에서 일감을 꺼내 처리. 클라이언트 수가 늘어도 스레드 수는 일정하다.

### 1.13–1.14 이벤트와 세마포어
- **이벤트(Event)**: 잠자는 스레드를 깨우는 신호 도구. Reset(0)/Set(1) 두 상태. `WaitForSingleObject` / `SetEvent` 패턴. .NET에서는 `ManualResetEventSlim`, `AutoResetEvent`.
- **세마포어(Semaphore)**: 동시 접근 허용 스레드 수를 N개로 제한. 카운터가 0이 되면 대기. 카운터 최댓값을 1로 설정하면 뮤텍스와 동일. 생산자-소비자 패턴에서 큐 항목 수를 카운터로 관리하는 용도로도 쓴다.

### 1.15 원자 조작
- **원자 조작(Atomic Operation)**: 뮤텍스 없이 하드웨어 명령어 단위에서 원자성을 보장. 32/64비트 정수 수준 연산에 적합.
- 주요 종류: 원자적 더하기(fetch-and-add), 값 맞바꾸기(swap), 조건부 맞바꾸기(compare-and-swap, CAS).
- 2~3개를 초과하는 변수의 일관성을 잠금 없이 유지하는 것은 극히 어렵고, 논리적 증명 없이는 버그 위험이 있다.
- .NET에서는 `Interlocked.Increment`, `Interlocked.CompareExchange` 등.

### 1.16 흔한 실수 7가지
1. **읽기에 잠금 안 하기** — 쓰기만 잠그고 읽기는 잠그지 않으면 간헐적 비정상 값 발생. 100만 줄 프로젝트에서 원인 추적이 극도로 어렵다.
2. **잠금 순서 꼬임** — 코드베이스가 커지면 `func1: A→B`, `func2: B→A` 역순이 슬금슬금 생긴다. 뮤텍스 개수를 최소화하는 것이 최선.
3. **너무 좁은 잠금 범위** — 변수마다 별도 뮤텍스를 두면 잠금/해제 오버헤드가 실제 데이터 접근보다 비싸진다. 균형을 찾아야 한다.
4. **디바이스 타임이 섞인 잠금** — `printf`·`cout` 같은 콘솔 출력도 OS 수준에서 무겁다. 잠금 구간 안에서 I/O를 하면 다른 스레드가 전부 대기한다. "CPU 사용률은 낮은데 처리량이 낮은" 현상의 1순위 원인.
5. **잠금의 전염성** — 보호된 컨테이너에서 포인터·참조를 꺼내 잠금 해제 후 사용하면, 그 포인터가 가리키는 메모리는 여전히 공유 자원이다.
6. **잠금된 뮤텍스 삭제** — 아직 lock 상태인 뮤텍스를 가진 객체를 `delete`하면 메모리 손상·교착 상태. 소멸자에서 잠금 여부 검사 방어 코드가 필요하다.
7. **일관성 규칙 깨기** — 연관된 변수(예: 리스트 + 카운터)를 서로 다른 뮤텍스로 보호하면, 두 작업 사이에 다른 스레드가 끼어들어 논리적 일관성이 깨진다. 연관 데이터는 같은 뮤텍스로 묶어야 한다.

## 함정 / 과용 경계

- **뮤텍스 과분할(1.16.3)**: 성능 최적화 목적으로 멤버마다 별도 뮤텍스를 두면, 잠금 오버헤드가 오히려 늘고 잠금 순서 관리도 폭발적으로 복잡해진다. "방 하나 = 뮤텍스 하나" 수준을 기준점으로 삼아라.
- **잠금 구간 안 I/O(1.16.4)**: `Console.WriteLine`, 파일 쓰기, DB 동기 쿼리를 lock 구간 안에 절대 두지 않는다. 틱 루프 안에서는 헌법 원칙 #5와 동일한 이유로 금지.
- **원자 조작 과신**: `Interlocked`는 단일 변수 1개에만 원자성을 보장한다. 두 변수 사이의 일관성이 필요하면 반드시 뮤텍스를 써야 한다(1.17 경고).
- **싱글스레드 서버가 항상 더 단순한 건 아님**: 프로세스 간 공유 메모리가 필요해지는 순간(예: 맵 간 채팅 브로드캐스트) 프로세스 IPC 비용이 멀티스레드 lock 비용보다 비싸질 수 있다.
- **"지금 작동한다"는 잠금 없는 코드 믿지 않기**: 비원자 연산을 잠금 없이 쓰면 낮은 확률로 버그가 터진다. CI 통과 ≠ 안전.
