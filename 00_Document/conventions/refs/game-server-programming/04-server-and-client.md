# [GSP-04] 게임 서버와 클라이언트 (Game Server and Client)
> 패키지→온라인 게임 서버의 역할 진화, 클라-서버 상호작용 4가지, 서버 품질 4축(안정성/확장성/성능/관리편의성)을 한 장에 정리.

---

## 언제 참조하나 (트리거)
- 서버가 "무엇을 책임져야 하나"를 결정할 때 (데미지 계산 위치, 루팅 굴림 위치 등).
- 확장성(Scale-out/up) 또는 성능 목표를 정할 때.
- 클라-서버 연결·요청-응답·푸시·해제 흐름을 설계하거나 리뷰할 때.
- 서버 안정성(crash, malfuction) 방어 코드를 작성하기 전 체크리스트로.

---

## 핵심 내용

### 4.1 패키지 게임에서의 서버 (§0229 — 무료 접근)
- 1990년대 중반: 패키지 게임(CD-ROM 설치형)이 주류. 네트워크는 56Kbps 모뎀, 연결 자체에 10~15초 소요.
- 서버 개념이 아예 없거나 LAN 대전 수준에 머묾.
- 이 시절 "서버"는 단순히 대전 조율(matchmaking)용 박스였음.

### 4.2 온라인 게임에서의 서버 (§0232 — 무료 접근)
- MUD(Multi User Dungeon)가 온라인 게임의 원형. 텍스트 UI, 모뎀 통신.
- 인터넷 보급 후 그래픽 MMORPG로 진화 → "게임 서버" 개념이 본격 분화.
- 여러 유저가 동시에 같은 공간을 공유하므로 서버가 **단일 진실 공급원**이 되어야 함.

### 4.3 서버의 역할 — 게임 루프 비교 (§0234 — 무료 접근)
- **싱글플레이어 게임 루프**: 입력 수신 → 게임 로직(60TPS 세션 업데이트, 데미지 계산) → 렌더링. 전부 클라 단독.
- **온라인 게임 루프**: 클라는 입력 전달 + 렌더링만. 로직은 서버가 소유.
- 서버의 3대 역할:
  1. **다수 유저 간 상호작용 중재** — 클라끼리 신뢰할 수 없으니 서버가 판정자.
  2. **클라 해킹으로 훼손 불가한 연산** — 데미지, HP, 골드 등은 서버 전용.
  3. **플레이어 상태 유지** — 접속 끊겨도 상태 보존, 재접속 시 복원.

### 4.4 클라이언트-서버 상호작용 4가지 (§0236 — 무료 접근)
1. **연결(Connection)**: 클라가 TCP 연결 요청 → 서버 수락/거부 → 인증 핸드셰이크.
   서버는 연결된 클라가 악의적 행위자일 수 있음을 전제해야 함.
2. **요청-응답(Request-Response)**: 클라가 메시지 전송 → 서버가 처리 후 결과 반환.
   RPC 패턴의 원형. 모든 요청은 검증 후 처리.
3. **능동 알림(Active Notification / Push)**: 서버가 이벤트 발생 시 클라에 먼저 전송.
   브로드캐스트(맵 전체), 멀티캐스트(시야 범위 내), 유니캐스트(개인 알림) 세 가지.
4. **연결 해제(Disconnection)**: 정상 로그아웃, 타임아웃, 비정상 종료.
   서버는 세 경우 모두 플레이어 상태를 안전하게 정리해야 함.

### 4.5 게임 서버가 하는 일 (§0238 — 무료 접근)
- 클라가 데미지를 자체 계산하면 자신의 공격력·상대 방어력·HP를 알기 때문에 조작 가능.
- **서버 중앙집중 판정**이 유일한 해법. 클라는 "내가 공격했다"는 의도만 전달.
- 서버는 결과를 계산하고 전체 관련 클라에 브로드캐스트.

### 4.6 서버 품질 4축 (§0242~0262 — 무료 접근)

#### 4.6.1 안정성(Stability) (§0243)
- 정의: 서버 프로세스가 24/7 중단 없이 올바르게 동작하는 능력.
- 두 종류의 불안정:
  - **비정상 종료(crash)**: 배열 인덱스 오버플로우 같은 코딩 버그.
  - **오작동(malfunction)**: 서버는 살아있지만 잘못된 결과 생성 (아이템 중복 지급, 무적 버그 등).
- 핵심: 결제한 아이템이 사라지거나 없는 골드가 생기면 서비스 사고 수준.

#### 4.6.2 확장성(Scalability) (§0248)
- 정의: 유저 수 증가 시에도 서비스 품질이 유지되는 능력.
- **Scale-up(수직 확장)**: 서버 장비 CPU·RAM 업그레이드. 소프트웨어 설계 비용 낮음, 하드웨어 비용 지수적 증가, 처리 상한이 장비 한계.
- **Scale-out(수평 확장)**: 서버 대수를 늘림. 하드웨어 비용 선형, 소프트웨어 분산 설계 비용 높음, 총 처리 용량 무제한에 가깝지만 장애 지점이 복수.
- 게임 서버는 동시접속 피크에 탄력 대응해야 하므로 Scale-out 지향이 일반적.

#### 4.6.3 성능(Performance) (§0251)
- 확장성과 구별: 확장성은 "많아져도 속도 유지", 성능은 "처음부터 빠른 처리 속도 자체".
- 게임 종류별 허용 지연 편차가 큼:
  - 턴제 보드게임: 1초 지연도 무방.
  - FPS·실시간 액션: 50ms 초과 시 판정 불공정 → 서버 로직이 1 tick(50ms) 안에 완결되어야 함.
- 성능 목표는 장르·플레이 패턴으로 역산해서 설정.

#### 4.6.4 관리 편의성(Manageability) (§0262)
- 게임 서버는 GUI 없는 콘솔 프로그램으로 백그라운드(데몬/서비스)로 동작.
- Windows: SCM 서비스 등록 → 시스템 부팅 시 자동 시작, 로그인 불필요.
- Linux/Unix: systemd/init 데몬. 로그 관리, 모니터링 연동이 핵심.
- 운영 중 원격 상태 조회, graceful shutdown, hot-reload 가능성이 관리 편의성의 실체.

### 4.7 플레이어 정보의 저장 (§0265 — 무료 접근)
- 싱글플레이어: 로컬 디스크 저장. 온라인: 서버 DB 중앙 저장.
- 데이터 손실은 "서비스 장애"와 동급 취급. 결제 재화 관련 손실은 법적 문제로도 이어짐.
- 악의적 수정(무적, 아이템 복사) 방지 → 서버만이 DB에 쓸 수 있어야 함.
- 저장 cadence 전략: 즉시 저장(중요 이벤트) + 주기 저장(30초 스냅샷) 혼합이 일반적.

### 4.8 서버 구동 환경 (§0270 — 무료 접근)
- 1990년대 중반: Solaris 유닉스 서버 주류.
- Windows Server: IOCP(I/O Completion Port, 1995~)가 수백~수천 클라 동시 처리를 가능하게 하면서 게임 서버 OS로 부상. 개발자가 서버·클라를 같은 Windows 머신에서 함께 실행 가능한 것도 장점.
- 2000년대 이후: Linux(epoll), FreeBSD(kqueue)가 IOCP에 준하는 성능 제공 → Windows Server vs Linux 양강 체제.
- 선택 기준: 팀의 숙련도 + 운영 툴 생태계 + 라이선스 비용.

### 4.9 서버 개발 지침 (§0278 — 무료 접근)
- **"가장 잘 다루는 것을 써라"**: 언어·OS·툴 모두 익숙한 것 우선.
- **안정성 > 코드량**: 신뢰할 수 없는 기술을 프로덕션에 실험하지 말 것.
- **점진적 학습, 보수적 배포**: R&D 환경에서 새 기술 탐구, 라이브 서비스는 검증된 기술로.
- 서버 운영은 "달리는 차 타이어 교체" 비유 — 중단 없이 변경해야 하므로 기반 기술 숙련이 필수.

## 함정 / 과용 경계
- **클라에서 "최종 결과" 표시를 위해 데미지 계산 복사**: 표시용 prediction이라도 공식은 `98_Shared/GameData/`에 단일화해야 함. 클라에서 독립 수식 쓰면 헌법 #1·#4 동시 위반.
- **확장성 과조기 설계**: Scale-out 아키텍처는 소프트웨어 복잡도를 크게 높임. 동시접속 수백 명 이하에서는 Scale-up이 압도적으로 단순하고 충분. 지금 Dawnholder는 단일 프로세스로 충분함.
- **안정성을 "배포 후 고치면 된다" 태도**: 게임 서버 데이터 손상은 사용자 신뢰 손실 + 결제 재화 문제로 이어짐. 범위 검증·소유권 확인은 처음부터.
- **관리 편의성 무시**: 콘솔에만 의존하면 원격 서버에서 장애 대응 불가. 최소한 structured logging + graceful shutdown은 초기부터.
- **성능 목표 없이 최적화**: 장르별 허용 지연 역산 없이 마이크로최적화 → 과조기 최적화. 20TPS(50ms/tick) 기준을 지키는 것이 먼저.
