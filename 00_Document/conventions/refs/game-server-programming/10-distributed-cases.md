# [10] 분산 서버 구조 사례 (Distributed Server Architecture Cases)
> 실제 게임 서비스 컴포넌트(인증/DB/매치메이킹/AI/로깅)별 분산 설계 패턴 + 장르별 아키텍처 참고

## 언제 참조하나 (트리거)
- 인증·DB·매치메이킹·AI·로깅 중 하나가 병목으로 확인되어 분리를 고려할 때
- "어디에 어떤 전용 서버를 두면 좋을지" 아키텍처 결정 전 체크리스트로
- MMORPG/FPS/RTS 장르별 서버 구조 레퍼런스가 필요할 때
- 로그 서버 분리나 통계 분석 파이프라인 설계 논의가 시작될 때

---

## 핵심 내용

### 10.1 로그온 처리의 분산 (무료 접근)

- **단일 서버 병목**: 인증 서버 1대 + DB 1대 구성에서 동시 접속이 늘면 CPU(복호화) + DB I/O 두 곳이 동시에 포화된다. 데이터 용량 자체(1KB × 60억 명 ≈ 6TB)는 문제가 아니라 **트랜잭션 처리량**이 한계.
- **수평 확장**: 인증 서버를 여러 대로 복제(데이터 단위 분산). 플레이어 데이터 간 상호의존이 없으므로 단순 복제가 가능.
- **클라이언트 라우팅 두 가지**:
  1. 클라이언트가 서버 주소 목록을 갖고 랜덤 선택.
  2. 목록 없이 단일 진입점 사용 → 앞단에 **로드 밸런서(하드웨어 L4/L7)** 삽입, 요청을 여러 인증 서버로 분산.
- 인증 서버와 DB는 **분리 확장**됨 — 두 계층 각각이 독립적으로 스케일아웃 대상.

### 10.2 데이터베이스의 수평 확장 (무료 접근)

- **샤딩(Sharding)**: DB를 여러 인스턴스로 분할, 플레이어를 나눠 저장. 플레이어끼리 직접 상호작용이 없다는 전제가 성립할 때 가장 단순.
- **샤드 키(파티션 키)**: 어느 샤드에 레코드가 있는지 결정하는 키. 이 예에서는 **사용자 ID 문자열** → XOR 조합 후 MOD N으로 샤드 인덱스 산출.
- **재해싱(Rehashing) 문제**: 샤드 수를 10 → 11로 늘리면 `MOD 10` → `MOD 11`으로 매핑이 바뀌어 기존 레코드가 엉뚱한 샤드를 가리킴. 샤드 추가 시 **기존 레코드 일부를 새 샤드로 이주**해야 하는 운영 비용 발생 — 해시 테이블 리해싱과 동일한 원리.
- 해시 함수 예제는 최대 255개 샤드 제한이 있음(반환 타입에 따른 제약) — 실제 서비스에서는 일관성 해싱(Consistent Hashing)이 표준 대안. (일반 지식 보완)
- 확장 공식: 트래픽 증가 시 인증 서버 수 + DB 샤드 수를 **비례적으로** 함께 늘린다.

### 10.3 매치메이킹의 분산 처리 (무료 접근)

- **유즈케이스 우선**: 10명 모아서 방 생성 → 대기 → 전투 시작. 분산 설계 전 반드시 실제 사용 시나리오를 정의한다.
- **단일 서버 병목**: 매치메이킹(대기열 계산)과 게임 룸(전투 월드 시뮬레이션)을 같은 서버에서 처리하면, 룸 수가 늘수록 전투 CPU + 매치메이킹 CPU가 동시에 포화.
- **분리 전략**:
  - **배틀 서버** 여러 대 — 개별 게임 룸의 전투 처리 전담.
  - **로비 서버** 1대 — 매치메이킹 + 대기열 + 방 배정 전담.
  - 같은 룸 안의 플레이어들은 빈번하게 상호작용 → 한 배틀 서버에 묶는 것이 데이터 응집도(cohesion) 측면에서 맞음.
- **지역(리전) 분산 추가 이점**: 배틀 서버를 US-West/US-East/KR/JP/Shanghai 등 AZ별로 배치하면 매칭 후 레이턴시를 줄일 수 있다.

### 10.4 몬스터 NPC 처리의 분산 처리 (무료 접근)

- **서버 몬스터 처리 3대 업무**: (1) 일정 주기(1/30 또는 1/10초) 위치·애니메이션 시뮬레이션, (2) 가시자 클라이언트에 결과 브로드캐스트, (3) 플레이어 공격 처리·보상 지급.
- **성능 압박 세 가지**: 몬스터 수 >> 플레이어 수, A* 경로탐색 CPU 비용, 기획자 요구로 인한 복잡한 AI 코드.
- **전용 몬스터 서버 패턴**: 게임 서버 → 몬스터 서버로 공격 요청 전달 → 몬스터 서버가 대미지 계산 + 보상 처리 → 결과를 게임 서버에 반환 → 클라이언트 갱신.
- **오버헤드 함정**: 몬스터 1마리 처리는 ~1000 클록 이하인데, 서버 간 메시지 패싱(소켓 호출 + 커널 진입 + 디바이스 드라이버)만 4000+ 클록. 300 클록 실연산을 위해 4000 클록 OS 오버헤드 → **분리가 오히려 역효과**가 날 수 있음.
- **광역 스킬 집중 버스트**: 플레이어가 몬스터 군집에 AoE 사용 시 게임 서버 ↔ 몬스터 서버 간 메시지가 폭증 → 순간 지연·서비스 중단 위험.
- **결론**: 몬스터 서버 분리는 반드시 **프로파일러로 AI 코드 CPU 점유율을 측정한 뒤** 결정. 근거 없는 선행 분산 금지.

### 10.5 플레이어 간 상호 작용 분산 처리 (무료 접근)

- **상호 작용 특성 5가지**: 높은 정확도(PvP 판정 ms 단위), 높은 성능, 고빈도(기관총 초당 5회 이상), 원자성(모든 관련 플레이어에게 동시 반영), 낮은 허용 지연(1/20초 오차도 게임플레이 영향).
- **권장 기본 전략**: 플레이어 간 직접 상호작용은 **분산하지 않는 것**이 원칙. 동기화 요구와 원자성 유지 비용이 분산 이득을 압도한다.
- 분산이 필요하다면 **상호작용하지 않는 플레이어 그룹 단위**로만 지역 분산(예: 서로 다른 존/채널의 플레이어 집합은 다른 서버).

### 10.6 로그 및 통계 분석의 분산 처리 (무료 접근)

- **로깅 목적**: 플레이어 행동 추적(10초마다 위치, 사냥 데이터, 사망 기록, 아이템 사용), 게임 밸런스 분석(사망 히트맵, XP 곡선, 몬스터 보상 분포), 분쟁 조사.
- **DB 직접 기록 병목**: DB 기록은 파일 직접 기록보다 수십 배 느림. 로그 누적 시 큐 길이 증가 → 쿼리 응답 지연 → 게임플레이 레이턴시 스파이크.
- **분석 쿼리 경합**: 통계 분석 쿼리는 DB 실행에 약 10분 소요 → 이 기간 중 일반 게임 DB 연산이 경합으로 크게 느려진다.
- **해결 아키텍처**: 게임 서버가 로그를 **전용 로그 서버**에 전달(비동기) → 로그 서버가 DB 기록 담당 → 분석 쿼리도 로그 DB에서만 실행. 게임 플레이 서버는 ODBC/ADO 오버헤드에서 해방.
- **파일 기반 로그 → 배치 적재 패턴** (일반 지식 보완): 로그를 먼저 파일로 빠르게 기록 후 배치로 DB 적재하는 두 단계 구조도 흔히 사용됨. Kafka/로그 큐로 게임 서버 → 수집기 → 분석 DB로 이어지는 파이프라인이 현대 표준.

### 10.7 게임 장르별 분산 서버 형태 (무료 접근)

- **MMORPG**: 게임 월드를 소지역 단위로 파티션 → 각 지역 담당 서버. 경매장 같은 특수 기능은 별도 서버로 분리. 릴레이 서버(클라이언트 메시지를 적절한 서버로 전달) + 로직 서버(지역 단위 처리)로 이원화. 인접 서버끼리 위치·HP 등 연속 복제(replication); 캐릭터 밀도 초과 시 소유권을 인접 서버로 이관.
- **EVE Online / Game of War 유형**: 수백만 명이 단일 광활한 월드를 공유하는 구조는 소지역 분할이 어려움 → 특수한 공간 파티셔닝 또는 시간 팽창 기법 필요. (일반 지식 보완)
- **NPC 로직 분리 변형**: NPC AI가 병목이면 NPC 로직만 별도 머신으로 이전. 반대로 플레이어 이동 연산이 병목이면 이동 계산만 분리도 가능.
- **소켓 I/O 병목 변형**: 게임 서버와 클라이언트 사이에 **패킷 릴레이 서버**를 두어 멀티캐스트 분산 처리를 전담.
- **FPS/RTS** (일반 지식 보완): FPS는 방(룸) 단위 인스턴싱이 표준 — 배틀 서버 풀 + 마스터(매치메이킹) 1대. RTS는 참여 플레이어 수가 적어 단일 게임 서버로도 충분한 경우가 많음; 관전자·리플레이 분리가 쟁점.
- **핵심 원칙**: "어떤 장르든 정답은 없다. 해당 프로젝트의 성능 분석 결과로 결정한다." 장르별 사례는 참고 답안이지 정형식이 아님.

### 10.8 요약 및 결론 (무료 접근)

- 게임 장르만으로 분산 형태가 결정되지 않는다. 같은 장르 내에서도 전투 방식·커뮤니티 설계에 따라 아키텍처가 달라진다.
- **두 가지 실수 경계**: ① 분산 불필요한 컴포넌트를 분산 → 오버헤드만 증가. ② 반드시 분산해야 할 컴포넌트를 방치 → 단일 장애점.
- 9장의 분산 서버 설계 원칙을 기반으로, 10장 사례를 참고 답안으로 삼아 자신의 게임에 맞게 커스터마이징하라.

## 우리 프로젝트 적용

| 주제 | 현재 상태 | 해당 클래스·파일 |
|------|----------|----------------|
| 인증 분산 / 로드밸런서 | **현재 무관** (싱글 서버 개발 단계) | — |
| DB 샤딩 | **현재 무관** (LocalDB 단일 인스턴스, M5 영속화 예정) | EF Core 마이그레이션 파일 |
| 매치메이킹 / 로비 | **현재 무관** (맵 Portal 이동만 존재) | `02_Server/GameServer/GameMap.cs` portal handoff |
| 몬스터 AI 분산 | **채택 후보 아님 (우선 프로파일링 먼저)** | `02_Server/GameServer/Maps/GameMap.cs` `UpdateEnemies()` — God class 분리가 선행 과제 |
| 플레이어 간 상호작용 분산 | **이미 올바른 방향** — 단일 맵 Actor 안에서 처리, 분산 없음 | `02_Server/GameServer/GameMap.cs` `ProcessAttack()` |
| 로그 서버 분리 | **채택 후보** — M4.4 cheat-flag + Serilog 도입 시 로그를 별도 로그 서버나 파일 큐로 빼는 것이 적합 | M4.4 계획, 현재 없음 |
| 장르별 패턴(MMORPG 지역 분할) | **이미 사용 중** — 맵 Actor 분리(M4.2 완료), 맵별 단일스레드 20TPS tick | `02_Server/GameServer/GameMap.cs`, `TickScheduler` |

**가장 가까운 적용 포인트**: 로그 서버 분리 패턴. M4.4에서 Serilog 도입 시 게임 서버가 직접 DB에 로그를 쓰지 않도록 **비동기 로그 싱크(파일 → 배치 적재)** 구조를 선택하면 10.6절 권고와 정합.

## 함정 / 과용 경계

- **근거 없는 선행 분산**: "몬스터가 많으니 AI 서버 분리" → 10.4절이 경고한 바로 그 실수. 반드시 프로파일러 수치 먼저.
- **플레이어 상호작용 분산 시도**: 원자성·동기화 요구가 극심해 득보다 실이 크다. 10.5절 권고대로 "분산하지 않는 것"이 기본값.
- **샤드 수 임의 결정**: 재해싱 비용이 운영에 직격. 초기 설계 시 **샤드 수를 충분히 크게 잡거나 일관성 해싱** 사용.
- **분산 = 성능 해결** 오해: 메시지 패싱 오버헤드가 분산 이득을 상쇄할 수 있음(10.4절 클록 계산 참조). 경량 연산일수록 분산 효과 감소.
- **장르 패턴 복붙**: "MMORPG니까 지역 서버 분할" → 프로젝트 특성(전투 방식, 동시접속 규모)과 맞지 않을 수 있다. 10.8절 결론 참조.
