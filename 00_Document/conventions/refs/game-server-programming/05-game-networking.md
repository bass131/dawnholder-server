# [GSP-05] 게임 네트워킹 (Game Networking)

> 온라인 게임에서 서버-클라이언트가 게임 상태를 어떻게 나눠 가지며, 지연(latency)을 어떻게 감추는지를 다루는 핵심 설계 장. Prediction/Reconcile의 근거 이론.

---

## 언제 참조하나 (트리거)

- Prediction, Reconcile, Dead Reckoning, lag compensation 설계나 버그를 다룰 때.
- 서버 권위 모델(Server Authority)을 새 기능에 어떻게 적용할지 논의할 때.
- 넓은 맵에서 플레이어 수 증가로 네트워크 트래픽 문제가 생길 때 (AOI/Visibility 필터링 검토).
- RTS식 명령 동기화(Lock-step) vs MMORPG식 상태 동기화 방식 선택 기준이 필요할 때.
- 치트/핵 방어, rate-limit, 패킷 암호화 설계를 할 때.

---

## 핵심 내용

### 5.2 게임플레이 네트워킹 — 세 가지 모델

#### 모델 1: 모든 연산을 서버에서 (고전 모델) — 0286

클라이언트 = 멍텅구리 터미널. 사용자 키 입력과 화면 출력만 담당.
서버가 게임 로직 + 렌더링 + 화면 스트리밍까지 전담.
장점: 치트 원천 차단. 단점: 서버 부하 극단적, 현대 게임에선 비현실적.

#### 모델 2: 렌더링은 클라이언트에서 — 0289

서버: 월드 상태 연산 + 최소한의 렌더링 데이터만 전송.
클라이언트: 그래픽 리소스 보유 + 렌더링 전담.
핵심 계약: **서버와 클라이언트의 월드 상태(scene)를 동일하게 유지** = 동기화(synchronization).
현대 온라인 게임의 기본 구조. 서버가 상태를 권위적으로 계산하고, 클라이언트는 그것을 화면에 옮기는 역할이다.

#### 5.2.3 추측항법 (Dead Reckoning) — 0297

문제: 클라이언트가 다른 플레이어의 위치를 표시할 때, 서버로부터 온 패킷은 이미 과거의 상태다. 화면에 그대로 그리면 항상 한 템포 늦게 보인다.

해법: **상대방의 이동을 어느 정도 예측해서 위치를 보정**하는 것이 Dead Reckoning.

구현 요소:
- **레이턴시 측정**: A→B 패킷 전송 후 B가 응답, A가 왕복 시간 측정 후 2로 나눠 편도 지연 추정.
- 측정된 지연과 상대방의 속도 벡터를 이용해 "지금쯤 여기 있겠다"고 외삽(extrapolate).
- 예측이 틀리면 다음 실제 위치 패킷 도착 시 보정 — 가시적 끊김 vs 보이지 않는 보정 중 선택.

---

### 5.3 레이턴시 마스킹 (Latency Masking) — 0301

기본 플로우:
1. 클라이언트가 방향키 입력을 서버로 전송
2. 서버가 위치 연산
3. 서버가 1/30~1/10초 간격으로 위치 업데이트 전송
4. 클라이언트가 수신 후 Dead Reckoning으로 부드럽게 보간

문제: 방향키를 누른 순간 캐릭터가 **즉시 움직이지 않고 지연 후 움직임** → 조작감 최악.
원인: 서버 왕복(RTT) 동안 플레이어가 "아무 반응 없음"을 보게 됨.

해법 = **Prediction(예측 선행 이동)**:
- 클라이언트가 입력을 서버에 보내는 동시에, 서버 응답을 기다리지 않고 **로컬에서 즉시 캐릭터를 이동**시킴.
- 서버 응답이 오면 실제 위치와 비교 → 차이가 있으면 **Reconcile(보정)**.
- 플레이어 눈에는 즉각 반응처럼 보이고, 권위는 여전히 서버가 유지.

이것이 곧 **Prediction/Reconcile** 패턴 — 레이턴시를 없애는 게 아니라 *감추는(masking)* 기술이다.

---

### 5.4 넓은 월드, 많은 캐릭터 처리 — 0307

문제: MMORPG에서 수천 명의 캐릭터가 있을 때 모든 상태 변화를 모든 클라이언트에 방송하면 트래픽이 폭발한다.

관찰: **플레이어 관심사는 눈앞의 가까운 것들**. MMORPG에서 1km 떨어진 캐릭터는 화면에 거의 안 보인다.

해법 = **Visibility(가시 영역) 필터링 / AOI(Area of Interest)**:
- 서버는 플레이어의 가시 반경 내 변화만 해당 클라이언트에 전송.
- 모든 월드 변화를 전체 방송(broadcast)하지 않음.
- 트래픽은 (전체 캐릭터 수)에서 (가시 범위 내 캐릭터 수)로 급감.

구현: 월드를 격자(grid) 또는 공간 파티셔닝으로 분할, 인접 셀에 속한 엔티티만 관심 목록에 포함.

---

### 5.5 RTS 게임의 Lock-Step 동기화 — 0309

RTS 특성: 캐릭터 수십~수백 개, 플레이어 수는 적음 (2~8인).

문제: 캐릭터가 많아질수록 상태 동기화 트래픽 폭증. MMORPG 방식(상태 전송)으로는 감당 안 됨.

**Lock-Step 알고리즘**:
- "군대에서 신호에 맞춰 모두가 같은 동작을 하는 것"처럼, 모든 클라이언트가 **동일한 입력 명령만** 공유.
- 서버(또는 피어)가 매 틱 "이번 틱에 각 플레이어가 내린 명령" 목록만 전파.
- 각 클라이언트가 동일한 명령 목록으로 **로컬에서 동일하게 시뮬레이션** → 결과가 일치.
- 전송 데이터: 상태 전체가 아닌 **명령(Command)만** → 트래픽 극소.

전제 조건: **완전한 결정론(Determinism)** — 같은 입력이 항상 같은 결과를 낳아야 함. 부동소수점 불일치 하나가 전체 탈동기화(desync)를 유발한다.

MMORPG와 차이:
| 방식 | 전송 단위 | 클라이언트 역할 | 캐릭터 수 적합 |
|---|---|---|---|
| 상태 동기화 (MMORPG) | 위치/HP 등 상태값 | 서버 상태 표시 | 적음~중간 |
| Lock-Step (RTS) | 입력 명령만 | 로컬 시뮬레이션 | 수백 개 가능 |

---

### 5.6 실제 레이턴시 줄이기 — 0314

두 가지 실용 기법:

**1. UDP 사용**
TCP는 패킷 유실 시 재전송 대기(HOL blocking)로 지연 발생. 캐릭터 위치처럼 **연속적으로 송신되는 메시지는 유실돼도 다음 패킷이 보정**하므로 UDP가 더 적합.

**2. 패킷 병합(Coalescing)**
개별 메시지를 매번 즉시 송신하지 말고, **짧은 대기 구간에 모아 한 번에 전송**.
- 무선 CSMA 오버헤드, TCP/IP 헤더 오버헤드 감소.
- 권장 배치 간격: **10ms 이하** (너무 길면 체감 지연 증가).

---

### 5.7 게임플레이 이외의 네트워킹 — 0316

로그인 프로세스 표준 흐름:
1. 클라이언트 → 서버: 로그인 요청 (ID/PW)
2. 서버: DB에서 자격증명 조회/검증
3. 서버 → 클라이언트: 인증 결과 통보
4. 성공 시: 서버가 DB에서 플레이어 정보를 메모리로 로드

이 외에도 채팅, 매칭메이킹, 길드 등 게임플레이와 무관한 네트워크 흐름이 별도 설계 필요.

---

### 5.8 해킹과 보안 — 0325~0332

멀티플레이어 게임의 해킹은 피해자가 다수 → 단일 플레이어 게임보다 훨씬 심각.

**두 종류**:
- **크래킹(Cracking)**: ID/PW 탈취, 서버 데이터 손상/절취. 일반 인터넷 서비스 해킹과 유사.
- **치트(Cheat)**: 본인 스탯 비정상 강화 또는 다른 플레이어 방해.

#### 5.8.1 네트워크 해킹 — 0326

공격: 중간자(MITM)가 클라이언트-서버 패킷을 도청 → ID/PW 탈취.
인터넷은 수많은 공유 네트워크 장비를 경유하므로 도청을 *막을 수 없다*.

핵심 용어:
- **평문(plaintext)**: 암호화 전 데이터
- **암호문(ciphertext)**: 암호화 후 데이터
- **암호 키(encryption key)**: 고정 크기 바이너리 데이터 — 키 없이는 원문 복원 불가

해법: **전송 데이터를 암호화**. 도청돼도 내용을 알 수 없게 만든다.

#### 5.8.2 클라이언트 컴퓨터 해킹 — 0330

공격: 악성 첨부파일/링크로 클라이언트 PC에 악성코드 심기 → 실행 중인 프로세스 메모리 조작.
한계: 클라이언트 메모리 안에는 암호화 전 평문이 이미 존재 → 암호화만으로 방어 불충분.
대응: OS/앱 최신 패치, 불필요한 보안 기능 비활성화 금지, 출처 불명 실행파일 차단.

#### 5.8.3 서버 컴퓨터 해킹 — 0331

서버 해킹은 전체 사용자가 피해 → 개인 PC 해킹보다 파급이 훨씬 크다.
대응:
- **방화벽**: 공개 리스닝 포트(플레이어 접속용)를 제외한 모든 포트 차단.
- **쿼리 인젝션 방어**: DB 접근 시 파라미터 바인딩 사용 (7장 참조).
- **지속적 패치**: 공격자는 새 취약점을 계속 발굴 → 방어도 지속적이어야 함.

#### 5.8.4 게임 치트 — 0332

대표 공격: **패킷 재전송(Replay Attack)**.
- 공격자가 "공격 행동" 패킷 하나를 캡처해 서버에 수백 번 재전송 → 서버가 수백 번의 공격 처리 → 비정상적으로 빠른 공격속도.

핵심 방어: **서버가 메시지 간 시간 간격도 유효성 검증** (Rate-limit).
- 초당 최대 공격 횟수 제한, 타임스탬프/시퀀스 번호 검증, 의심 패턴은 cheat-flag 로깅.

공격-방어는 지속적 군비 경쟁: 게임이 복잡해질수록 새로운 취약점이 발생 → 보안은 일회성이 아니라 *지속적 운영*이다.

## 우리 프로젝트 적용

### 5.2 게임플레이 네트워킹 — 이미 사용 중

`02_Server/`가 모델 2(렌더링은 클라이언트)를 완전히 구현 중:
- `02_Server/GameServer/Maps/GameMap.cs`: 서버 권위 월드 상태 관리 + 연산.
- `02_Server/GameServer/Network/GameSession.cs`: 클라이언트에 최소 상태 패킷만 전송.
- 헌법 원칙 #1 "클라이언트 = 렌더러"가 이 모델의 직접 명문화.

### 5.3 레이턴시 마스킹 — 이미 사용 중

`03_Client/Assets/Scripts/`:
- `Prediction/PlayerPredictor.cs` + `Prediction/InputHistory.cs`: Prediction 구현. 입력 즉시 로컬 이동 + 히스토리 큐 보관.
- Reconcile: 서버 위치 패킷 수신 시 히스토리와 비교 → 불일치 보정.
- `State/RemoteEntity.cs`: Dead Reckoning 원리 적용 — 150ms 버퍼링 후 보간 표시.
- 입력 송신 50ms cadence = 서버 20TPS 틱과 정렬.

### 5.4 넓은 월드 — 채택 후보

현재 맵별 브로드캐스트 방식(`GameMap.BroadcastPacket()`). 플레이어 수가 많아지면 AOI 필터링 필요.
`02_Server/GameServer/Maps/GameMap.cs`의 `BroadcastPacket()` 개선 포인트로 마킹.

### 5.5 Lock-Step — 현재 무관

Dawnholder는 MMORPG 상태 동기화 방식. RTS Lock-step은 아키텍처 근본이 달라 현 단계에서 불필요.
참고 가치: **Determinism의 중요성** — lag compensation의 rewind 결과가 서버-클라 간 일치해야 하는 이유.

### 5.8 보안 — 일부 적용, 일부 미비

적용 중:
- `02_Server/GameServer/Network/GameSession.cs` Rate-limit: 기본 패킷 빈도 제한.
- 헌법 원칙 #3 Trust Boundary: 클라이언트 입력 전부 untrusted 처리.

M4.4 이월/계획:
- **cheat-flag 테이블 로깅**: 의심 패킷 패턴 기록 (`02_Server/`).
- **Serilog 구조적 로깅**: 보안 이벤트 추적.
- **패킷 암호화**: 현재 평문 TCP → TLS 또는 자체 암호화 레이어 (장기 과제).

## 함정 / 과용 경계

- **Prediction 남용**: 클라이언트가 HP, 데미지, 아이템 획득까지 예측하면 치트 경계가 흐려진다. Prediction은 **이동(visual 선행)**에만 적용, 게임 결과(전투/아이템)는 서버 응답 대기가 원칙.
- **Dead Reckoning 과도 외삽**: 레이턴시가 크거나 속도 변화가 잦으면 예측 오차가 시각적으로 튄다. 외삽 한계(`maxExtrapolationTime`)를 두고, 임계 오차 이상이면 즉시 스냅.
- **Lock-Step을 MMORPG에 적용**: 한 명이 지연되면 전체 게임이 그 사람을 기다려야 한다. MMORPG처럼 수백 명이 접속하는 환경에선 단 한 명의 lag spike가 서버 전체를 멈추게 된다.
- **AOI 없는 무차별 브로드캐스트**: 플레이어 수가 늘수록 O(n²) 트래픽 증가. 50명만 넘어도 체감 가능 — 조기에 AOI 설계해야 한다.
- **치트 방어를 클라이언트에 의존**: 클라이언트는 공격자가 완전히 제어할 수 있는 환경. 모든 유효성 검사는 서버에서만 신뢰.
- **Rate-limit만 있고 시퀀스 번호 없음**: 패킷 재전송 공격은 Rate-limit 안에서도 가능하다. 패킷에 단조 증가 시퀀스 번호를 붙이고 서버가 중복/역순 패킷을 거부해야 완전한 방어.
