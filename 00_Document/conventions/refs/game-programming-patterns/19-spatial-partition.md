# [19] Spatial Partition (공간 분할)
> 객체를 위치 기반 자료구조에 저장해 "이 좌표 근처 객체 찾기"를 O(n²) → O(1)~O(log n)으로 낮추는 최적화 패턴.

## 언제 참조하나 (트리거)
- 전투 판정에서 "공격 범위 안 적 탐색" 루프가 느리다는 프로파일링 결과가 나올 때.
- 서버 틱(20TPS)에서 n²쌍 비교가 걸린다는 의심이 들 때.
- 맵 안 유닛 수가 수십 개를 넘기 시작하고 hitbox/aggro 범위 쿼리 빈도가 높아질 때.
- 새 맵이나 Zone을 설계하면서 공간 쿼리 구조를 선택해야 할 때.

## 핵심 내용
- **문제**: 유닛 n개가 있으면 "가까운 적 찾기"를 브루트포스로 하면 매 틱 O(n²)쌍 비교. n=100이면 ~5,000쌍, n=500이면 ~125,000쌍 — 틱이 50ms인데 비교만으로 예산 초과.
- **해법**: 월드를 공간 자료구조로 색인. 새 위치 쿼리는 해당 셀/노드만 검색하면 됨. 구조에 따라 O(1) ~ O(log n) ~ O(k) (k=결과 수).
- **대표 구현 — 고정 그리드(flat grid)**:
  - 월드를 셀(e.g., 100×100 픽셀 블록)로 나누고, 각 셀이 이중 연결 리스트로 그 칸 안 유닛을 관리.
  - 유닛 이동 시: 같은 셀이면 좌표만 갱신. 다른 셀이면 O(1) unlink → O(1) relink.
  - 범위 쿼리: 해당 셀 + 인접 셀만 순회. 인접 4~8개 셀로 double-count 방지 가능.
  - 장점: 구현 단순, 메모리 고정, 이동 업데이트 빠름. 단점: 빈 셀 낭비, 밀집 구역에서 효과 감소.
- **계층 구조 — 쿼드트리/옥트리**:
  - 전체 공간을 하나의 파티션으로 시작. 한 파티션 안 유닛이 임계값 초과 시 4등분(2D) 또는 8등분(3D). 밀집 구역만 재귀 분할.
  - 빈 공간 낭비 없음, 밀집 구역 정밀 분할. 단점: 이동 업데이트 시 계층 탐색 필요, 코드 복잡.
- **기타 구조**: BSP(Binary Space Partitioning, 평면으로 재귀 이분), k-d 트리(다차원 이진 탐색 트리, 분포 균형), BVH(Bounding Volume Hierarchy, 정적 지오메트리에 강함).
- **두 축의 설계 결정**:
  - 평탄(flat) vs 계층(hierarchical): 평탄은 단순·예측 가능. 계층은 밀집/희소 혼재에 유리.
  - 객체 독립(fixed) vs 객체 의존(adaptive): fixed는 증분 삽입 O(1). adaptive는 초기 구축 비용이 크고 동적 오브젝트에 부적합.
- **언제 쓰나**: 위치 있는 객체가 많고, 위치 기반 쿼리(근처 탐색)가 매 틱 빈번하고, 프로파일링으로 병목이 확인됐을 때.
- **언제 안 쓰나**: n이 작으면(수십 이하) 자료구조 오버헤드가 이득보다 큼. 메모리가 극히 제한적일 때. 객체가 거의 이동 안 하고 쿼리도 드물 때.

## 우리 프로젝트 적용
- **현재 상태**: 미적용. `02_Server/GameServer/Maps/GameMap.cs` 안 `ProcessAttack` 및 `UpdateEnemies`에서 적 탐색이 `_players` + `_enemies` 리스트를 전체 순회하는 브루트포스로 추정됨.
- **단기 채택 후보**: 맵 안 유닛 수가 50~100명 이상 될 M5~M6 구간에서 고정 그리드가 첫 선택. 구현 단순하고 이동 업데이트 비용이 예측 가능해 20TPS 틱 예산 관리에 유리.
- **적용 지점**:
  - `02_Server/GameServer/Maps/GameMap.cs` — `ProcessAttack` 공격 범위 탐색, `UpdateEnemies` aggro 범위 탐색을 그리드 쿼리로 교체.
  - `02_Server/GameServer/Maps/` 하위에 `SpatialGrid.cs` 신설. 셀 크기는 최대 공격 범위의 2배로 잡으면 인접 1셀 탐색으로 커버 가능.
- **lag compensation와 연계**: `PlayerEntity` 링 버퍼에 저장된 과거 위치로 rewind 후 공간 쿼리 시, 과거 스냅샷을 기준으로 그리드를 다시 색인해야 정확. 구현 복잡도가 오르므로 우선 현재 위치 기준 그리드로 시작, rewind 연동은 M4.4 이후 검토.
- **클라이언트 측**: 클라이언트에서 공간 쿼리가 필요한 경우(예: 로컬 사운드 감쇠, RemoteEntity 렌더 컬링)에 동일 패턴 적용 가능. 단, 판정 권위는 서버에만.

## 함정 / 과용 경계
- **너무 이른 최적화**: 유닛 30명 이하 맵에서 그리드 추가하면 이동 업데이트 코드만 복잡해지고 성능 이득이 없음. 프로파일링 먼저.
- **셀 크기 오판**: 셀이 너무 크면 "같은 셀 안 객체" 수가 많아져 브루트포스와 동일. 셀이 너무 작으면 인접 셀 탐색 수가 폭증. 경험 법칙: 셀 크기 ≈ 최대 상호작용 거리의 1~2배.
- **계층 구조 과도 도입**: 쿼드트리는 동적으로 자주 이동하는 오브젝트(플레이어, 몬스터)에 유지 비용이 큼. 정적 지형/콜라이더에 BVH, 동적 유닛에 그리드를 분리 운영하는 패턴이 실전적.
- **이중 연결 리스트 포인터 오염**: 유닛 풀(Object Pool) 패턴과 함께 쓸 때 재활용 시 prev/next 초기화를 빠뜨리면 dangling pointer. 풀 반환 시 반드시 셀에서 unlink 먼저.
- **헌법 #5 위반 주의**: 그리드 재구축(전체 셀 초기화)을 틱 루프 안에서 동기로 돌리면 50ms 예산 초과. 재구축 필요 시 다음 틱 분산 처리 또는 증분 업데이트만.
