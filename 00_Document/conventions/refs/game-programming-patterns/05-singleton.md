# [GPP-05] Singleton (싱글턴)
> "클래스의 인스턴스가 하나뿐임을 보장하고, 전역 접근점을 제공한다" — 쓰면 안 될 상황이 대부분인 패턴.

## 언제 참조하나 (트리거)
- `static readonly` 전역 관리자 클래스(`AudioManager`, `NetworkManager` 등)를 새로 설계할 때.
- 기존 Singleton 클래스를 리팩터링하거나 의존성을 정리할 때.
- "이걸 어떻게 여러 곳에서 접근하지?" 라는 질문이 떠오를 때 — 먼저 이 파일을 읽는다.
- `ServiceLocator`·`SubclassSandbox` 패턴 선택 분기 전 비교 참조.

## 핵심 내용

### 패턴이 다루는 두 가지 문제
GoF Singleton은 **"단일 인스턴스 보장"** 과 **"전역 접근점 제공"** 을 한 번에 해결한다. 문제는 이 두 관심사가 서로 독립적인데 하나로 묶여 있다는 것이다.

- **단일 인스턴스 보장이 필요한 경우**: 파일시스템 래퍼처럼 비동기 I/O 상태를 관리하는 클래스는 인스턴스가 둘이면 서로 상태를 모른 채 충돌한다. 이때 인스턴스가 하나임을 강제하는 건 타당하다.
- **전역 접근이 필요한 경우**: 오디오, 로그 등 게임 전반에서 쓰는 객체를 매번 파라미터로 전달하기 번거로울 때 전역 접근점이 편리하다.

### Singleton의 표면적 장점
- **지연 초기화(Lazy init)**: 실제로 호출되기 전까지 생성되지 않는다. 사용하지 않으면 비용 없음.
- **런타임 초기화**: `main()` 전에 실행되는 정적 멤버와 달리 런타임 정보를 사용해 초기화할 수 있다.
- **다형성 지원**: 플랫폼별로 서브클래스를 조건부 컴파일해 교체할 수 있다.

### 왜 쓰면 안 되는가 — 세 가지 근본 문제

1. **전역 상태다.** 클래스로 감쌌을 뿐 전역 변수와 본질이 같다. 전역 상태는 (a) 함수 추론을 어렵게 만들고, (b) 의도하지 않은 결합을 부추기며, (c) 멀티스레드 환경에서 경쟁 조건·교착을 유발한다.

2. **하나의 클래스에 두 책임을 합쳐 버린다.** 로거가 파일을 시스템별로 분리해야 하는 요구가 생기면? Singleton이라 단일 인스턴스 제약을 깨기 어렵다. "단일 인스턴스"와 "전역 접근"은 따로 설계해야 한다.

3. **지연 초기화가 게임에 독이 된다.** 처음 호출되는 시점에 리소스 로드·메모리 할당이 일어나면 인게임 프레임 스터터가 발생한다. 게임은 초기화 타이밍을 직접 제어해야 한다. 결과적으로 많은 게임이 lazy init을 포기하고 정적 인스턴스를 쓰는데, 그러면 다형성 이점마저 사라진다.

### 언제 완전히 쓰면 안 되나
- 테스트가 필요한 코드: 전역 상태는 테스트 격리를 무너뜨린다.
- 멀티스레드 컨텍스트(서버 틱 루프, JobQueue 등): 락 없는 Singleton은 레이스 컨디션.
- "매니저" 클래스가 없어도 될 때: `BulletManager`가 Bullet을 생성하고 범위를 체크한다면, 그 로직은 `Bullet` 자신 안으로 이동해야 한다. 나쁜 OOP 설계의 징후.

## 우리 프로젝트 적용

| 상태 | 클래스/파일 | 비고 |
|------|-------------|------|
| **채택 후보 (Service Locator로 대체 권고)** | `02_Server/` 내 미래 오디오·설정·로그 서비스 | Serilog DI 방식으로 처리 — Singleton 불필요 |
| **이미 사용 중 (유의 필요)** | `03_Client/` 내 Unity MonoBehaviour 싱글턴 패턴 | Unity `Instance` 패턴은 씬 전환 시 null-ref 위험. `DontDestroyOnLoad` 관리 명시 필요 |
| **대안 채택 중** | `GameServer` / `MapRegistry` | DI 컨테이너(`IServiceProvider`) 없이도 생성자 주입 또는 `Game` 루트 객체 단일 진입점 방식 선호 |

핵심: **서버 틱 루프(`02_Server/GameServer/Loop/`)는 전역 상태 접근 자체를 최소화해야 한다.** Singleton을 틱 루프 안에서 호출하면 헌법 원칙 #5(블로킹 금지)와 원칙 #1(서버 권위) 경계가 흐릿해진다.

## 함정 / 과용 경계

- **"전역이 필요하다 → Singleton"** 의 자동 반사 금지. 우선 파라미터 전달(의존성 주입)을 고려하라. 실제로 의존성이 명시되면 아키텍처 냄새가 드러나 설계가 개선된다.
- **"매니저" 폭발**: `AudioManager`, `InputManager`, `NetworkManager`... 게임 코드베이스에서 Singleton 남용의 전형. 각각이 정말 인스턴스 1개여야 하는지, 아니면 단지 어디서든 접근하고 싶은 것인지 구분하라.
- **Unity에서의 Singleton**: `Awake()`에서 `Instance = this` 패턴은 씬 재로드·additive 로드 시 이전 인스턴스가 파괴되지 않으면 중복 생성된다. `DontDestroyOnLoad` + null 검사 없이 쓰면 씬 전환 버그의 단골.
- **테스트 불가 코드 양산**: Singleton을 직접 호출하는 코드는 목(mock) 주입이 불가능해 유닛 테스트가 막힌다.

## 대안 정리 (우선순위 순)

1. **파라미터 전달(의존성 주입)**: 가장 명시적. 함수 시그니처가 의존성을 드러낸다. 로그처럼 "cross-cutting concern"에는 시그니처 오염이 크다는 단점.
2. **Base class를 통한 접근 (Subclass Sandbox)**: 하위 클래스가 보호된 메서드를 통해 공유 리소스에 접근. 시그니처 오염 없이 결합 범위 제한 가능.
3. **루트 Game 객체 단일 전역**: 전역을 여러 개 두는 대신 `Game::instance().getAudio()` 하나로 집중. 이후 멀티 인스턴스 지원도 열려 있다.
4. **Service Locator 패턴**: 전역 레지스트리에서 서비스 인터페이스를 조회. Singleton보다 유연하고 테스트 시 mock 교체 가능 — [[15-service-locator]] 참조.
5. **단일 인스턴스만 필요하다면**: 전역 접근 없이 생성자 어설션(`Debug.Assert(!instantiated_)`)으로 중복 생성 방지만 해도 충분.
