# [GPP-10] Bytecode (Bytecode)
> 행동(behavior)을 데이터로 인코딩해 경량 VM이 해석하게 함으로써, 코드 재컴파일 없이 안전하게 로직을 정의·수정·샌드박싱하는 패턴.

## 언제 참조하나 (트리거)
- 마법(spell)/스킬/AI 행동 등을 비개발자가 반복적으로 수정해야 할 때
- 출시 후 패치로 게임 밸런스나 스크립트를 교체해야 할 때
- 모딩 지원이나 사용자 제공 스크립트를 엔진과 격리(sandbox)해야 할 때
- 컴파일 속도가 너무 느려 디자이너 이터레이션 속도를 막고 있을 때

## 핵심 내용

### 해결하는 문제
C++ 같은 시스템 언어에 행동을 하드코딩하면, 스킬 하나를 고칠 때마다 재컴파일이 필요하고 코드가 엔진 전체에 결합된다. 동시에 스크립트를 그냥 eval하면 크래시나 보안 구멍이 생긴다. Bytecode 패턴은 이 두 위험을 동시에 해소한다: **행동을 데이터(바이트 배열)로 표현**하고, 그것을 가상 기계(VM)가 안전하게 해석한다.

### 해법 구조
세 가지 핵심 요소로 구성된다:

- **명령어 집합(instruction set)**: `enum`으로 정의된 유한한 연산 목록. 이 집합이 "무엇을 표현할 수 있는가"의 경계를 결정한다.
- **바이트코드**: 명령어 열거형 값들이 평탄한 바이트 배열로 저장된 이진 포맷. 게임 데이터 파일에 담겨 런타임에 로드된다.
- **스택 기반 VM**: 내부 스택과 명령어 포인터를 가진 해석기. 바이트코드를 순서대로 읽으며 switch로 각 명령을 실행한다.

### 실행 모델: 스택 머신
명령어들은 인자를 스택에서 pop하고 결과를 push한다. 예를 들어 `health + (agility + wisdom) / 2`를 설정하는 흐름:

```
LITERAL 0       → 스택: [0]           // 마법사 인덱스
GET_HEALTH      → 스택: [45]          // 현재 체력 읽기
LITERAL 0       → 스택: [45, 0]
GET_AGILITY     → 스택: [45, 7]
LITERAL 0       → 스택: [45, 7, 0]
GET_WISDOM      → 스택: [45, 7, 11]
ADD             → 스택: [45, 18]
LITERAL 2       → 스택: [45, 18, 2]
DIVIDE          → 스택: [45, 9]
ADD             → 스택: [54]
SET_HEALTH      → 스택: []            // 결과 반영
```

스택이 중간 변수를 모두 암묵적으로 처리하므로 코드 생성이 단순하다.

### 명령어 카테고리
- **외부 프리미티브**: 게임 엔진 API 호출 (`setHealth`, `playSound`, `spawnParticles`). 어떤 능력을 허용할지 큐레이션이 핵심.
- **내부 프리미티브**: 리터럴 적재, 산술(`ADD`, `DIVIDE`), 비교(`LESS_THAN`, `EQUAL`)
- **제어 흐름**: 명령어 포인터를 직접 바꾸는 jump 명령. 반복문·분기를 구현할 수 있지만 무한루프 위험이 생겨 실행 횟수 상한 설계가 필요하다.
- **추상화**: 서브루틴 콜(call stack을 별도로 유지). 코드 재사용 허용.

### 스택 기반 vs 레지스터 기반 VM
| 항목 | 스택 기반 | 레지스터 기반(Lua 등) |
|------|-----------|----------------------|
| 명령어 크기 | 1바이트 가능 | 32비트 전형 |
| 코드 생성 난이도 | 단순 | 복잡 |
| 총 명령어 수 | 많음(스택 조작 많음) | 적음 |
| 구현 난이도 | 쉬움 | 어려움 |

책 추천: **스택 기반으로 시작하라.** 구현도 쉽고 컴파일러 작성도 쉽다.

### 값 표현 방식
- **단일 정수형**: 가장 단순, 표현력 제한
- **태그드 유니언(tagged union)**: 타입 태그 + 공용체. 동적 언어 대부분이 사용. 범용적이고 안전하지만 태그 오버헤드 존재.
- **비태그 유니언**: 컴팩트하고 빠르지만 타입 정보 없음 → 신뢰할 수 없는 바이트코드에는 위험
- **다형 클래스**: 확장성 좋지만 가상 함수 + 힙 할당으로 Interpreter 패턴의 단점 재현

추천: 단일 타입으로 될 수 있으면 그렇게, 안 되면 태그드 유니언.

### 바이트코드 생성 방법
두 가지 길이 있다:
1. **텍스트 언어 + 컴파일러**: 문법 설계 → 파서 구현 → 에러 처리. 기술적으로 도전적이고 비개발자에게 진입장벽이 높다.
2. **그래픽 저작 도구**: 초기 UI 투자가 크지만 사용자가 틀린 선택을 사전에 막을 수 있다. 비프로그래머에게 훨씬 친화적.

어느 쪽이든 **저작 도구 없이는 Bytecode 패턴을 도입하지 말라** — 생 바이트코드를 손으로 쓰는 건 비현실적이다.

### Interpreter 패턴과 비교
Interpreter(표현식 트리 방식)는 객체 하나당 포인터 역참조 + 가상 호출 → 캐시 오염이 심하고 느리다. Bytecode는 연속 메모리에 밀집 배치되어 일반적으로 5~10배 빠르다. 다만 Interpreter는 일반 코드 디버깅 도구를 그대로 쓸 수 있는 반면, Bytecode는 전용 디버깅 인프라가 필요하다.

### 언제 쓰지 말아야 하나
- 성능이 절대적인 핵심 경로(틱 루프 안, 물리 연산 등)
- 동작이 단순하고 바뀔 일이 없는 경우 — VM 비용이 이득을 초과
- 저작 도구 개발에 리소스를 쓸 수 없는 경우
- 팀 전체가 바이트코드 디버깅 방법을 이해할 시간이 없는 경우

## 우리 프로젝트 적용

**현재 상태: 채택 후보 (현재 미사용)**

현재 Dawnholder는 마법/스킬 행동이 없고 전투는 간단한 수치 공식으로 처리 중이다. 그러나 다음 지점에서 Bytecode 패턴이 미래에 관련된다:

- **스킬/마법 시스템 (미래)**: 스킬 효과를 `98_Shared/GameData/`에 바이트코드 파일로 저장하면, 서버 재컴파일 없이 밸런스 수정 가능. `02_Server/`의 `GameMap.ProcessAttack()`이 현재 C# 코드로 직접 처리하는 부분을 장기적으로 교체 대상으로 볼 수 있다.
- **AI 행동 스크립팅 (미래)**: `EnemyEntity`의 `EnemyState` FSM이 고정 C# 코드인데, 몬스터 종류가 늘면 다양한 AI 행동을 데이터로 정의할 필요가 생긴다. `99_Tools/`에 바이트코드 컴파일러를 두고 `02_Server/`의 AI 루프가 VM으로 해석하는 구조가 가능하다.
- **보안 요건**: `02_Server/Handlers/`에서 클라이언트 입력을 신뢰 경계 원칙(헌법 #3)에 따라 검증하는 것과 유사하게, 모딩 허용 시 사용자 스크립트를 VM으로 샌드박싱하는 데 직접 활용된다.

현재 채택 전제조건: 저작 도구(비주얼 에디터 또는 컴파일러)가 없으면 도입 금지.

## 함정 / 과용 경계
- **언어 크리프(scope creep)**: "작게 시작한 VM"이 반쪽짜리 프로그래밍 언어로 자라는 경향이 있다. 명령어 집합 크기에 명시적 상한을 정해두어야 한다.
- **디버깅 인프라 부재**: 바이트코드는 일반 디버거가 인식하지 못한다. VM에 전용 트레이싱·역추적 기능 없이 배포하면 버그 원인 추적이 거의 불가능하다.
- **반복문 → 무한루프**: 제어 흐름을 추가하는 순간 Turing-complete에 가까워지고 실행 시간 상한 구현이 필수다. 틱 루프 안에서 쓴다면 특히 치명적(헌법 #5: tick 블로킹 금지).
- **조기 도입**: 스킬이 10개 이하이고 디자이너가 요청하지 않은 단계에서 VM을 만드는 것은 과잉 엔지니어링이다.

## 관련
- Interpreter 패턴(GoF) — 같은 문제를 트리 방식으로 해결. 캐시 비친화적이지만 디버깅 용이.
- [[09-update-method]] — 게임 오브젝트 행동을 매 틱 실행하는 구조. Bytecode VM의 `interpret()` 호출 위치와 맞닿는다.
- [[12-type-object]] — 데이터로 몬스터 종류를 정의하는 패턴. Bytecode로 "행동까지 데이터화"하면 Type Object의 자연스러운 확장이 된다.
