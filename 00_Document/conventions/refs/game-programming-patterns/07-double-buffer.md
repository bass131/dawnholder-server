# [GPP-07] 더블 버퍼 (Double Buffer)

> 순차적으로 쌓이는 상태(state)를 "작업 중인 버전"과 "공개 버전" 두 벌로 유지해, 관찰자가 항상 완성된 스냅샷만 보도록 보장하는 패턴. 분류: Sequencing Patterns

---

## 언제 참조하나 (트리거)

- 렌더링 / 프레임버퍼 관련 코드를 작성하거나 "화면 찢김(tearing)" 문제를 분석할 때
- 같은 프레임 안에서 여러 엔터티가 서로의 상태를 읽고 쓸 때 **업데이트 순서가 결과를 바꿔버리는** 버그를 마주쳤을 때
- AI FSM 또는 행동 시뮬레이션에서 "먼저 처리된 적이 이미 갱신된 상태를 읽는" 순서 의존 버그를 디버깅할 때
- 멀티스레드 환경에서 한 스레드가 쓰는 중 다른 스레드가 읽어 partial read가 발생하는 상황을 설계할 때

---

## 핵심 내용

### 문제

컴퓨터는 명령을 순차적으로 실행하지만, 사용자(또는 다른 시스템)는 변화가 **동시에, 순간적으로** 일어난 것처럼 인지해야 한다. 대표적인 두 가지 충돌 상황:

1. **그래픽 티어링**: 디스플레이 드라이버가 픽셀을 읽는 도중에 렌더러가 같은 버퍼에 쓰면 "반은 이전 프레임, 반은 다음 프레임"이 화면에 나타난다.
2. **AI 순서 의존성**: 격투 씬에서 Harry → Baldy → Chump 순으로 업데이트할 때, Harry가 Baldy를 때리면 Baldy의 갱신된 상태를 Chump가 같은 프레임 안에 이미 읽어버린다. 처리 순서를 바꾸면 동작이 달라진다.

### 해법 구조

버퍼를 두 벌(**current**, **next**) 유지한다.

| 역할 | current 버퍼 | next 버퍼 |
|------|-------------|-----------|
| 읽기 | 외부 코드가 읽음 (완성된 상태) | 읽지 않음 |
| 쓰기 | 쓰지 않음 | 이번 프레임 수정분 누적 |
| 교환 | 프레임 끝에 **swap()** 한 번 — current ↔ next 역할 전환 |

swap은 반드시 **원자적(atomic)**이어야 한다. 교환 도중 어느 쪽도 접근할 수 없어야 한다.

### 두 가지 교환 전략

**포인터 교환 (그래픽 모델)**
- 포인터만 맞바꾸므로 O(1), 빠름
- 단, 외부 코드가 버퍼 내부 데이터를 포인터로 저장해 두면 교환 후 dangling 가능
- next 버퍼의 데이터는 "두 프레임 전" 내용이 남아 있음(프레임 1→A, 2→B, 3→A 핑퐁)

**데이터 복사 교환 (상태 복사 모델)**
- `currentSlapped_ = nextSlapped_` 처럼 값을 복사, O(n)
- 항상 "한 프레임 전" 데이터를 가짐 (더 신선)
- 비디오 드라이버처럼 고정 주소를 요구하는 경우 필수

### 분산 버퍼 최적화 (Hybrid)

엔터티마다 상태 배열 `bool slapped_[2]`를 두고, 전역 정적 인덱스 `static int current_`를 공유한다. `swap()`은 `current_ = 1 - current_` 한 줄로 모든 엔터티에 적용 — 반복문 없이 O(1).

### 언제 쓰나

다음 네 조건이 **모두** 충족될 때:

1. 상태가 점진적으로 수정된다
2. 수정 도중에 같은 상태를 접근하는 코드가 있다
3. 접근자가 진행 중인 작업을 보면 안 된다
4. 작성이 완료될 때까지 읽기를 기다리게 하고 싶지 않다

### 언제 쓰지 않나

- 메모리가 부족한 환경(임베디드·구형 콘솔): 상태를 두 벌 유지하는 비용이 금지
- 순차적이고 동시 접근이 없는 단순 시스템: 복잡도만 늘어남
- 교환 비용이 수정 비용보다 큰 경우: 성능 이점이 사라짐

**클라이언트 Prediction/Reconcile (`03_Client/`)**
- `PlayerPredictor` + `InputHistory`가 사실상 더블 버퍼 역할: "클라가 예측한 상태(next)"와 "서버 확인 상태(current)"를 분리. 서버 스냅샷 도착 시 swap(reconcile). 구조적으로 동일한 원리.

### 채택 후보

**AI 상태 동시 갱신 문제 (`02_Server/GameMap.cs`)**
- `GameMap.UpdateEnemies()`(현재 665줄 God class)는 적들이 서로를 공격하거나 플레이어를 감지할 때 **처리 순서에 따라 결과가 달라지는 버그** 잠재. 적 상태(position, HP, FSM 상태)를 더블 버퍼링하면 틱 안에서 순서 독립적 업데이트 보장.
- 지금은 단일 Enemy 목록을 직접 수정 중 — 복잡도 커지기 전에 도입 검토.

**`RemoteEntity` 보간 버퍼 (`03_Client/`)**
- 150ms 수신 버퍼가 current/next 개념을 암묵적으로 사용. 명시적 더블 버퍼 구조로 정리하면 코드 의도가 명확해짐.

### 현재 무관

- `02_Server/`의 틱 루프 내 플레이어 위치 처리: 단일 스레드 맵 Actor 구조라 동시 접근이 없고, lag compensation rewind 버퍼(4-tick ring buffer)가 역할을 이미 수행.

## 함정 / 과용 경계

- **swap 비원자성**: 교환 도중 다른 코드가 끼어들면 두 버퍼 모두 부분 상태가 됨. lock 또는 수직 블랭킹(vsync) 타이밍 필수.
- **포인터 dangling**: 포인터 교환 방식에서 외부가 버퍼 내부 주소를 캐싱하면 교환 후 쓰레기 데이터. 우리 코드에서는 `EnemyEntity` 참조를 오래 저장하지 않도록 주의.
- **핑퐁 데이터 오염**: 프레임 N에서 next 버퍼를 쓰기 전 반드시 초기화. 초기화를 빠뜨리면 두 프레임 전 잔재가 섞임 — 코미디 AI 예제의 `nextSlapped_ = false` 패턴 참고.
- **조기 도입 경계**: 동시 접근이 없는 곳에 도입하면 코드만 복잡해짐. "순서 의존 버그가 실제로 발생한 곳"에만 적용.
- **분산 swap 반복문 비용**: 엔터티가 수천 개면 swap 반복문 자체가 틱 시간을 잡아먹음. Hybrid 정적 인덱스 방식(O(1) swap)으로 해결.
