# [GPP-11] Subclass Sandbox (서브클래스 샌드박스)
> 기반 클래스가 "허가된 도구 세트"를 제공하고, 파생 클래스는 그 도구만 써서 abstract 샌드박스 메서드를 구현한다 — 파생 클래스가 외부 시스템에 직접 닿지 않도록 결합을 한 곳에 모으는 패턴.

---

## 언제 참조하나 (트리거)
- 파생 클래스가 수십~수백 개로 늘어날 때(스킬, 버프, 상태 이상, 아이템 등) 각자 엔진 시스템을 직접 콜하기 시작하면.
- 엔진 시스템(사운드·파티클·물리·네트워크)이 바뀔 때 파생 클래스 전부를 고쳐야 하는 상황이 반복될 때.
- "기반 클래스 하나 + 얕고 넓은 파생 트리" 구조를 설계할 때.
- `GameMap.ProcessAttack`, `GameMap.UpdateEnemies` 같은 게임플레이 메서드들이 다양한 공격 유형·적 AI 타입으로 분기하면서 점점 커질 때.

---

## 핵심 내용

### 문제
파생 클래스가 많으면 비슷한 코드가 반복되고, 각 파생 클래스가 오디오·파티클·물리 등 여러 엔진 시스템에 직접 의존하게 된다. 엔진 API 하나가 바뀌면 수십 개 클래스를 동시에 수정해야 하고, 동작 일관성도 깨지기 쉽다.

### 해법 구조
1. **샌드박스 메서드(Sandbox Method)**: 기반 클래스에 `protected abstract void Activate()` 같은 추상 메서드를 하나 둔다. 파생 클래스가 행동을 "채워 넣는" 유일한 장소다.
2. **제공 연산 집합(Provided Operations)**: 기반 클래스가 `protected` 비-가상 메서드들로 허용된 동작 도구를 제공한다(`Move`, `PlaySound`, `SpawnParticles` 등). 파생 클래스는 이 도구만 써야 한다.
3. **파생 클래스는 외부에 직접 접근하지 않는다**: 엔진 시스템 참조는 기반 클래스 안에만 있다.

### 결합 재분배 효과
- **제거**: 파생 클래스 ↔ 엔진 시스템 간 직접 결합.
- **집중**: 기반 클래스 ↔ 엔진 시스템 결합 한 곳으로 모임.
- **결과**: 파생 클래스는 단순·고립(수정 쉬움), 기반 클래스는 복잡(변경 시 파급 큼).

### 계층 구조 모양
"얕고 넓은(shallow but wide)" 트리: 기반 1개 + 파생 多, 깊은 다단계 상속 체인 X. 기반 클래스에 투자한 품질이 모든 파생에 즉시 적용된다.

### 제공 연산 설계 결정 3가지
| 질문 | 선택지 | 지침 |
|---|---|---|
| **어디에 넣나** | 기반 클래스 직접 메서드 vs. 위임 헬퍼 객체 반환 | 메서드가 너무 많아지면 `GetSoundPlayer()` 같이 헬퍼 객체로 위임. 헬퍼는 교체·테스트 쉬움. |
| **무엇을 제공하나** | 최소(거의 안 제공) ~ 최대(모든 것 제공) | 복수 파생 클래스가 공통으로 쓰는 것만 제공. 단일 사용 연산은 불필요한 기반 클래스 비대화. |
| **상태를 어떻게 주나** | 생성자 전달 / 2단계 init / static / Service Locator | 생성자 전달은 파생마다 파라미터가 전파되어 번거로움. 2단계 init은 까먹을 위험 → 팩토리 래핑으로 해소. static은 전역 공유 주의. |

### 취약 기반 클래스(Brittle Base Class) 위험
파생 클래스 전부가 기반에 의존하므로 기반 변경이 전파 폭이 크다. 완화책: 관련 연산을 Component/Helper 클래스로 분산(Update Method + Component 패턴 조합).

### 반대 패턴: Template Method
Template Method는 **기반 클래스가 알고리즘 골격을 갖고** 파생이 빈칸을 채운다. Subclass Sandbox는 반대로 **파생 클래스가 알고리즘 전체를 갖고** 기반이 도구를 제공한다.

### 언제 쓰지 말아야 하나
- 기반 클래스가 이미 너무 복잡할 때 — 추가 부담이 크다.
- 파생 클래스 행동이 너무 다양해서 공통 도구를 추출하기 어려울 때.
- 깊은 다단계 상속이 필요한 구조일 때 (패턴이 제안하는 것과 반대).
- 파생 종류가 계속 폭증한다면 Type Object나 데이터 드리븐 방식을 먼저 고려.

## 우리 프로젝트 적용

### 이미 사용 중 (암묵적)
- **`EnemyEntity` + `EnemyState` FSM**: `EnemyEntity`가 `Move`, `Attack`, `BroadcastPosition` 등을 제공하고 각 State(`Idle/Patrol/Chase`)가 `Update()` 샌드박스 안에서 그 메서드만 쓴다. 명시적 패턴이라기보다 자연스럽게 동일 구조.
- **`GameMap.ProcessAttack`**: 공격 유형(근접·원거리·광역)이 늘어날 때 지금은 if/switch 분기. 각 공격 타입을 `AttackBehavior`의 파생 클래스로 올리고 `Execute(GameMap context)` 샌드박스를 채우는 방식으로 확장 가능.

### 채택 후보
- **스킬/버프 시스템 (미래 M5+)**: 스킬 개수가 늘어날 때가 패턴을 적용할 시점. `SkillBase.Activate()` 샌드박스 + 기반 클래스 제공 연산(`DealDamage`, `ApplyBuff`, `SpawnEffect`)으로 스킬 파생 클래스를 격리.
- **`UnityClientSession` God class 분리 후**: 패킷 핸들러를 `PacketHandlerBase`에서 파생하는 구조로 리팩터할 때, `Send`, `Log`, `ApplyState` 같은 도구를 기반에 두면 이 패턴이 자연스럽게 적용됨.

### 현재 무관
- 서버 `02_Server/Network/` 레이어(`Session.cs`·`Listener.cs`·`Connector.cs`·`RecvBuffer.cs`·`SendBuffer.cs`): 이 수준은 파생 클래스 다양성이 없으므로 패턴 적용 불필요.

## 함정 / 과용 경계
- **기반 클래스 비대화**: 모든 편의 메서드를 기반에 욱여넣으면 God Class가 파생에서 기반으로 이동할 뿐. 제공 연산은 2개 이상 파생 클래스가 공통으로 필요한 것만.
- **깊은 파생 체인에 적용 금지**: Sandbox 패턴은 1단 파생 트리에 적합. 3단 이상이면 "어느 기반의 도구를 쓰나" 혼란.
- **샌드박스 메서드 밖에서 로직 누출 주의**: 파생 클래스가 `public`/다른 `protected` 메서드를 추가하면 결합 격리 효과가 사라짐. 파생 클래스는 `Activate()`(또는 해당 샌드박스) 하나만 채우는 규칙을 팀이 인지해야 함.
- **조기 적용 경계**: 파생 클래스가 3~4개일 때는 그냥 분기가 낫다. 10개 이상 늘어나는 확신이 생겼을 때 도입.
- **틱 루프 안에서 사용 시**: 제공 연산 내부에 `await`/`Thread.Sleep` 금지 (헌법 원칙 #5). 샌드박스 안의 행동도 비동기 블로킹 절대 X.
