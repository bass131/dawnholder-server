# [15] 서비스 로케이터 (Service Locator)
> 구체 구현을 숨기고 서비스에 전역 접근점을 제공하는 패턴 — "전역 접근은 필요하지만 구현에는 묶이고 싶지 않다"

## 언제 참조하나 (트리거)
- 오디오·로깅·랜덤 같은 "어디서나 필요한 시설"을 코드베이스 곳곳에서 직접 의존 없이 쓰고 싶을 때
- `GameMap` 또는 `GameSession`에서 특정 서비스(예: ILogger, IAudioService)를 하드코딩 없이 교체 가능하게 만들고 싶을 때
- 개발 중 실제 서비스 대신 Null/Mock/로깅 래퍼로 조용히 교체해야 할 때
- 단일 인스턴스를 보장해야 하지만 Singleton의 강한 결합이 싫을 때

## 핵심 내용

### 문제
오디오, 로깅, 메모리 할당, 난수 생성 같은 시스템은 게임 전체에서 접근이 필요하다.
콘크리트 클래스에 직접 의존하면 구현 교체 시 호출 지점이 전부 수정된다.
그렇다고 매개변수로 모두 전달하면 함수 시그니처가 폭발한다.

### 해법 구조
세 구성요소:
1. **서비스 인터페이스(Interface)**: 소비자가 아는 계약. 구현 없음.
2. **구체 서비스 제공자(Concrete Provider)**: 인터페이스를 실제로 구현.
3. **로케이터(Locator)**: 전역 정적 접근점. `GetService()` 반환 + `Register()` 등록. 제공자 정체나 획득 방식을 외부에 숨김.

소비자는 로케이터에만 의존 → 구체 제공자와 완전 분리(의존성 주입 방식으로 외부에서 등록).

### 변형 1 — Null Service(널 서비스)
서비스 미등록 시 `null` 대신 "아무것도 안 하는" Null 구현체를 반환.
→ 호출부 null 체크 불필요, 안전하게 무시. 개발 중 미완성 시스템을 조용히 우회 가능.

### 변형 2 — 로깅 데코레이터(Logging Decorator)
실제 서비스를 래핑해 호출을 기록하고 내부 제공자에게 전달.
기존 클래스 수정 없이 관측성(observability)을 추가. Decorator 패턴과 자연스럽게 조합.

### 서비스 등록 방식 세 가지
| 방식 | 장점 | 단점 |
|------|------|------|
| **런타임 외부 등록** (게임에서 가장 일반적) | 빠름, 런타임 교체 가능, 복잡한 생성자 허용 | 초기화 순서를 외부에서 관리해야 함 |
| **컴파일 타임 바인딩** (전처리기/define) | 런타임 오버헤드 0, 가용 보장 | 교체 시 재컴파일, 유연성 낮음 |
| **설정 파일 + 리플렉션** | 재컴파일 없이 구성 변경 | 런타임 비용, 구현 복잡 |

### 서비스 미등록 시 세 가지 대응
- **Assert 중단**: 즉각 오류 감지. 큰 팀에선 팀원 작업 멈춤 유발.
- **Null Service 반환**: 우아한 무시. 의도치 않은 미초기화를 숨길 위험.
- **null 반환 + 호출부 체크**: 최대 유연성. 에러 처리 로직이 분산됨.

### 언제 쓰나
- 전체 코드에서 횡단으로 사용하는 "시설"성 서비스 (오디오, 로깅)
- 공개 API에 노출하기 어색한 인프라성 객체
- 런타임에 제공자를 교체해야 하는 상황 (개발/릴리즈 빌드 분리 등)

### 언제 쓰지 않나
- 매개변수 전달이 여전히 현실적이면 그게 더 명확하다 ("Sparingly" — 저자 권고)
- 서비스 의존 체인을 투명하게 추적해야 하는 경우
- 초기화 순서 제어가 중요한 경우 (숨겨진 순서 의존이 버그 원인이 됨)

## 우리 프로젝트 적용

### 이미 사용 중
- **없음** — 현재 Dawnholder는 로케이터 패턴을 명시 사용하지 않음.
  `GameMap`·`GameSession`은 구체 클래스 직접 참조 방식.

### 채택 후보
- **서버 로깅 (M4.4 Serilog 도입 예정)**
  `ILogger` 인터페이스 + Serilog 구현체를 `ServiceLocator.Register<ILogger>(...)` 방식으로 등록하면, `GameMap`·`GameSession`·`TickScheduler` 전역에서 로케이터 경유로 호출 가능.
  Null Logger를 기본으로 두면 로그 없이도 서버가 구동됨.
- **클라이언트 오디오 서비스**
  `UnityClientSession` 내부에서 오디오를 직접 호출하는 대신, `AudioLocator.GetAudio()` 경유로 분리 가능 (Unity의 `AudioManager` 싱글톤 교체 대안).
- **개발/릴리즈 빌드 제공자 교체**
  디버그 빌드에서는 LoggingAudioService(데코레이터), 릴리즈에선 실제 AudioService 등록.

### 현재 무관
- PDL XML 직렬화, 패킷 핸들러 라우팅 — 로케이터보다 직접 등록 테이블(Dictionary)이 맞음.
- 서버 틱 루프 내부 — 틱 루프 안에서 로케이터 조회 비용이 허용되는지 측정 필요 (static 포인터 반환이면 거의 무비용).

## 함정 / 과용 경계
- **숨겨진 의존성**: 소비자 코드만 봐서는 어떤 서비스를 쓰는지 알 수 없음. 코드 리뷰·디버깅 시 흐름 추적이 어려워짐.
- **초기화 순서 버그**: 로케이터 등록 전에 호출하면 Null Service가 조용히 요청을 삼킴 → 의도치 않은 무시를 Null 전략이 숨김.
- **Singleton 냄새**: 남용하면 사실상 "전역 변수 창고"가 됨. 진짜 필요한 서비스만 등록할 것.
- **과분할 경계**: 서비스가 한 곳에서만 쓰인다면 그냥 생성자 주입이 더 명확. "어디서나 필요"가 진짜인지 먼저 확인.
- **틱 루프 내 로케이터 조회**: static 포인터 반환이면 사실상 무비용이지만, 런타임 설정 기반(리플렉션)이면 tick 안에서 호출 금지 (헌법 원칙 #5 위반 위험).

- [[14-event-queue]] — 오디오 서비스에 요청을 큐잉할 때 Event Queue와 자연스럽게 조합됨.
