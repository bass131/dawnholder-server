# [18] 오브젝트 풀 (Object Pool)
> 고정 크기 배열로 객체를 미리 할당해두고, 생성·소멸 대신 빌려주고 반납받아 재사용. 메모리 단편화와 할당 비용을 없애는 최적화 패턴.

## 언제 참조하나 (트리거)
- 매 틱/프레임마다 수십~수백 개의 객체를 생성·소멸하는 코드를 짤 때 (파티클, 발사체, 사운드 인스턴스, 팝업 UI).
- GC Spike나 힙 단편화(heap fragmentation)로 인해 frame-time이 튀는 현상을 잡아야 할 때.
- 서버 Game Loop 틱 안에서 new/delete를 피해야 할 때 (헌법 #5 No Blocking 연장선).
- 풀 오버플로 전략(조용히 실패 vs 강제 퇴출 vs 런타임 확장)을 결정해야 할 때.

## 핵심 내용

### 문제
힙 할당을 반복하면 두 가지 문제가 생긴다.

1. **단편화(fragmentation)**: free 힙이 연속 블록이 아닌 구멍들로 쪼개진다. 전체 여유 메모리가 충분해도 충분히 큰 연속 블록이 없으면 할당 실패. 게임은 수십 분 이상 돌리는 소크 테스트(soak test)를 통과해야 하므로, 드문 단편화도 장기 실행 시 시스템을 무력화할 수 있다.
2. **할당 속도**: OS 힙 할당자 호출 자체가 비결정적(non-deterministic)이고 느리다.

### 해법: 고정 배열 + free list
- 객체를 담을 **고정 크기 배열**을 미리 할당.
- 사용 중인 객체(active)와 사용 가능한 객체(available)를 구분하되, 별도 플래그 배열 없이 **unused 객체의 메모리 자체를 연결 리스트 포인터로 사용**(union trick).
- `firstAvailable_` 포인터가 free list 헤드를 가리킨다. 할당은 O(1), 반납도 O(1).

```
Union 구조 (파티클 예시):
  live 상태: x, y, xVel, yVel
  unused 상태: next (ParticlePool 안의 다음 빈 슬롯 포인터)
```
죽은 파티클의 메모리에 next 포인터를 겹쳐 쓰므로 추가 메모리 0.

### 초기화 방식 두 가지
- **풀이 직접 init**: 풀이 모든 초기화 인터페이스를 제공. 외부에 raw 포인터 노출 없음. 더 안전하나 풀 인터페이스가 비대해질 수 있음.
- **외부 init**: `Particle* p = pool.create(); if (p) p->init(x, y, vx, vy);` 구조. 풀은 슬롯만 반납. 외부 코드가 포인터를 캐싱하면 이후 재사용 시 use-after-free 버그 위험.

### 풀 오버플로 시 전략
| 전략 | 내용 | 적합 케이스 |
|------|------|-------------|
| **조용한 실패** | 풀이 꽉 차면 생성 요청 무시 | 파티클, 사운드 — 하나 빠져도 게임플레이에 영향 없음 |
| **강제 퇴출** | 가장 우선순위 낮은 기존 객체를 강제 반납 | 사운드 채널 — 가장 조용한 소리 교체 |
| **런타임 확장** | 풀을 동적으로 키우거나 overflow pool 추가 | 다만 "풀이 다시 줄어야 하나?" 정책도 함께 결정해야 함 |
| **사전 튜닝** | 레벨별 최댓값으로 풀 크기 조정 | 제일 흔한 접근; 드문 엣지케이스를 위해 항상 큰 슬롯을 낭비할 수도 있음 |

### 크기 이질성 문제
한 풀에 크기가 다른 객체를 섞으면 슬롯 크기를 가장 큰 타입에 맞춰야 해서 낭비. 해법: **타입별로 풀을 분리**. 예: 파티클 풀 / 적 풀 / 사운드 인스턴스 풀.

### 언제 쓰나
- 빈번한 생성·소멸 사이클 + 객체 크기가 균일할 때.
- GC 지원 환경(C#, Java)에서도 GC Spike가 문제될 때 (GC는 풀 안의 객체를 회수하지 않으므로 예측 가능한 메모리 유지).

### 언제 쓰지 말아야 하나
- 객체 수 상한이 없는 시나리오 — 고정 풀은 강제 상한이 됨.
- 풀 크기가 너무 크면 그만큼 메모리가 항상 점유 — 다른 용도에 쓸 메모리를 낭비.
- 풀 재사용 객체는 **자동으로 초기화되지 않는다.** 이전 생애(past life)의 데이터가 거의 맞게 남아 있어 버그를 숨길 수 있음 — `init()`에서 모든 필드를 완전히 초기화하는 규율이 필수.
- GC 환경에서 풀 안에 활성 객체가 다른 객체를 참조하고 있으면 GC가 그것들을 회수하지 못함. 반납 시 외부 참조를 null로 명시 해제해야 함.

## 우리 프로젝트 적용

**이미 사용 중 — 서버 RecvBuffer / SendBuffer**
- `02_Server/Network/RecvBuffer.cs`, `02_Server/Network/SendBuffer.cs`가 고정 크기 버퍼로 동작. 소켓 수신·송신 경로에서 byte[] 반복 할당 대신 버퍼 재사용.

**채택 후보 — 서버 파티클(발사체/히트이펙트 이벤트)**
- `02_Server/GameServer/Combat/` 에서 매 틱 공격 판정 시 HitEvent 객체를 임시 생성·소멸한다. 틱 루프 안 GC 압박 최소화를 위해 `HitEvent` 풀 또는 `struct`+`Span<T>` 스택 할당 고려 대상.
- 특히 헌법 #5 "틱 루프 블로킹 금지"와 맞닿음 — GC 트리거를 줄이는 것이 목적.

**채택 후보 — 클라 파티클 이펙트**
- Unity 클라이언트 `03_Client/`에서 공격/피격 이펙트 오브젝트가 Instantiate/Destroy 패턴으로 남아 있다면 `ObjectPool<T>` (Unity 2021+ 내장) 또는 수동 풀로 교체 고려. 프레임 스파이크 방지.

**현재 무관**
- `98_Shared/Protocol/` 패킷 클래스 — PDL 코드 생성기가 매 메시지마다 객체를 새로 만들지만 패킷 수가 적어 지금은 문제없음. 패킷 처리량이 늘면 패킷 오브젝트 풀링 검토 필요.

## 함정 / 과용 경계

- **전체 초기화 규율 누락**: 재사용 객체에 이전 상태 잔류 → "거의 맞는" 버그. `init()`에서 모든 필드 덮어쓰기를 강제하는 lint 또는 코드 리뷰 체크포인트 필요.
- **참조 유출**: 풀이 외부 init 방식일 때 외부 코드가 포인터/참조를 캐싱하면 풀이 슬롯을 재사용하는 순간 댕글링 참조 발생. 풀 관리 init 방식이 더 안전.
- **GC 참조 잔류**: C# 환경에서 풀에 담긴 객체가 다른 힙 객체를 참조하면 GC 압박이 오히려 증가. 반납(deactivate) 시 외부 참조 null 처리 의무.
- **크기 낭비 과대 단일 풀**: 모든 적·발사체·이펙트를 한 풀에 넣으면 슬롯 크기를 최대 타입 기준으로 잡아야 해서 작은 객체용 메모리가 낭비. 타입별 분리 풀이 정석.
- **조기 최적화**: 초당 수십 건 미만의 할당은 현대 .NET GC로 충분히 처리 가능. 먼저 프로파일러로 실측하고 풀 도입.
- **풀 크기 고정 vs 확장 정책 미결**: 확장 풀은 피크 시 메모리를 잡아먹고 수축 정책이 없으면 영구 점유. 최댓값을 명시적으로 정하고 레벨별 튜닝 또는 오버플로 전략을 문서화.
