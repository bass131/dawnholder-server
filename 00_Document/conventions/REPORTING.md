# 보고서 작성 기준

역할과 모델 라우팅은 [AGENTS](../../AGENTS.md#모델-라우팅)를 따른다. 보고서 자료·HTML 구성·전용 생성 스크립트는 Astra가 작성하고 별도 Opus 검증자가 검토하며, 메인 Claude가 사용자 최종 보고를 전달한다. 작은 변경은 짧게 보고하며 모든 작업에 대형 HTML을 의무화하지 않는다.

## 사용자 최종 보고 형식

형식은 [AGENTS의 메시지와 보고](../../AGENTS.md#메시지와-보고)를 따른다. 아래 설명 기준은 필요한 세부 항목을 고르는 데 적용하며 고정 분량이나 별도 장을 추가하는 의무가 아니다.

Astra→메인 보고는 변경 요약·검증 근거 위치·리스크·결정 요청·판정 원문 경로를 유지한다. 사용자 최종 보고와 판정 원문을 같은 산출물로 취급하지 않는다.

작업·PR·안건·관찰·결함을 부를 때는 **`번호 - 작업내용`**으로 쓴다(예: `PR168 - 목표 전 후보와 재개 진입 정비`). 번호만으로 작업을 대신하지 않으며 다시 언급할 때도 짧은 작업 설명을 붙인다. 운영툴 기록의 제목·본문과 사용자 보고는 목적을 드러내는 이름을 쓰고 D1·M-2 같은 내부 마일스톤 코드를 단독 제목으로 쓰지 않는다. 역사 코드나 외부 계약 이름을 무관하게 일괄 변경하는 규칙은 아니다. 제품·도구 파일의 배치/이름은 [CODE_CONVENTION](CODE_CONVENTION.md#파일-위치와-이름)을 따른다.

## 먼저 확인할 문맥

- 현재 goal과 정확한 branch/head, 구현·검증·병합 상태를 확인한다. 관련된 직전 보고서와 goal의 필요한 결과 부분만 읽는다. 전체 과거 대화·소스·로그를 다시 모으지 않는다.
- 이전 완료 성과, 이번에 바뀐 것, 이번에 실제 다시 검증한 것, 아직 남은 것을 구분한다. 과거 완료를 미합의·미착수로 되돌리거나 과거 실행을 이번 실행으로 재사용하지 않는다.
- 보고서는 시점이 있는 설명용 산출물이다. 상태·결정·결과의 원본은 goal이며 보고서에 상태 스냅샷 시각과 고정 근거를 연결한다. 작성 모델은 지정과 실제 확인 여부를 구분한다.

## 독자가 판단할 수 있는 설명

규모에 맞춰 다음 질문에 답한다. 단순히 절 제목을 채우거나 로그·테스트 수를 늘려 분량을 만들지 않는다.

1. **무엇이 달라졌는가:** 사용자가 체감하거나 다음 변경에서 달라지는 결과와 현재 완료 상태를 먼저 설명한다.
2. **왜 문제였는가:** 실제 변경 이유의 분산·상태 소유·실패 경로·숨은 입력을 파일·메서드·구체 시나리오로 짚는다. 구조 개선과 재현된 결함 수정을 구분한다.
3. **왜 이 경계인가:** 선택한 책임·의존 방향, 검토한 대안과 대가, 유지한 기존 구조의 이유를 설명한다. 당시 기록과 후속 설계 해석, 계측 결과를 구분한다.
4. **어떻게 동작하는가:** 필요한 경우 전후 상태 소유와 호출 흐름을 비교한다. 패킷 순서·callback 시점·실패·종료 같은 보존 계약을 보인다. 개념도와 실제 실행 trace를 구분한다.
5. **코드에서 무엇을 보면 되는가:** 대표 실제 diff를 짧게 골라 어떤 책임이 어디로 이동했는지 해설한다. 정확한 base/head와 전체 diff·소스 링크를 함께 제공한다. 삭제된 코드가 다른 소유자로 이동한 것인지 기능 제거인지 명시한다.
6. **무엇으로 확인했는가:** 테스트의 입력·관찰·잡아내는 회귀를 설명한다. 기준선에서도 통과한 동작 보존과 기준선에서는 실패한 오류 검출을 구분한다. 빌드·단위/통합·Unity EditMode/PlayMode·실제 서버·사람의 플레이·DB 실행을 합치지 않는다.
7. **어디까지 믿을 수 있는가:** 남은 결합·미실행 경로·측정 한계와 영향, 다음 결정·작업의 기존 합의 여부를 기록한다.

AI 평가나 구조 수치는 대상·기준선/변경 후 commit·과제·방법·환경·노출 조건을 명시한다. 이전 평가가 있으면 연결하고 이번에 재평가했는지 밝힌다. 테스트 건수나 답안 적합도 점수를 전체 코드 품질·생산성·인과적 개선율로 바꾸지 않는다.

## HTML 구성

- 첫 화면에는 핵심 결론과 이번 결과를, 본문에는 단계별 설계 판단을 둔다. 상세 PR/head·명령·원시 근거는 필요한 위치 또는 기술 부록에 연결한다.
- 요약·단계 카드·전후 흐름·선택 비교·짧은 코드 해설로 읽기 위계를 만든다. 긴 문단과 큰 원시 diff만 나열하지 않는다. 중요한 결론을 펼침 영역 안에만 숨기지 않는다.
- diff는 실제 고정 Git 결과를 escape해서 표시한다. 추가·삭제는 색과 `+`/`-` 기호로 함께 구분하고 대표 구간과 전체 변경의 관계를 설명한다. 도식·의사 코드를 실제 diff처럼 제시하지 않는다.
- 목차·근거 링크·좁은 화면의 표/코드 스크롤을 제공한다. 테마·인쇄 같은 기능을 추가하면 실제 동작도 검증한다. 외부 서비스나 라이브러리 없이 로컬에서 읽을 수 있는 구성을 우선한다.
- 파일 크기·문장 수·장식 수를 품질 기준으로 삼지 않는다. 독자가 변경 이유와 검증 한계를 빠르게 찾을 수 있는지로 검토한다.

## 전달 전 독립 확인

작성자의 쓰기 종료 후 별도 Opus 검증자가 canonical 상태·고정 diff·수치·테스트명·이전/이번 실적 구분과 상대 링크를 확인한다. HTML은 실제 렌더에서 데스크톱과 좁은 화면, 목차·표·diff, 추가한 테마·인쇄 동작을 검증한다. 문서 변경만으로 게임 테스트를 다시 실행하지 않는다.

내용 오류는 작성자에게 돌리고 파일 소유권을 명시한다. 마지막 정정 뒤 정확한 산출물과 검증 근거를 연결한다. 보고서 완성과 사용자 병합 승인·main 통합을 구분한다.

참고 형식은 [M0–M3 보고서](../../01_Phases/reports/2026-09-29-refactor-before-persistence/report.html)다. 보고서의 과거 수치·권한·완료 상태는 템플릿으로 복사하지 않는다.
