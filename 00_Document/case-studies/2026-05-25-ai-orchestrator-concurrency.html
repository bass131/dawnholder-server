Capstone Methodology · Case Study

AI를 조율자로 — 자율주행이 아니라

한 동시성(concurrency) 설계 결정에서, 인간의 비판적 개입이 AI의 과대-단정을 어떻게 교정했는가

프로젝트: Dawnholder (2D MMORPG) 맥락: M4.2 Phase 03 — 맵 전환 migration 2026-05-25
"AI에게 전권을 위임하는 것이 아니라, AI를 조율자(orchestrator)로 운용한다."
AI는 빠르게 코드를 생산하고 그럴듯한 근거를 댄다. 하지만 스스로 확신에 차 단정할 때가 있고, 그 단정이 오버엔지니어링이나 가짜 안심으로 흐를 수 있다. 이 문서는 그 순간 인간이 "정말 맞아?"를 두 번 던져 AI를 코드 사실 규명으로 끌고 가, 결국 더 단순하고 정확한 결론에 도달한 실제 대화를 박제한다.

0. 무대 — 무엇을 결정하던 중이었나

서버가 플레이어를 한 맵에서 다른 맵으로 옮기는 migration 로직을 막 구현한 직후였다. 자동 리뷰(reviewer 에이전트)가 🟡 경고 하나를 냈다: GameSession._currentMapId 필드가 여러 스레드에서 접근되는데 Volatile 보호가 없다는 것. AI(나)는 이 경고에 대한 해법을 사용자에게 설명하기 시작했다.

1. 대화의 궤적

AI · 첫 제안
"이 문제의 정답은 두 상태(_currentMapId + _migrating)를 단일 int로 합치는 것이에요." 과대-단정
— 리뷰어가 권한 건 "Volatile로 바꿔라" 정도였는데, AI는 더 큰 리팩토링을 "정답"이라 단정했다.
인간 · 개입 ①
"Volatile로 한다고 무조건 안전하게 잡히는 게 아니잖아. 좀 더 Atomic하게 처리하는 게 제일 안전할 것 같은데." 개념 검증
AI · 1차 정정
"맞아요 — Volatile ≠ Atomic. 다만 이 변수는 RMW(읽고-수정-쓰기)가 아니라 단일 writer라 Volatile로 충분하고… 제가 '단일 int 합치기가 정답'이라 단정한 건 과했어요. 그리고 진짜 안전망은 그 변수가 아니라 EnqueueJob 직렬화예요." 과대 1차 인정
인간 · 개입 ②
"이상한데… 정말 그게 맞아?" 직관적 불신
— 한 번의 정정으로 만족하지 않고, 설명 자체가 아직 미심쩍다는 신호를 보냈다.
인간 · 핵심 통찰
"서로 다른 비동기 스레드가 결국 그 변수를 읽거나 쓴다면 나는 Atomic한 과정이 필요하다고 생각하고, 그게 아니면 lock-free로 가도 상관없을 거란 가정이야. 근데 문제는 코드 작성을 AI인 네가 한 거라 그 부분이 확인이 안 돼서 — 블랙박스가 돼버렸기 때문이야." 판단 기준 + 신뢰 문제 분리
AI · 사실 규명
"추측을 멈추고 실제 호출 경로를 코드로 추적하겠습니다." → 멀티스레드 접근을 사실로 확정하고, 그 사실에 기준을 적용해 정확한 결론(Volatile, Interlocked 아님)에 도달. 블랙박스 해제

2. 블랙박스를 연 결과 — 코드가 말한 사실

AI가 추측 대신 호출 경로를 끝까지 추적하자, 다음이 사실로 확정됐다.

// 읽기 = socket 스레드
[socket]  패킷 도착 → SubmitMoveIntent / SubmitAttack / SubmitEnterPortal
            └─ GetMap()  // 여기서 _migrating · _currentMapId 를 읽음
            └─ map.EnqueueJob(람다)  // 실제 작업은 큐에 넣기만

// 쓰기 = tick 스레드 (단일 LongRunning Task)
[tick]    TickScheduler → EnqueueJob 람다 실행
            └─ migration: _currentMapId = dest;  Volatile.Write(_migrating, 0);
변수읽기 스레드쓰기 스레드RMW?필요한 보장
_migratingsockettick아니오 (단일 writer)Volatile ✓ (이미 적용)
_currentMapIdsockettick아니오 (단일 writer)Volatile ✗ → 보강 필요
인간의 기준이 옳았다
"서로 다른 스레드가 접근하면 동기화가 필요하다" — 호출 경로가 이를 사실로 입증했다. 다만 정밀하게는 RMW가 아니라 단일 writer + 단일 워드(int/enum)이므로, Atomic(Interlocked)이 아니라 가시성만 보장하는 Volatile이 정답이었다. (Interlocked는 entity id 발급(++) 같은 진짜 RMW에만 필요.)

3. AI 단독이었다면 vs 조율했을 때

✗ AI에게 전권 위임했다면

  • "단일 int 합치기"라는 오버엔지니어링을 정답으로 박았을 것
  • 혹은 리뷰어 경고를 가볍게 넘겨 plain 필드를 그대로 방치 (x86에서 테스트 통과 → 가짜 안심)
  • "블랙박스" 상태로 커밋 — 다음 사람이 호출 경로를 다시 추적해야 함

✓ 인간이 조율자로 개입했을 때

  • 과대-단정을 두 번의 "정말 맞아?"로 교정
  • 판단 기준(멀티스레드↔atomic)을 인간이 제시 → AI가 사실 규명으로 응답
  • 결론: 가장 단순하고 정확한 해법(Volatile) + 동시성 가정을 주석/테스트로 박제

4. 테스트의 본질적 한계 — 정직하게

"그럼 테스트로 가려낼 수 있나?"라는 물음에 대한 정직한 답: 메모리 가시성 버그는 테스트로 "없음"을 증명할 수 없다.

  • x86 CPU는 strong memory model이라 plain 변수도 거의 안 깨진다 → 테스트가 통과해버린다 (가짜 안심).
  • 그러나 ARM(weak model, 예: 클라우드 ARM 서버)에선 같은 코드가 깨질 수 있다.
  • 따라서 가시성은 테스트가 아니라 정적 보장(호출 경로 확정 → Volatile)으로 잡는다.
  • 테스트가 잡을 수 있는 건 race의 기능적 결과(이동 중 패킷이 버려지나, 이동 중 끊김에 유령 캐릭터가 남나) — 이는 결정론적 인터리빙 테스트로 검증한다.

5. 방법론으로 일반화

  1. AI의 "정답"은 가설로 받는다. 확신에 찬 단정일수록 한 번 더 의심한다.
  2. 판단 기준은 인간이 쥔다. "멀티스레드면 동기화" 같은 원칙을 인간이 제시하면, AI는 그 기준에 맞춰 사실을 규명한다.
  3. 블랙박스를 강제로 연다. "코드가 실제로 어떻게 동작하는지" 호출 경로를 사실로 요구한다 — AI의 설명이 아니라 코드를.
  4. 한 번의 정정에 만족하지 않는다. 이 사례에서 결정적 교정은 두 번째 "이상한데"에서 나왔다.
  5. AI에게 정직한 한계를 말하게 한다. "테스트로 없음을 증명 못 한다"는 한계를 드러내는 것이 가짜 안심보다 안전하다.
결론
AI는 이 대화에서 두 번 틀렸고("단일 int 정답", 진짜 안전망 오인) 두 번 교정됐다. 교정의 동력은 더 똑똑한 AI가 아니라 "정말 맞아?"를 멈추지 않은 인간이었다. 이것이 자율주행(autopilot)과 조율(orchestration)의 차이다 — 핸들은 인간이 쥐고, AI는 빠른 엔진이다.
