### 우선순위 검토 영역 3개

**[A] Phase 03 — "옵션 B 변형 third path" 헌법 #4 동등 보호 판정**

상황: Phase 정의에는 **옵션 A**(`98_Shared/Network/FrameValidator.cs` 단일 helper 신설)가 권장으로 적혀 있었어. 하지만 `02_Server/Network/Session.cs:23-25`에 박힌 옛 사유 주석을 발견했지 — "ServerCore는 의도적으로 Shared 참조 X(재사용성) — 두 파일 동시 변경 컨벤션으로 처리". 이 정신을 보존하려고 사용자가 **옵션 B 변형**으로 결정했어:

- `02_Server/Network/FrameValidator.cs` 신설 (서버 측, 50 lines)
- `04_ClientNet/FrameValidator.cs` 신설 (클라 측, 73 lines)
- 두 helper 같은 시그니처(`TryValidateFrameHeader(ushort, out string?)`) + 같은 상수(`MinFrameSize=4`, `MaxFrameSize=4096`)
- 양쪽 파일 상단에 cross-reference 주석으로 동기화 약속 명시
- drift guard 테스트 2건(`MaxFrameSize_MatchesSharedConstants_DriftGuard` + `PacketSession_Constants_DelegateToFrameValidator`)으로 commit 시점 자동 검출

내 판정은 "정합"이었어 — drift guard와 cross-reference 주석이 헌법 #4 "복사-붙여넣기 금지" 정신의 *동등 보호*를 제공한다고 봤거든. 그리고 이 패턴이 "공유 vs 분리 갈래의 third path"로 일반화 가능한 학습 자산이라고 사용자한테 ★★★ 어필 키워드로 박아줬어. 그런데 솔직히 이게 *진짜* 동등 보호인지, 아니면 내가 사용자 결정을 사후 정당화하는 가짜 학습 자산 박은 건지 외부 시각이 필요해.

확인해줄 것:
1. 옵션 B 변형이 헌법 #4 정신과 동등 보호인지, 아니면 그냥 *코드 중복의 정당화 시도*인지.
2. ServerCore 재사용성(ADR-012 Y2 분리)과 헌법 #4 사이의 third path로 일반화 가능한 패턴인지, 아니면 옛 사고 패턴 잠복이나 over-engineering인지.
3. 한국 게임 회사 백엔드 면접에서 "헌법 #4 vs 모듈 재사용성 갈등" 답변으로 어필 가치가 진짜 있는지, 아니면 면접관 입장에서 "왜 처음부터 shared 안 박았어요?" 가 자연스러운 반응인지.

**[B] Phase 04 — Deterministic build 정합**

문제: `dotnet build`가 매번 Unity Plugins/Shared.dll을 dirty로 만들어서 git status에 노이즈가 누적되고 의도치 않은 commit 위험이 있었어.

내가 짚은 원인: `<EmbedAllSources>true</EmbedAllSources>` + `<DebugType>embedded</DebugType>` 조합이 절대 경로/timestamp를 dll에 임베드 → 매 빌드 hash가 달라짐 → PostBuild의 `SkipUnchangedFiles="true"`가 항상 실패 → 매번 복사.

봉합:
```xml
<Deterministic>true</Deterministic>
<PathMap>$(MSBuildThisFileDirectory)=/_/</PathMap>
```
양쪽 csproj(`98_Shared/Shared.csproj` + `04_ClientNet/Dawnholder.Client.Net.csproj`)에 동일하게 박음.

검증: 본 머신에서 `dotnet build Dawnholder.slnx` 5회 연속 → 1회차 후 baseline과 5회차 후 git status가 정확히 동일. 추가 dirty 없음.

확인해줄 것:
1. `<PathMap>$(MSBuildThisFileDirectory)=/_/</PathMap>` 형식이 MS 가이드에 정합한지 — 일반적인 reproducible build 패턴에서는 솔루션 루트를 잡아야 하는지, 아니면 csproj 단위로 잡는 게 맞는지.
2. 다른 머신(팀원 정유현/인규, 또는 향후 CI/CD 환경)에서 *진짜로 같은 hash*가 나올 가능성 — 본 검증은 같은 머신 5회 한정이라 cross-machine 확신이 부족해.
3. `EmbedAllSources` + `DebugType=embedded` + `Deterministic` 세 옵션 결합에 알려진 함정이나 trade-off가 있는지 — 임베드된 소스가 deterministic을 깨는 케이스 등.

**[C] Phase 02 — Event-based race elimination 정합**

상황: 옛 클라이언트가 캐릭터 선택 후 `C_CharacterSelect`를 보낼 때 폴링 또는 timing-based 방식을 썼는데 이게 race window를 만들었어. 새 구현은 캐릭터 선택 UI 이벤트에 핸들러 직접 등록해서 *event-driven*으로 송신.

서버 측 상태 머신: `_handshakeCompleted` + `_characterSelected` flag 2개. 핸들러 진입 시점에 두 flag 단계별로 점검해서 잘못된 순서의 패킷을 fail-closed disconnect.

확인해줄 것:
1. event-based 송신이 race를 진짜 차단하는지, 아니면 또 다른 race가 잠복(같은 event 두 번 fire / event handler 잔재 / Unity main thread vs socket worker thread 충돌)하는지.
2. 서버 측 flag 2개 패턴이 4번째 flag 추가 시점에 **enum 응집으로 리팩터링** 권장으로 박혀 있어(Rule of Three 정신). 이 cadence가 적절한지, 아니면 지금 시점에 이미 enum이 맞는지.
