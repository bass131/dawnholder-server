⚖️ Trade-off 상세

Plan A (Y2 분리) — 장단점

장점 ✅단점 ❌
• 환경별 최적화 자유 (이론상)
• 한쪽 변경이 반대편 빌드 즉시 안 깸
• Mirror / FishNet 같은 현업 솔루션 패턴 일관
• Phase 03~05에서 이미 짠 코드 그대로 유지
• "socket을 클라 입장에서 한 번 짜본" 학습 임팩트 (그러나 이미 박힘 — Plan B로 가도 보존) 		• 같은 코드 두 벌 (SendBuffer/RecvBuffer 거의 동일)
• 양쪽 동기화 책임 (수동, 잊으면 어긋남)
• 분리 가치 검증 안 됨 — 환경별 차이가 *코드에 박힌* 사례 0
• 새 socket 기능 추가 시 양쪽 작성
• "왜 두 벌인가" 매번 설명 부담
• 헌법 #4 "복사-붙여넣기 금지" 정신과 살짝 충돌

Plan B (책임 단위 분리) — 장단점

장점 ✅단점 ❌
• 코드 두 벌 → 한 벌 (헌법 #4 강화)
• socket 학습 한 번만 짜면 끝
• Shared의 정의("양쪽 동기 필수 cross-cutting")와 부합
• 새 기능 추가 시 한 곳만
• 면접 답변 강력:
"처음엔 Y2 분리 채택, 코드 두 벌 작성하며 분리 가치가 검증되지 않음을 발견. 책임 단위 분리로 정제. 결정을 지속 재검증하는 사고."
• 환경 차이 = 핸들러에서만이라는 깔끔한 원칙 		• Phase 03~05 일부 작업이 *재구성 대상* (sunk cost)
• ADR-012 → ADR-013 정제 (10분)
• 04_ClientNet/ 폴더 통째 이동/제거
• 미래 진짜 환경 차이 발생 시 다시 분리 가능성 (왔다갔다 위험)
• Mirror/FishNet 같은 현업 패턴과 약간 다름 (그러나 gRPC는 통합 패턴)

💡 권장 + 솔직한 자기 분석

권장 = Plan B (책임 단위)

핵심 사유:

  • 분리 가치 검증 0: Plan A의 socket 코어 분리는 *환경별 최적화 자유*를 사유로 박혔지만, 실제 코드에서 그 자유가 *발현된 사례 0*. SendBuffer/RecvBuffer는 *완전 동일 코드*.
  • 면접 임팩트가 더 강함: "결정을 굳히지 않고 지속 재검증" = 시니어 사고 시연.
  • 변경 비용 ~2h, ADR-013 정제 ~10분. 한 Phase 안에 들어감.
  • 미래에 *진짜 환경 차이*가 발현되면 그때 다시 분리. 단 *그때까지 sunk cost 없음*.

⚠️ AI 자기 분석 — 왜 Plan A를 처음 추천했나

(솔직히 까보면)

  • ADR-012를 권위로 받아들임 — 6일 전 결정을 *고정된 진실*로 가정. ADR 자체는 *trade-off 명시 + 변경 가능*이 본질인데.
  • Sunk cost — Phase 03~05의 04_ClientNet 신작 작업을 *무효화하기 싫음*.
  • 깊은 재검토 부담 회피 — *작은 변경(③ 책임 단위)*으로 *진짜 문제(분리 자체의 정당성)*를 우회.

이 셋 모두 합리적 사유 아닌 심리적 관성. 시니어 사고는 결정을 지속 재검증하는 것. 사용자가 그걸 짚어준 게 AI의 사고 부족을 드러냄.
