## 순서와 첫 범위

사용자는 **개발 기록 공동 조회 → 서버 등록·로그 조회** 순서에 동의했다. 사람은 운영툴 화면을, Game Dev/Management 에이전트는 화면 없이 같은 자료를 읽는다. 두 세션의 조회 권한은 같고 쓰기·서버 조작 권한은 별도로 다룬다.

첫 구현 설계는 로컬 stdio MCP와 공통 조회 모듈이다. 클라이언트가 소유하는 프로세스가 기존 catalog를 읽어 앱 종료와 독립시킨다. Game Dev도 회신 msg_3187ffc08f9d에서 이 범위를 확인했다. 실제 클라이언트 연결 여부는 검증 결과와 구분하고 전역 설정을 바꾸지 않는다. HTTP·관리백엔드 구축 없이 프로젝트 실행 명령/연결 예시부터 제공하는 범위다.

## 공동 조회 완료조건

1. 목록/검색 → 시스템 요약 → 관련 변경·결정·검증·계획과 근거 메타데이터 순서로 필요한 내용만 읽는다. 안정된 시스템/기록/출처 ID로 연결한다.
2. 응답은 catalog hash·revision·asOf·source commit을 담는다. UI와 에이전트가 같은 원본을 읽으며 과거 기록을 최신 게임 상태로 표시하지 않는다.
3. 한 요청은 검증된 단일 버전을 사용한다. 요청 사이의 변경을 식별하고 이전 버전을 요구한 요청에 최신 내용을 조용히 섞지 않는다. 파일 변경은 다음 조회에서 재빌드 없이 읽는다.
4. 검색어/ID/페이지·응답량을 제한한다. 누락·손상·끊긴 참조를 명시적으로 반환하고 미조회 원문을 읽었다고 말하지 않는다. 쓰기·서버 제어·shell·임의 파일 경로/URL 읽기는 노출하지 않는다.
5. 앱을 켜지 않고 실제 MCP client의 초기화·목록·읽기·검색·종료와 두 client의 같은 자료 조회를 독립 검증한다. 오류·버전 변경·읽기 전용 보존 및 기존 UI/저장의 영향 회귀를 확인한다. 시험 client와 실제 두 개발 세션 연결 성공은 구분한다.

구현 소유는 Sol6.1의 05 MCP/조회·필요한 공통 계약·프로젝트 설정, 테스트/하니스는 독립 Astra, goal·결정·보고는 메인 Astra다. 실제 모델 확인 불가는 unknown, 새 CLI는 --no-daemon이다. 초안 승인 자동화·폼 UI·새 하위 문서 저장 체계는 첫 조회 구현의 완료로 주장하지 않는다.

## 기록 작성·수정 원칙

- 에이전트 초안 → 담당 메인 검토 → 정식 반영. 같은 작업/PR/검증은 기존 ID를 찾아 연결하고 여러 시스템에서 공유 참조한다.
- 사실에는 코드 버전/PR/로그/검증 근거를 연결한다. 계획·추정·구현·검증을 구분하며 근거가 부족하면 미확인으로 남긴다. 링크 존재만으로 진실성을 자동 보장하지 않는다.
- 기존 기록과 충돌하면 자동 덮어쓰지 않는다. 현재 요약은 갱신하되 이전 내용·변경 이유·근거를 이력으로 보존한다.
- 긴 과거 설명은 ID·시점·출처가 있는 하위 문서로 연결한다. 요약부터 읽고 필요한 상세만 추가로 가져온다.

## 서버 등록·로그 합의

- 가동 시 서버 정보와 로그 읽는 방법을 등록한다. 영구 serverId와 실행마다 다른 runId를 구별하고 등록/실행정보는 JSON으로 보관한다. 저장된 정보만으로 현재 실행 중이라고 판단하지 않는다.
- 실제 로그는 기존 원본을 우선 활용한다. 새 형식이 필요할 때 JSONL을 추천 후보로 검토하고 CSV는 내보내기 용도로 둔다.
- 기본 조회는 현재 운영 서버 최근 10분, 오류·경고 중심 요약과 필요한 주변 일반 로그다. 서버/실행/시간대/근거와 확인하지 못한 구간을 함께 표시한다. 읽기 실패는 오류 없음이 아니다.
- 일반 로그는 서버당 최대 7일·최대 1GB, 둘 중 하나라도 넘으면 오래된 순으로 정리한다. 실제 남은 기간과 삭제된 구간을 표시한다. 조사 근거로 별도 보존한 로그는 일반 자동 정리에서 제외한다.
- 등록·조회는 화면과 독립적인 운영백엔드의 후속 책임이며 이번 개발 기록 MCP가 서버 운영백엔드까지 구현한다는 뜻은 아니다. 서버 시작/종료·DB 저장·3D는 이 범위의 완료로 주장하지 않는다.
