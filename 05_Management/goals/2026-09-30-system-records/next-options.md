# PR147 이후 작은 설계 선택지

2026-09-30 논의안. 새 목표·구현 승인이 아니다. 현재 실적·병합 상태는 [goal](goal.md), 기존 요구·결정은 [requirements](../../requirements.md)와 [decisions](../../decisions.md)가 원본이다.

## 공통 전제

합의된 방향은 사람과 에이전트가 같은 근거를 읽고, 실행 중 기록을 설정하며, 창과 서버 운영의 수명을 분리하는 것이다. React/Electron과 WSL ASP.NET Core는 채택했다. 기록의 현재 구현은 로컬 JSON과 Electron 읽기/저장이다. API/MCP, 항목별 폼, 관리백엔드·서버 제어는 아직 구현되지 않았다.

catalog는 시스템/공통 기록/출처 ID와 기준시점·revision·hash를 유지한다. Game Dev의 규칙·기술 계약·진행 goal/CURRENT를 복제 정본으로 만들지 않는다. 조회한 자료는 맥락이며 새 실행 권한이나 최신 게임 상태를 뜻하지 않는다.

## A. 조회 경계 후보

화면과 에이전트가 공유하는 논리적 조회 계약을 먼저 정한다. `listSystems`, `getSystem(id)`, `getRecord(id)`, `getSource(id)`를 후보로 두며 응답에 catalog hash·revision·asOf와 근거 가용성을 포함한다. 이름은 설계 후보이고 새 HTTP API가 존재한다는 뜻은 아니다. 검색은 결과 수·응답 크기를 제한하고 관련 기록의 버전을 섞지 않는다.

첫 MCP는 로컬 stdio에서 이 조회 계약을 노출하는 후보를 추천한다. 사용자 앱과 에이전트가 같은 검증된 파일을 읽고 앱 종료와 독립적으로 조회할 수 있다. 프로세스 수명은 연결 클라이언트가 소유한다. WSL 운영백엔드와 결합하지 않아도 되는 범위다. HTTP 공동 서비스가 필요해지면 loopback 바인딩·인증·Origin 검증·Windows/WSL 노출 시험을 별도 설계한다. stdio 채택도 아직 사용자 결정 전이다.

MCP는 안정된 시스템/기록 ID의 resources/list·resources/read를 후보로 삼고 필요할 때 읽기 전용 검색 도구를 더한다. 임의 파일 경로·shell·URL fetch·catalog 저장·서버 제어를 받지 않는다. 로컬 근거 본문은 첫 단계에서 자동 수집하지 않고 출처 메타데이터를 반환한다. 손상/누락은 명시적으로 실패시키며 조용히 다른 버전으로 바꾸지 않는다. 이는 MCP Resources의 URI 기반 맥락 제공 방식을 적용한 설계 제안이다. [공식 Resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources), [Transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## B. 폼 편집 후보

원본을 별도 DB로 옮기지 않고 기존 catalog에 저장한다. 시스템·기록·출처를 구분해 한 항목씩 편집하며 ID 변경과 참조 대상 삭제는 첫 범위에서 제외하는 안을 추천한다. 내용의 사실성/상태 변경은 사람이 판단하고, 프로그램은 필수값·ID 참조·충돌을 검증한다. 현재 JSON 편집은 고급 편집으로 유지할 수 있다. 변경 이유와 검증 근거를 입력하게 하는 범위는 사용자와 정한다.

## C. 서버 권한·수명 후보

R-02/04/05/06/07에 따라 단일 로컬 서버, 화면과 운영 수명 분리, 제한 재시작, PC 재부팅 후 수동 라이브 시작, 저장완료 뒤 정상 종료, 개발/라이브 버전 분리는 기존 합의다. 정확한 인증·자동복구 한도·로그 정책·백엔드 자동시작은 미합의다.

운영백엔드는 등록된 서버 ID→승인된 배포/실행 경로를 해석하고 실행 세대와 PID를 함께 관리하는 후보를 둔다. 임의 PID·shell 명령 제어를 받지 않는다. 상태는 프로세스 존재/응답 가능/접속 수락/저장 중/정상 종료를 구분한다. 로그는 등록된 스트림과 cursor/최대량으로 조회하며 파일 경로 전체 권한으로 확대하지 않는다. 창 X와 명시 앱 종료가 서버를 종료시키지 않는 기존 계약을 유지한다.

실제 정상 종료 제어는 GameServer 저장/복원과 flush 완료·실패 응답 계약이 선행돼야 한다. timeout/저장 실패를 종료 성공으로 바꾸거나 자동 강제종료·예약 재시작하지 않는다. ASP.NET Core의 StopAsync 수명 훅은 비정상 종료 시 호출이 보장되지 않으므로 게임 저장완료의 증거를 대신할 수 없다. [공식 hosted services 수명 설명](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0).

## 추천 순서와 결정 질문

기록 맥락 공유를 먼저 완성한다면 **PR147 병합 판단 → A 읽기 전용 조회 → B 폼 편집 → C 상태·로그 읽기 → 저장 계약 준비 후 실행/종료 제어**를 추천한다. A/B는 GameServer 저장 기능에 의존하지 않고 서로 구현상 독립이다. 기존 라이브 운영 우선순위(R-01)를 더 급하게 적용한다면 C의 상태·로그 읽기를 앞당길 수 있다. 이 순서는 추천이며 기존 사용자 우선순위를 새로 확정한 것이 아니다.

첫 논의에서는 다음 하나만 고르면 된다: 에이전트 공동 조회, 사람의 기록 편집, 서버 상태·로그 읽기 중 당장 가장 필요한 것이 무엇인가. 선택 뒤 A라면 앱 종료 중 조회와 첫 클라이언트, B라면 기존 항목 수정/추가 범위, C라면 첫 서버 식별·로그 원본과 읽기 권한부터 확정한다. Three.js와 자동 수집·기록 정본 전환은 이 세 선택지의 첫 범위에 포함하지 않는다.
