# Game Dev ↔ Management 기록 이주 협의안

## 사용자 요청과 이 문서의 목적

2026-09-30 사용자: “OK 전체적으로 그럼 이주를 시작해볼까 메인 게임 개발 세션에 이 맥락 한번 의논해서 전달해볼래?, 우리 세션이 단독으로 해서는 안되는 이야기 인거 같아서”.

사용자는 아래 전체 방향을 받아들이고 이주를 위한 공동 협의를 요청했다. 구체적 정본 전환·저장 구현·공통 운영 규칙 변경은 양쪽 메인이 먼저 맞춘다. 이 문서는 검토 요청이며 전달·수신·합의 완료 증거가 아니다. 현재 작업 상태의 원본은 [goal.md](goal.md)다.

## 논의한 방향

- Management를 사람과 에이전트가 “무엇을 만들었고, 왜 구축했으며, 어떤 검증을 했는가”를 조회하는 공통 진입점으로 만든다.
- 게임 프로젝트에는 작업 규칙·규율·실행 방법을 중심으로 남기고 운영툴에서도 해당 원문을 참조한다. 코드·PDL·스키마·실행 가능한 테스트와 코드 버전에 밀접한 계약은 게임 저장소에 유지하는 예외를 제안한다.
- 시스템의 현재 설명과 변경 이력을 연결한다. 기록 유형은 시스템, 변경, 결정, 검증, 계획으로 나눈다. 관련 시스템은 안정된 ID로 연결하고, 하나의 변경이 여러 시스템에 걸칠 수 있다.
- 구현·검증·병합·배포 상태를 별도로 다룬다. 계획을 실적으로, 과거 검증을 현재 코드 검증으로 표시하지 않는다.
- 향후 에이전트는 운영툴과 같은 기록을 API/MCP로 조회한다. 규칙 참조·해당 시스템·관련 결정·변경·검증·미해결 사항을 필요한 범위로 반환한다. 기록 조회가 게임 조작 권한을 부여하지 않는다.
- Three.js 시스템 지도는 같은 시스템/관계 데이터를 사용하는 표현 방식의 후보다. 계층 탐색·노드 상세·관계 필터·선택한 처리 흐름을 보여준다. 설계 흐름과 실제 관측은 구분한다. 라이브 계측과 3D 구현은 이 협의만으로 착수하지 않는다.

## 정본 배치 제안 — 공동 확정 필요

| 정보 | 추천 정본 | Management 역할 |
|---|---|---|
| AGENTS·목표 루프·코드 규칙·빌드/실행 방법 | Game Dev 저장소 | 원문 버전을 명시한 참조 보기 |
| 코드·PDL·스키마·테스트·코드와 함께 바뀌는 계약 | Game Dev 저장소 | 저장소 ID + commit + 상대 경로 + 심볼로 연결 |
| 시스템 설명·개발 이력·결정·검증 요약 | Management 소유 기록 저장소 | 작성·검색·표시·에이전트 조회 |
| PR·CI·로그·이미지 등 근거 | 원래 근거 또는 보존된 증거 파일 | 대상 버전·관찰 시점·출처와 함께 연결 |

Management 소유 기록은 Git으로 버전 관리 가능한 Markdown+구조화된 메타데이터를 우선 제안한다. 검색 DB는 재생성 가능한 색인으로 둔다. 앱 DB만이 유일한 복구 수단이 되는 설계는 현재 제안하지 않는다. 별도 저장소 분리 여부, 디렉터리, 형식은 아직 미확정이다.

소스 주소에 특정 PC 절대 경로를 정체성으로 쓰지 않는다. tracked 근거는 commit으로, 미커밋/로컬 근거는 보존한 snapshot·상대 경로·hash로 대상을 구별한다. PR 상태에는 조회/전달 출처와 기준 시점을 함께 둔다.

## 기존 문서 연결과 전환 원칙

- FEATURE_MAP → 시스템·코드 진입점 후보. ARCHITECTURE와 domains → 현재 설명·변경 계약의 근거. ADR → 결정. 목표별 goal/verification → 변경·검증 기록의 근거.
- 기존 문서의 여러 역할은 구분해서 옮긴다. 특히 domains의 변경 규칙과 시스템 설명을 통째로 같은 종류로 취급하지 않는다.
- 먼저 원문→새 기록 ID 대응표와 원문 버전/snapshot을 확보한다. 의미·링크·첨부·검증 수치·미실행 항목을 독립 검토한다.
- 시범 시스템으로 전투를 제안한다. 원문을 보존한 상태에서 실제 기록과 화면/에이전트 조회를 시험하고, 조회 결과의 출처·버전 일치를 확인한다.
- 새 정본이 검증된 항목만 소유권을 전환한다. 이후 기존 위치는 보관 또는 새 위치 안내로 유지하고, 두 곳을 독립 편집하는 상태를 피한다.
- 진행 중 goal의 정본은 전환 합의 전까지 그대로 둔다. Game Dev CURRENT와 공통 스킬의 원본 경로 계약은 Management가 단독 변경하지 않는다.
- 과거 작성/검증 시점·경로·결과는 소급 수정하지 않는다. 보존본은 당시 증거이고 새 위치 안내와 구별한다.

## Game Dev 메인에게 요청하는 답변

1. 정본 배치 제안에서 게임 저장소에 반드시 남겨야 할 문서·계약과 이주 가능한 범위를 알려달라. 특히 ARCHITECTURE/FEATURE_MAP/domains/ADR/완료 goal/진행 goal의 처리 기준이 필요하다.
2. 현재 진행 중인 P0~P7 및 OPEN PR과 충돌하지 않을 시점·파일 소유권·기준 commit/snapshot을 지정해달라. 앞선 전달 상태는 PR140/142 병합, PR141/143/144/145 OPEN, P0~P7는 계획/branch 준비였으므로 현재 상태가 바뀌었다면 보정해달라.
3. 전투 시스템 하나로 원문 보존 시범 이주를 시작하는 순서와, 이후 확장 전에 확인할 완료조건에 의견을 달라. Management는 기록 모델/UI/조회 경계를, Game Dev는 게임 의미·근거 버전·원문 전환을 소유하는 분담을 제안한다.
4. 에이전트의 맥락 조회를 목표 루프에 연결할 때 필요한 규칙과 실패 시 대체 읽기 방식을 협의해달라. 진행 goal/CURRENT/규칙 변경은 Game Dev가 소유하고, 기존 사용자 승인 경계를 보존한다.

답변은 짧은 동의/수정안·근거 경로·현재 Git 상태로 충분하다. 전체 소스·대화·로그를 전달할 필요는 없다. 양쪽이 같은 파일을 쓰지 않도록 Game Dev 소유의 로컬 회신 문서를 만들고 경로를 전달하는 방식도 가능하다.

## 작업 경계

현재 협의 단계에서는 문서 이동·삭제·기존 정본 폐기·게임 코드 수정·서버/WSL/SQL 실행·의존성 설치·Orca Task/Run 생성·전역 설정 변경을 하지 않는다. 사용자는 후속 대화에서 일반 세션 간 통신을 명시 허용했다. 이전 인계 단계의 IPC 재시도 제한을 이번 협의 메시지에 적용하지 않는다. 현재 실행 환경에서 일반 메시지를 주고받으며 에이전트가 권한 설정을 변경하지 않는다. 이후 구현은 Sol6.1, 독립 검증·보고는 Astra로 분리하며 새 CLI는 --no-daemon을 사용한다. 각 PR의 병합 직전에 사용자 명시 승인을 받은 뒤에만 병합한다.
