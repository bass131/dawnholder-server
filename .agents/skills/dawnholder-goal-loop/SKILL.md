# 목표 루프

역할·모델 라우팅·파일 소유권·Git 승인 경계는 [AGENTS](../../../AGENTS.md)를 따른다. 프로젝트 밖에 이 절차를 설치하거나 스킬 사용으로 실행 권한을 넓히지 않는다.

이 스킬은 이 머신의 로컬 목표·Orca 작업 절차다. 사람 팀원이 자기 머신에서 실행하는 세션은 [AGENTS 외부 팀원 세션](../../../AGENTS.md#외부-팀원-세션)의 쓰기·PR·통신 권한과 게임 기획 안내를 따른다. 담당 문서에 관련된 품질 기준은 유지하되 로컬 goal·Sol·검증자·배치 절차를 외부 팀원에게 적용하지 않는다.

## 기준과 상태

목표·허용 범위·관찰 가능한 완료조건·산출물·검증 범위를 기존 사용자 합의에서 확인한다. 이미 정한 것을 다시 묻지 않는다. 합의된 목표 폴더의 `goal.md`에 기준, 현재 상태, 주요 결정, 실제 결과·근거 경로와 미해결 사항을 모은다. `00_Document/operations/CURRENT.md`는 이 파일을 가리킨다.

goal 범위 절은 **만들 것·건드릴 곳·하지 않을 것·관찰 가능한 완료조건** 네 항목으로 쓴다. PR별 산출물·경계와 중간/종료 점검 지점을 함께 확정한다. 착수 전 메인이 승인 초안과 대조하고, 차이가 있으면 사용자가 판단한 뒤 의존 작업을 시작한다. 이미 승인된 같은 범위를 다시 묻지 않는다.

루프에서 수정할 것은 **완료조건을 막는 범위 안 결함**이다. 이에 해당하는 독립 결함, 이번 변경의 테스트/빌드/CI 실패, 계약·규칙 위반과 한정된 재발 방지를 다룬다. 같은 산출물 수정이 **3회를 넘으면 메인 체크포인트**를 알린다. 수정 횟수는 [같은 계약·결함 번호의 확정 실패 3회](../../../00_Document/operations/ORCA.md#confirmed-failures)와 별도로 기록하며 서로 대체하지 않는다.

완료조건 밖의 새 기능·화면·도구·검사·디자인·다른 영역 정리는 다음 계획 후보 한 줄로 기록하고 아이디어마다 승인을 요청하지 않는다. 새 사용자 요청도 기본은 다음 계획이며 이번 goal 포함을 명시하면 메인이 재계획한다. 애매하면 메인에 범위 판정을 묻고 기본은 밖이다. 완료조건 변경이 필요한 수정의 의존 진행은 판단 전에 멈춘다. 이번 변경과 무관한 기존 실패는 밖으로 분리하되 PR 보고에 공개한다.

사용자 교정은 [교정 층과 반복 규칙](../../../00_Document/conventions/CODE_CONVENTION.md#교정-층과-반복-규칙)에 따라 막을 수 있는 가장 높은 층을 선택하고, 문서로 끝내면 이유를 goal에 남긴다. 첫 발생은 goal 기록, 새 반복 규칙은 두 번째 발생부터다. 이 원칙만으로 새 검사·린트를 구현하거나 기존 승인 규칙을 무효화하지 않는다. 문서 가지치기는 2026-10-31 Gardener 평가 때 판단한다.

현재 goal에서 발견한 후보는 보류 목록에 원천과 [BACKLOG](../../../00_Document/operations/BACKLOG.md)의 안정적 ID/기존 예정 goal 링크를 남긴다. 점검 사이 새 아이디어의 공용 후보 정본은 BACKLOG이며 goal에 후보 상세·진행 장부를 복제하지 않는다. 이미 예정된 목표는 중복 후보로 등록하지 않는다. DB 연동 선행 등 현재 사용자 우선순위는 해당 goal의 결정에서 확인하고 과거 계획을 현재 착수 권한으로 삼지 않는다.

재개할 때 해당 목표와 Git 상태, 필요한 근거만 읽고 남은 작업을 이어간다. 전체 대화·소스·원문 로그를 목표 기록에 복제하지 않는다. 루프 정의·스킬 설정만으로 지속 목표를 활성화하지 않으며, native goal 도구는 사용자가 실제 지속 목표 시작을 명시 요청한 경우에만 사용한다.

목표 검토의 [R-7 Fable 시범](../../../00_Document/operations/ORCA.md#r7-fable-pilot)과 Astra의 [R-8 목표 종료·재진입](../../../00_Document/operations/ORCA.md#r8-astra-lifecycle)은 해당 정본을 따른다.

여러 마일스톤으로 합의된 작업을 분할하거나 재개할 때는 [마일스톤 운영](references/milestones.md)을 읽는다. 로드맵은 순서·의존성·목표 링크만, 기준·상태·결과는 각 `goal.md`에 둔다.

## 위임 계약

파트 리드와 작업자는 첫 대상 파일 쓰기 전에 [작업 맥락 스킬](../dawnholder-task-context/SKILL.md)의 역할별 최소 읽기와 사전 메모를 적용한다. 메모·규칙 원문 계약·검증 판정은 그 스킬의 [양식](../dawnholder-task-context/references/templates.md)을 사용하고 완료 보고에는 계획과 구분한 실제 준수 위치를 남긴다.

파트 리드 Astra는 [코드 작성 기준](../../../00_Document/conventions/CODE_CONVENTION.md)의 관련 부분을 읽고 설계 → 분할 → 외부 Sol 구현 → 신규 외부 Opus 실사·테스트 → 문서 → PR 순서로 진행한다. 내부 서브에이전트는 읽기 전용 조사·요약에만 쓴다. 선택한 경계·이유·보존 동작을 기록한 뒤 파일 소유권을 정한다. 위임할 때 관련 코드·문서는 경로와 필요한 부분으로 한정해 다음을 전달한다.

반복 규칙의 검사화·수리 안내, 정본 helper의 짧은 경로, 수기 목록 존재 검사, warning→실측→사용자 승격/강등, 실행불가/위반 구분과 구조/동작 별도 커밋은 [하네스 원칙](../../../00_Document/conventions/CODE_CONVENTION.md#하네스-원칙)을 다음 계약부터 승인 범위에 적용한다. 이 하네스 원칙만으로 주석 삭제·작은 작업 예외·검증 차등·가지치기를 도입하지 않는다. 이미 진행 중인 계약과 검증의 고정 입력은 조용히 바꾸지 않고 [버전 인계](references/orca-work.md#역할과-작업-계약)로 연결한다.

- 요구사항·보존 동작·완료조건과 설계 선택 기준.
- 허용 파일·쓰기 소유권, 필요한 최소 맥락.
- 적용할 CODE_CONVENTION 관련 절 원문 전체와 출처 경로·기준 commit 또는 미커밋 hash. 링크나 요약으로 원문을 대체하지 않는다.
- 검증 범위·환경, 명령 실행·외부 변경 권한.
- 원본 로그 저장 위치(TEMP 또는 목표 산출물 경로)와 결과 보고 위치.
- 역할·발신 태그·지정 모델, 작업 하나 후 정산·종료 및 재사용 금지. 제품 파일과 테스트 파일의 소유권을 분리한다.

의존성이 없고 파일이 겹치지 않는 작업은 병렬로 맡긴다. 구현자와 독립 검증자는 분리한다. 리뷰어에게는 요구사항·변경 대상·원시 근거를 주며 예상 답·의심 결함·이전 평가로 결론을 유도하지 않는다. 소유권 이전은 기존 작업의 쓰기 종료 후 명시한다.

외부 세션 작업자를 발행할 때 [Orca 위임 지침](references/orca-work.md)의 pane 배치·준비·정산 절차를 읽는다. 일반 작업자에게 추가 분할 권한이 생기는 것은 아니다.

## 구현·검증·수정

구현자의 쓰기 종료 뒤 신규 Opus 검증자에게 테스트 파일 소유권을 배정하고 [역할별 적용 기준](../../../00_Document/conventions/CODE_CONVENTION.md#역할별-적용)에 따라 먼저 보고와 실제 수행을 실사한다. 실제 코드 변경은 독립 테스트 코드 작성·실행, 문서만 변경한 경우는 정적 검토로 구분한다. 검증자는 제품 코드를 수정하지 않는다. 결함은 번호로 반환해 새 Sol 세션에서 수정하고 새 Opus 세션에서 재검증한다. 확정 실패 3회 집계와 네 번째 새 Sol/Fable, 다섯 번째 전 메인 판단은 [실패 정본](../../../00_Document/operations/ORCA.md#confirmed-failures)을 따른다.

검증자는 결함을 반환하거나 재검증할 때 각 결함의 「이 결함을 검사로 바꿀 수 있나」 판단을 [검증 판정 양식](../dawnholder-task-context/references/templates.md#검증-판정)에 기록한다.

범위 안의 수정·검증은 계속한다. 설계 분기·범위 변경은 메인이 선택지·영향·추천을 정리해 사용자와 결정한다. 반복 실패·도구 부재·외부 의존은 원인과 영향을 기록하고, 영향을 받지 않는 일은 이어간다. 메인이 알리지 않고 구현 전체를 떠맡지 않는다.

검증자는 작업 맥락 스킬에 따라 메모·원문 계약·실제 diff를 대조하고 가독성·주석 위치·책임 분리·배치/이름·탐색·중복 이유를 판정한다. 메모 부재·관련 원문 누락·적용 규칙 위반·메모/결과 불일치는 수정 또는 메인 결정 전 통과를 차단한다. 검토했고 지적 없음·미검토·해당 없음과 이유를 구분한다.

측정값 위장·제품 계산 복제로 항상 통과하는 테스트, 실패한 기존 테스트의 전수 분류와 사람 가독성 지적은 [작업 맥락 판정 정본](../dawnholder-task-context/SKILL.md#독립-판정과-통과-차단)을 따른다. 같은 부류의 출처 누락은 이번 BACKLOG에서 행이 달라도 같은 부류로 보고한 사례와 전수 대조 근거를 보존한다. 이를 일반 집계로 승격하려면 구체안·영향을 Astra에 질문하고 관련 없는 허용 구현은 계속한다. 현행 같은 계약/번호 확정 실패 집계·중복 금지를 임의 교체하지 않는다.

## 통합과 보고

Astra는 판정 원문과 필요한 근거를 메인에 전달하고 승인된 범위의 commit/push/PR을 맡는다. 메인은 판정 원문을 읽고 [R-2 원천 표본 대조](../../../00_Document/operations/ORCA.md#r2-source-check)를 따른 뒤 사용자에게 최종 보고한다. 병합 권한과 자동 병합 금지는 최신 [AGENTS](../../../AGENTS.md#git-권한)를 따른다. 구현·검증 완료와 승인·병합 대기를 구분한다.

Astra의 복귀 보고는 변경 요약·검증 근거 위치·리스크·결정 요청·판정 원문 경로로 구성하고 유형은 [R-4](../../../00_Document/operations/ORCA.md#r4-report-type)를 따른다. 원문 로그와 작업자 전체 대화는 붙이지 않는다. 사용자 최종 보고 형식은 [AGENTS의 메시지와 보고](../../../AGENTS.md#메시지와-보고)를 따른다.

완료조건을 실제로 충족한 뒤 목표 결과를 갱신한다. 문서·스킬 정비만으로 새 세션 자동 선택·게임 실행·DB 연결이 확인되었다고 말하지 않는다.

계획의 기본 점검은 전체 goal 종료이며 긴 goal의 중간 점검은 계획에서 지정한다. 예를 들어 현재 하네스 goal은 첫 BACKLOG PR 병합 뒤 중간 점검, 전체 PR/결과·[Gardener](../../../00_Document/operations/ORCA.md#goal-gardener) 뒤 종료 점검이다. PR 줄 수 상한으로 점검을 대신하지 않는다. 메인이 사용자와 결과·남은 위험·BACKLOG·다음 계획을 확인한 뒤 재개한다. **다음 goal은 자동으로 시작하지 않는다.** 로드맵 초안/갱신은 [마일스톤 종료 점검](references/milestones.md#검증과-인계), Astra 교체는 R-8을 따른다. 첫 PR마다 신규 Gardener를 자동 추가하지 않는다.
