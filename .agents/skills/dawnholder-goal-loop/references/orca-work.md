# Orca로 독립 목표를 위임할 때

큰 독립 목표를 별도 Orca 세션·worktree·작업 브랜치에서 진행하거나 실제 세션 감독이 필요할 때만 읽는다. 기본 절차와 현재 연결 검증 상태는 [ORCA.md](../../../../00_Document/operations/ORCA.md)에 있다.

## 역할과 작업 계약

메인은 사용자와 목표·범위·완료 조건 및 중요한 결정을 다룬다. 구현·검증·테스트는 작업자에게 최대한 위임한다. 메인이 명시 지정한 Orca 목표 담당자(coordinator)만 허용된 단일 목표·작업 공간·권한 안에서 좁은 구현·검증 작업을 한 단계 분할할 수 있다. 일반 작업자(leaf)는 재귀 위임하지 않는다. 새 독립 목표·범위 확대·추가 Orca 세션 생성은 원래 메인에 요청하고, 파일 소유권이 겹치지 않게 한다.

위임 입력은 아래 정도로 제한한다.

- 목표와 관찰 가능한 완료 조건.
- 필요한 파일·이미 합의한 결정·입력 자료의 위치.
- 작업자가 수정할 파일 범위와 건드리지 않을 영역.
- 검증 기준 및 DB·7777·Unity·WSL 작업 공간의 실행 소유권.
- 작업 결과를 기록할 위치와 막히면 메인에 올릴 판단 사항.

별도 검증자는 구현 diff와 기준을 읽고 필요한 검사·테스트를 수행한다. 구현 결함은 작업자에게 반환하고, 설계나 범위를 바꿔야 하면 선택지와 근거를 메인에 올린다. 복귀 정보는 **변경 요약 / 검증 근거 위치 / 리스크 / 결정 요청** 네 가지다. 원본 로그는 파일 또는 해당 Orca 작업 기록에 남긴다.

## 실제 실행 전후

1. 설치된 `orca-cli` 스킬로 해당 세션의 CLI를 선택하고 버전 일치 가이드를 읽는다. 신규 세션의 준비 확인과 단순 인계는 [세션 인계 스킬](../../dawnholder-session-handoff/SKILL.md)을 따른다. 사용자 요청이 감독·결과 대기·DAG 조정일 때만 `orchestration`을 적용하며 단순 handoff에는 작업 추적을 만들지 않는다. 명령 문법을 이 문서에서 추정하지 않는다.
2. 현재 런타임과 정확한 저장소·작업 공간을 확인한다. 감독형 Run/Task/Dispatch와 단순 소유권 handoff를 구분한다.
3. 독립 목표는 최신 main을 확인한 뒤 새 top-level worktree와 작업 브랜치를 사용한다. 현 기능 브랜치를 기본 출발점으로 삼지 않는다.
4. 실제 시작 응답에서 준비 상태·작업 공간·모델을 확인한다. Astra를 명시했다면 요청값과 적용값을 대조한다. 초기 실패에는 응답의 recovery 절차를 따른다.
5. 감독형 작업에서는 `worker_done`과 근거를 확인하고 공식 종료·재사용 절차를 마친다. PR 생성은 허용하지만 각 PR 병합 직전에는 사용자 명시 승인이 필요하다. 메인·목표 담당자의 판단이나 이전 포괄 승인으로 대체하지 않으며 자동 병합을 예약하지 않는다. 통합 뒤 영향 범위를 다시 검증한다.

`98_Shared/Protocol`과 생성 파일의 동시 수정, 공유 WSL clone 동기화, 7777 포트 경쟁, 공용 DB 쓰기, Unity Library 공유를 피한다. 구체적인 실행 방식은 [DEVELOPMENT.md](../../../../00_Document/operations/DEVELOPMENT.md)에서 확인한다.

이것은 요청 범위와 보고를 통제하는 운영 규약이다. 기술적 강제·컨텍스트 오염의 완전 차단·무인 복구를 보장하지 않는다. 별도 AgentDeck 시스템 개발은 포함하지 않는다. 일반 서브에이전트 실행을 실제 Orca runtime 검증의 대체 근거로 삼지 않는다.
