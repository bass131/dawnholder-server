# 마일스톤 분할과 재개

사용자가 여러 단계의 작업을 합의했을 때 적용한다. 새 목표를 임의로 추가하거나 이미 끝난 정리를 재개하는 근거로 사용하지 않는다.

## 기록 위치와 재개

- 계획 때 두 개 이상 goal로 이어져야 끝나는 안건이면 로드맵을 만들거나 갱신하고 각 goal이 그 로드맵을 링크한다. 이번 진행 중인 goal에 실제 파트 로드맵 작성 범위를 주입하지 않는다. 담당 리드는 종료 점검에서 초안을 내고 사용자 확인 뒤 갱신한다.
- 프로젝트의 `01_Phases/milestones/<이름>/roadmap.md`는 단계 순서·선행 의존성·목표 링크만 유지한다. 진행률·검증 결과·결정은 복제하지 않는다.
- Management는 goal이 `05_Management/goals/`에 있으므로 실제 마일스톤 위치를 해당 리드와 조율한다. 이름은 목적 중심으로 쓰고 번호 표기는 [REPORTING](../../../../00_Document/conventions/REPORTING.md#사용자-최종-보고-형식)을 따른다. 역사 코드를 무관하게 일괄 변경하지 않는다.
- 각 목표의 범위·제외·완료조건·파일 소유권·검증·실제 결과는 해당 `goal.md` 한 곳에 둔다. 평가 방법 같은 재사용 계약은 별도 문서로 연결하되 측정 결과는 목표에 기록한다.
- `CURRENT` → 현재 `goal.md` → 필요한 로드맵/계약 순서로 읽는다. 브랜치·HEAD·작업트리를 확인하고 기록과 다르면 메인이 차이를 정리한 뒤 남은 작업을 잇는다. 전체 과거 대화·소스·로그를 다시 수집하지 않는다.
- 예정 목표 문서는 착수·실행·병합의 증거가 아니다. 다음 목표는 선행 목표의 실제 결과와 사용자 합의 범위를 확인한 뒤 최신 `main`의 별도 브랜치에서 시작한다. 앞 목표의 병합 승인은 다음 PR의 승인이 아니다.
- 병합은 [AGENTS Git 권한](../../../../AGENTS.md#git-권한)을 따른다. 마일스톤 계획이나 이전 포괄 승인으로 각 PR 병합 직전의 사용자 명시 승인을 대신하지 않는다.

## 분할과 실행

각 단계는 **설계 문서화 → 구현 범위·계약 정리 → 작업 단위·외부 세션 분할 → 구현 → 독립 검증 → 결과 문서화 → 합의한 다음 단계** 순서로 진행한다. 대안 요약만으로 구현에 들어가지 않는다. 선택한 설계·이유·보존 동작·인터페이스·검증 경계를 해당 goal의 설계 절 또는 연결된 설계 문서에 남긴 뒤 구현 파일과 작업 소유권을 확정한다. 모델·신규 작업자/검증자·작업 하나 뒤 종료는 [AGENTS](../../../../AGENTS.md)를 따른다. 독립 세션을 생략하는 작은 작업 예외는 없으며 문서 실사·강/약 검증은 [검증 강도 4주 시범](../SKILL.md#검증-강도-4주-시범)을 따른다. 다음 단계가 새 goal이면 아래 종료 점검 뒤 재개한다.

이미 승인된 순차 작업은 매 단계 승인을 반복 요청하지 않고 진행한다. 설계 중 생긴 범위·게임 정책 분기는 메인이 기존 합의 안에서 판단하고, 합의 밖 결정이 필요하면 사용자와 정한다. 각 PR 병합 승인은 기존 AGENTS 경계를 그대로 따른다.

한 마일스톤이 큰 경우 독립 검증 가능한 작은 목표/PR로 나눈다. 메인이 각 목표의 경계와 의존성 링크를 정하고, 원래 목표에는 분할 결정과 후속 링크만 남긴다. 미완료를 완료로 표시하거나 같은 상태를 여러 장부에 쓰지 않는다.

서버/클라이언트처럼 파일이 분리돼도 프로토콜·공유 타입·전환 순서가 연결되면 먼저 보존 계약을 합의한다. 공유 파일의 쓰기 담당자는 한 명으로 두고 소비자는 그 계약이 확정된 뒤 진행한다. 통합 검증은 구현자와 분리한 검증자가 맡는다.

게임 정책을 바꾸는 선택은 구조 정리와 구분한다. 예를 들어 맵 이동 시 쿨다운 유지 여부, 파티 해산 후 진행도, 재접속 복원 범위는 메인이 사용자와 결정한다. 합의 전에는 현행 동작을 보존하며 조용히 새 정책을 채택하지 않는다.

스킬 읽기만으로 세션을 추가하거나 전역 권한·설정을 변경하지 않는다. Orca 세션이 실제로 필요한 경우에만 별도 [Orca 위임 지침](orca-work.md)을 읽는다.

## 검증과 인계

계획에 기본 **goal 종료 점검**과 필요한 중간 점검을 명시한다. 완료조건·PR 경계·범위 밖 목록의 판정은 [goal-loop](../SKILL.md#기준과-상태)에 둔다. PR 줄 수 상한을 두지 않으며 점검 사이 새 아이디어는 BACKLOG 후보와 goal의 한 줄 링크로 기록한다. 첫 BACKLOG PR 병합 뒤 중간 점검과 전체 종료 점검을 둔 현재 하네스 goal은 그 계획대로 진행한다.

전체 goal의 PR 병합·결과 기록·[Gardener](../../../../00_Document/operations/ORCA.md#goal-gardener) 뒤 메인이 사용자와 결과·남은 위험·BACKLOG·다음 계획을 확인한다. 담당 리드는 다음 단계·선행조건·바뀐 순서의 로드맵 초안을 내고 사용자 확인 뒤 갱신한다. 이후 로드맵의 다음 단계나 BACKLOG에서 다음 goal을 고르고 재개한다. 다음 goal 자동 착수는 금지하며 리드 교체는 [R-8](../../../../00_Document/operations/ORCA.md#r8-astra-lifecycle)을 따른다.

실행 전 [개발 안내](../../../../00_Document/operations/DEVELOPMENT.md)의 생성물·DLL 복사·포트·작업 공간 부작용을 확인한다. 빌드, 서버 테스트, 봇, Unity 컴파일/EditMode/실제 플레이, DB 검증을 별도 결과로 기록한다. 실패·차단·미실행을 성공으로 합치지 않는다.

목표 종료/세션 인계 시 `goal.md`에 다음 최소 정보만 남긴다.

- 목표 상태, 브랜치/base/HEAD, PR와 각 병합 승인·병합 여부.
- 확정한 결정과 보존할 정책, 변경 파일과 쓰기 종료/현재 소유자.
- 검증 명령·환경·결과·짧은 근거 경로, 미실행 범위와 영향.
- 다음 실행 항목·선행 조건·미해결 질문, 보존할 서버/Unity/SQL 등 실행 자원.

원문 로그는 별도 산출물에 두고 경로로 연결한다. 측정이나 테스트가 남았으면 그 상태를 그대로 인계한다. 문서·스킬은 안내이며 자동 기억·행동 강제·실행 성공을 보장하지 않는다.
